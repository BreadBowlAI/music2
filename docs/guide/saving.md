# Saving and undo

**In short**
- There's no Save: every change is written to the song's files at once, and Undo (⌘Z) takes it back, also after you close the song or the app.
- Code you typed and didn't save is kept too: after a crash, the code editor offers it back.
- Changes made by agents and other programs show as they land, each one undo step. V plays before and after.
- You win every clash: an agent waits while you hold what it would change.

- There's no Save for the song: every change is written to the files at once. ⌘S only saves the code editor's text.
- A note edit is heard at once, while it's being written to disk. If the disk refuses it (it's full, say, or another program replaced the file at that moment), the edit is taken back and a message says why; if the disk is slow to answer, a message says the edit isn't saved yet, and another says when it is. The same goes for an edit an agent sends while the song plays: the app says when it was taken back.
- Every edit made in the app is checked before it's written: the app works out what the change does to the song and refuses it if it would do anything else. An edit that touches several files (automating a knob writes its code and a new lane file) is written as one, all or nothing.
- Undo (⌘Z) and redo (⇧⌘Z) cover knobs, cables, effects, notes, renames, automation, fixes, code saves, and text files saved in another program while the song is open. Their tooltips, and the Edit menu, say what they take back ("Undo Hats volume"), also for an edit made in another window ("Undo Bass notes"), for an agent's change, by its name and its words ("Undo Claude: brighter hats"), and for a file saved in another program ("Undo outside change: the code in tracks/bass.ts"). Undo takes back the newest change, whoever made it, and only the one its name showed. If a change landed elsewhere after the name showed, Undo changes nothing and says which change is the newest now; press it again to take that one back. The history is kept with the song, so Undo and Redo still work after you close the song or the app, or after a crash (see below). An edit saved in another program is a change of its own, so Undo takes that back first. Undo is refused only when what it would put back changed since in a way that made no undo step (git, or a batch with an audio file in it, below); a change somewhere else in the file doesn't block it. Then the message says which file changed, with **Skip it**: that leaves your files as they are and lets Undo go on to the changes before it.
- Changes made in another editor, or by a script or git, show up once the other program has stopped writing for a moment (150 milliseconds, so usually within a quarter of a second). A file caught half-written never plays: a lane keeps the notes it had until its file reads again, and a code change that doesn't compile yet holds back the data saved with it, so a lane never plays empty in between. The app hears of changes from the system (FSEvents on a Mac, inotify on Linux), so an open song nobody is changing costs next to nothing, however many samples it has. On a network drive, which doesn't report other computers' changes, it reads the song's folder instead: every 50 milliseconds for a small song, less often for one with thousands of files, and at least once a second.
- While the song is open, each change an agent makes through `m2` (or the local API with the tools key, [Scripts and agents](api.md)), and each change to a text file saved in another program, is one undo step, and the app shows it as it lands. A notice at the foot of the timeline says who made it and what it is: "Claude: brighter hats", or "Changed outside the app: the code in tracks/bass.ts", with **Undo**. Several from the same author in a row are counted: "Claude: 3 changes · newest: brighter hats". The tracks, clips and knobs it changed are outlined until your next click or key press. The notice never takes the keyboard, and goes after 6 seconds (point at it to keep it). Its Undo takes back that change only, while it is the newest and undo can take it back; once a newer change came, it says so instead. A code-editor save of yours that didn't build yet stays yours: if another program's change then makes the song build, Undo takes back only that program's change. Some outside changes can't be undone in the app, and a message says so, with how many other files changed with them: a changed or removed audio file or plugin state (its old bytes are gone), a file that is a link, a file renamed only in capitals, and a change too big for undo to keep. Whatever git writes makes no undo step either (git can take it back): that is when git was running as the change landed and the files are now as git has them; a save while a `git status` runs is still a step. A new audio file in `assets/` stays when its change is undone. A change to `layout.json` alone makes no undo step: the app just shows it. A song open read-only keeps no undo steps of what the other window changes.
- **Hear before and after (V).** When the newest change was made by an agent or saved in another program, press **V**: you hear the song without it, and a pill in the top bar says "Before: Claude: brighter hats". Press V again (or click the pill) for "After", the song as it is. V only changes what you hear: the song's files, undo and what the window shows stay as they are, so quitting, or a crash, while you hear Before leaves the song as it was. You can flip while the loop plays; holding V down is one press. While the pill shows, agents wait: their changes are refused until it closes. Play, stop, the loop and the ruler keep it open: comparing is listening. Esc closes it and keeps what you hear: on Before, the change is undone then, one undo step, and a message says so, with **Redo**. Anything else you do closes it and goes back to the song as it is. A file another program saves meanwhile closes it too, and a message says so. On your own change, V says it is for changes made elsewhere: ⌘Z is yours.
- **Pointers.** An agent can point at a track, a clip, a lane, a knob or some bars (`m2 point`) to show you where something is: a small note there, with its name and words, "Claude: listen to the hats here", and **OK** to dismiss it. It never scrolls, zooms or selects anything, and a click on its words reaches what is under it: only Show and OK are its own. When what it points at is out of view, the note waits at that edge with **Show**, and only that click moves the view; Show never selects. A knob of a track the dock doesn't show is named beside that track's header (select the track to see it). It is never saved: one at a time, gone when the song closes.
- **Undo after closing.** The undo history is kept in the song's `.music2/` folder, written as each change lands, and read back when the song opens: Undo's tooltip names the same change it did before you closed it. It keeps the last 500 changes, up to 64 MB of text and 256 MB of plugin states; the oldest go first. Undo takes a change back only while the files it touches are exactly as that change left them. If a file was changed outside music2 while the song was closed (by git, another editor, or an agent writing it), Undo stops at the change that touched it, and its tooltip says "Undo isn't possible past the change made outside music2" (Redo the same). Changes to other files can still be undone. If the history can't be read (a disk fault, say), the song opens with no undo, and the status pill says so. It never undoes the wrong thing: a crash can make it forget the newest change, never mix changes up.
- **Unsaved code after a crash.** Code you type in the code editor and haven't saved yet is kept in the song's `.music2/` folder a second after you stop typing. It is never written to the song itself, so nothing plays it. If the app stops before you save (a crash, or quitting without saving), a notice says so when the song next opens, with **Show code**, and the code editor asks: "song.ts has changes that weren't saved. Restore them?" **Restore** puts your text back in the editor, still unsaved (⌘S saves it); **Discard** throws it away. If the file was changed since (by a knob, an agent or another editor), it says so first, and nothing is put back unless you click Restore. A song open read-only keeps no unsaved code.
- If another program changes a clip while you're editing it in the piano roll, your edit of that clip is refused, saying which clip, and the other program's version stays. Edits to different clips of one lane both stay.
- You win every clash with an agent. While you drag a knob, a clip or the tempo, record a take, compare with V, change a plugin's sound in its window before it is saved, or have unsaved code in a file, an agent's change to what you hold is refused (anything at all while you record or compare); it waits and tries again, and nothing you hold ends or waits for it. If you start a drag while its change is landing, the app takes the change back before you hear it. This only covers changes that come through `m2`: a file an agent writes directly can end your drag, as any outside save can.
- One program writes a song at a time. While the app has a song open, `m2` commands that write it hand their edit to the app, which makes it one undo step, the agent's; ones that only read it, render it or bounce a track work as they always did. A song that's open for writing elsewhere (another music2 window, say) opens read-only: the status pill says **Read only**, and its popover says where it is open, with **Retry** to take it over once it's free. You can play it and see its changes; nothing offers to edit it meanwhile.
- The lock and the edits being written live in the song's `.music2/` folder, which git ignores. If the app or the Mac stops in the middle of writing an edit, the status pill says so when the song opens next, with **Finish it** and **Discard it**: either leaves every file as it was before the edit or after it, never half.
- Problems that don't stop the song, such as data no lane reads after a key was renamed in code, a data file that doesn't read, or a missing sample or plugin, are counted by the status pill in the top bar ("2 problems"); click it for each one, with its fixes (and its code, under Details). So is a part that breaks while the song plays: a sound, a plugin, an audio file that can't be read, a stretch that failed, or the sound input. That part goes silent alone, the rest plays on, a message says so once, and it stays listed, with its track, until it plays again (Transport → Stop All Sound starts a stopped sound again). A fix runs only when you click it, and Undo takes it back. When a track's key was renamed in code, **Move all to …** moves its whole data folder to the new key at once.
