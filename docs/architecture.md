# Architecture contract

**Normative.** Adopted 2026-10-12 as step 2 of the [order of work](#order-of-work), and revised the same day after three reviews (a DAW producer's, a core engineer's and an accuracy check against the code). Every later step is built and reviewed against this page. Where [Song as a program](song-as-program.md) or the [code and graph editing design](code-graph-editing-design.md) disagree with it, this page wins. Those pages keep the product design and the reasoning behind it.

## How to read this

- **MUST**, **MUST NOT**, **SHOULD** and **MAY** mean what they mean in RFC 2119. A SHOULD may be broken only with the reason written next to the code that breaks it.
- Every rule has an id, such as `RENDER-8`. A test that checks a rule names the id in a comment. A change that breaks a rule changes this page first, in the same commit. A rule inserted after adoption gets a letter suffix (`RENDER-6a`); one added at the end of its section takes the next number. Ids already cited never move.
- **Why** gives the reason in one line. **Today** says where the code differs, or that it already matches. File and line pointers are to commit `92a19a3`. Step 1's code is named by file only, since it lands after that commit.
- "Step n" means a step in the [order of work](#order-of-work).

### Words used here

| Word | Meaning |
|---|---|
| **key** | A short readable name a person writes in code, such as `"lead-vox"`. Saved data is filed under keys. |
| **label** | Display text, such as `"Lead Vox"`. Never an address. |
| **module** | A graph with lanes and exports: the root module `song`, or a track. |
| **site** | One call expression in the source. |
| **revision** | An accepted state of the project: the pair `(code_rev, data_rev)`. |
| **cell** | Host-owned engine memory that holds one editable constant. |
| **plane** | The path a change takes through the system, chosen by the kind of file it touches. |
| **engine clock** | Samples processed since the live engine started. It only moves forward. |
| **transport clock** | The song position. It jumps on seek and loop. |
| **fixture** | One of the 5 projects in the repo: `examples/first-song`, `examples/with-plugins`, `examples/resample`, `templates/starter`, `templates/empty`. |
| **pure** | Made only of WebAssembly kernels, so it renders the same bits every time. A song with a hosted plugin is impure. |

## Owner decisions

These answer the plan's open questions (2026-10-12).

1. **Live and export.** Live playback may differ from export after a jump or an edit (tails, held notes, replaced nodes that start fresh), as in other DAWs. Export is always exact and deterministic. (Exact means an offline render from sample 0 for every song. Deterministic to the bit holds for pure songs, [RENDER-2](#offline); a song with a hosted plugin reports that it isn't reproducible.)
2. **Track signature.** The key comes first: `track("lead-vox", { name: "Lead Vox" }, fn)`, or `track("kick", fn)` with the label defaulting to the key.
3. **After the core,** synth and plugin work alternates with audio and sample work.
4. **Mute and solo** are listening-only monitoring overlays that never change the export. A separate "mute in song" is saved in code.
5. **Agents** may keep writing files directly. That is the save path, with loud diagnostics. Verified Tx edits are opt-in.
6. **A project whose code doesn't compile** opens silent, with diagnostics, so it can be fixed in the code editor.
7. **Patterns and events generated by code** get reserved room now (the `const-events` op) and are built later.
8. **Realtime target:** 50 tracks now. Partitions and threads come right after the arena.
9. **The data folder** is renamed from `timeline/` to `data/`.
10. **The project lock** is adopted now as a rule, and built in step 6 ([WRITE-17](#the-project-lock), [WRITE-18](#the-project-lock)). Forwarding CLI and MCP writes to the lock holder is deferred: a writer that can't take the lock fails with a clear message.

## Principles

- **P1. Identity has three kinds, each with its own rule.** Saved identity is a key written by a person in code. Derived identity lives only in memory. Labels, binding names, file paths, ordinals, array indexes and build-local counters are never identity.
- **P2. Files are the truth, and every writer is first class:** the app, the CLI, agents, text editors and git. Nothing that matters depends on an index only the app maintains.
- **P3. Only the files on disk decide what is accepted.** The session never moves, deletes or repairs files because it noticed something. Relinks, journal recovery and id assignment are offered as fixes, never applied automatically. The build reads nothing but the snapshot.
- **P4. Two write primitives and one music2 writer process:** `save()` for drafts, `Tx` for verified edits, and a project lock. Outside writers (editors, agents, git) can't be locked out; the watcher takes their changes in ([WRITE-19](#outside-writers)).
- **P5. Four planes of change,** chosen by which kind of file changed, not by who wrote it.
- **P6. Offline render is exact from sample 0.** Live playback is a persistent engine with two clocks. Live playback never replays, and export is always offline.
- **P7. Code that builds the graph never reads timeline data.** Notes reach instruments as sample-stamped event buffers.
- **P8. Each value has one home, and the UI shows which.** Monitoring overlays never change the song or the export.
- **P9. Break the format and the SDK once, now,** while the only projects are the 5 fixtures. Version them separately.
- **P10. Core holds no UI vocabulary:** no effect categories, knob ranges, undo labels or unit spellings. Core is what safety, determinism and a single source of truth need.
- **P11. The engine reaches plugins only through `PluginHost`.** Nothing assumes a plugin shares the app's process or threads.

## Planes of change

| Plane | Changed files (`DataPath` class) | Path | Budget |
|---|---|---|---|
| **Control** | none: cells, transport, audition, overlays, leases | an engine message or cell write; never the session | the next audio block |
| **Data** | Data: notes and control lanes | no QuickJS run; checked against the accepted lane declarations; `SwapLane`, sent as a preview once the Tx's candidate passes and its files still read as their bases, while the commit is made durable ([PLANE-5](#planes-of-change)) | under 20 ms from the edit's request to the first block that plays it; the time until the commit is durable, journal sync included, is measured beside it ([PLANE-5](#planes-of-change)) |
| **Prepared data** | Data: audio lanes, assets, plugin state | no QuickJS run; clip renders and state loads prepared off the audio thread; an `Activate` of the same structure that keeps every instance | no glitch; the old data plays until the switch, which waits for the renders ([RENDER-27](#plans-data-and-arrangement-swaps)) and the state load ([RENDER-26b](#plans-data-and-arrangement-swaps)) |
| **Arrangement** | Arrangement: tempo and meter | tables and clip renders prepared off the audio thread; an `Activate` of the same structure | no glitch; the old arrangement plays until the switch |
| **Code** | Code, Manifest | compile, check, verify, prepare against the plan that plays; `Activate` | audible under 200 ms after the compile finishes, not counting plugin loads ([RENDER-25](#plans-data-and-arrangement-swaps)) |

**PLANE-1.** The plane of a change MUST be chosen by `DataPath::class()` of the files it touches, and for Data, by whether it needs a render or a state load; never by who wrote them.
- *Why:* a lane file written by an agent or by git must get the same fast path as the app.
- *Today:* matches since step 6. A Tx or an outside batch that changes no Code, Manifest or Arrangement file takes the data path: its data is read against the accepted code, with no QuickJS run, and only `data_rev` moves (`core/session/src/take.rs`; `kind_of` in `core/session/src/tx/mod.rs`; `an_outside_lane_write_takes_the_data_path`, and through the server's watcher `an_outside_lane_write_is_swapped`). A lane whose file is the text it was read from keeps that read, so only the files a change touches are parsed (`Project::data` in `core/song/src/data.rs`). Since the G11 fix a `Clips` Tx parses nothing it doesn't change either: the editor and the plan take the accepted revision's read of a text that is the file (`DataSet::parsed`), the lane the plan made is the candidate's own data when its canonical text reads back to it bit for bit (`LaneData::reads_back`; else the text is parsed), snapshots share their texts and binaries map (`Arc`), so a clone or a diff costs the files that changed, and check, the planner's assertion and commit are one call with one read of the targets (`Session::commit_with`). `a_lane_write_after_an_outside_edit_is_planned_on_the_file` and `commit_with_is_check_then_commit` test them.

**PLANE-2.** A change that touches files of several classes MUST take the slowest of their planes (Code, then Arrangement, then prepared data, then Data).
- *Why:* one revision must never mix a new graph with stale timing.
- *Today:* matches since step 6: a change is named by the slowest plane of its paths (`take::Plane`), and a batch that changes code is compiled whole with its data (`core/session/src/take.rs`).

**PLANE-3.** Changes to Presentation or Ignored files MUST NOT create a revision.
- *Why:* moving a node on the canvas must not recompile or rebuild anything.
- *Today:* matches since step 4: a snapshot holds only what `DataPath` classes as Manifest, Code, Arrangement and Lane, and state sidecars, so `layout.json`, `.music2/` and other files make no revision (`core/song/src/lib.rs`; tested in `core/session/src/gate_tests.rs`).

**PLANE-4.** The compile itself SHOULD stay under 100 ms at p95 at 50 tracks.
- *Why:* the code-plane budget starts after the compile, so a slow compile is felt directly.
- *Today:* 84 ms measured at 50 tracks. Going over is the trigger for incremental compile ([Deferred](#deferred-with-triggers)). Step 5 made the build and check of p50 about a third slower, 33 → 44 ms at p95 (release, `m2_script::build_full` then `m2_ir::check`), since every control a std call leaves out is now a const ([PKG-3](#component-descriptors)).

**PLANE-5.** A Tx on the Data plane MUST be heard without waiting for the disk, and MUST NOT be accepted before it is durable. Once its candidate passes (its delta, its expectation and its planner's assertion) and every file it touches still reads as its base ([WRITE-15](#commit-journal-and-recovery) step 1), the engine is sent the candidate's lanes as a preview `SwapLane`, and the commit goes on to journal, stage, make durable (one barrier, `m2_os::fs::barrier`: `F_FULLFSYNC` on macOS, or `fsync` on a volume that refuses it; `fsync` on Linux) and rename. A lane that needs more room than its scheduler has, or a change the engine can't reach from what it plays by lane swaps alone, is heard once the commit is accepted, through an activation that keeps every instance ([RENDER-26](#plans-data-and-arrangement-swaps)). The revision, its `data_rev` and its undo step exist only once the renames are done. A commit that fails after its preview swaps the accepted data back, under the sounding-note rules of [RENDER-26a](#plans-data-and-arrangement-swaps), and says so in its error, which the app shows as a message. The sync is never skipped or weakened to meet the budget. The 20 ms is measured on the [reference Mac](#acceptance-gates) from the request to the first block that plays the preview. The time until the commit is durable is measured and reported beside it, on an idle disk and on one another writer keeps busy.
- *Why:* on macOS the durable sync alone took about 5 ms on an idle disk and up to 12 ms on a busy one when step 6 measured it, so a note that waited for it would be late whenever the disk is shared. An edit reported saved must survive a power loss. On the Linux development server a whole commit's syncs took 0.6 ms idle and 1.5 ms at p95 while another program wrote 1 GB (drives with power-loss protection, so a best case); the budget is judged on the reference Mac.
- *Today:* matches since the G11 fix. The session tells its host of a commit between its pre-check and its journal (`Session::before_write`, `Writing` in `core/session/src/tx/mod.rs`; the callback of `stage::commit`), for every judged Tx (a gesture's, an agent's, an undo's), never for a save, a recovery or a refused Tx, and checks its lock again after. The server's actor sends the candidate's lanes there (`crates/server/src/graph/preview.rs`) when the commit is data only, what plays is the accepted revision, and every lane fits its scheduler; what plays is then the candidate, and the settle after the commit adopts the accepted revision, sending nothing, or swaps the accepted data back. A failed commit's error ends "It played for a moment and was taken back." (an agent's refusal says `"taken_back": true`), or, when its rollback failed too, points to Needs attention; with the transport stopped nothing was heard, and the error says only what wasn't saved (`with_the_transport_stopped_no_message_says_the_edit_played`). A commit still not durable after 2 s is said in a message, and so is its save once it is (`a_save_the_disk_is_slow_to_make_is_said`), from a server thread that never waits for the session's actor, so an outside save that settles meanwhile doesn't hold it back (`the_server_says_a_slow_save_while_an_outside_save_waits_behind_it`). Every window is told how a commit ended when the transport played while it was previewed, or the user was told it isn't saved yet, whoever sent it: an agent's commit taken back is said in the app too (`an_agents_write_heard_and_taken_back_is_said_in_the_app`), and the app shows the same words once. Tested in `core/session/src/tx/hook_tests.rs` (the hook's place among the disk calls; failures at the journal, the staging, the barrier, a swap's read-back, the rollback and the lock accept nothing; never told of a refused Tx, a save or a recovery; killed in the hook) and `crates/server/src/graph/preview_tests.rs` (heard before durable; each previewed write made durable by its own one barrier, after the preview and before its renames, with nothing accepted while it runs; a refused write, a rename conflict and an interrupted commit; undo, two writes at once, a code save behind one, a drag, read-only, a replaced player, an export, a lane too big for its scheduler, a panic, a slow disk, a stopped transport, an agent's commit taken back; and `a_failed_build_then_a_lane_edit_rebuilds` for what plays lagging). Measured by `m2-gates --server tx-data` (G11; release, 512-frame buffers, 200 piano-roll writes from 1:00 on p16, each a journaled `Clips` Tx), on an M1 Pro (MacBookPro18,1, not the base M1), in seven runs (two when it was built, three when it was checked, two once its messages were fixed; at load averages 2 to 10):
  - From the request to the first block that plays it: p50 4.8 to 5.8 ms, p95 8.7 to 9.8 ms on an idle disk; p50 4.6 to 6.0 ms, p95 8.5 to 10.7 ms while another writer syncs 4 MB chunks; p50 4.9 to 5.6 ms, p95 8.2 to 10.7 ms with a 5,000-file `assets/`; every write a preview swapped into the renderer that plays, none taken back. Of that, the session's part before the preview (plan, check, pre-check) is p50 1.1 to 2.1 ms, p95 1.3 to 3.5 ms, and the wait for the next callback (one device buffer at most) most of the rest. Step 6 measured p95 28.6 ms idle and 35.7 ms busy, and about 77 ms with the 5,000 files; the same day as these runs, the build with the fix's part A and no preview measured p95 16.2 ms idle and 23.9 ms busy.
  - Until the commit is durable and accepted: p50 8.2 to 9.9 ms, p95 8.8 to 14.5 ms idle; p50 14.6 to 17.0 ms, p95 18.9 to 24.7 ms busy.
  - The barrier alone: p50 4.7 to 4.9 ms, p95 4.9 to 6.4 ms idle; p50 7.7 to 9.5 ms, p95 9.2 to 13.8 ms busy. A G11 run with `fcntl` and the renames interposed (no dtruss) counted an `F_FULLFSYNC` on each of its 809 journals, every one before that commit's first rename into the project.
  - Writes sent back to back wait for the one before to be durable (the step 6 design's C20; WRITE-22a's lane leases are the answer for drags). A held arrow key's nudges, one every 16 to 30 ms and each written as the piano roll writes it once the one before replied, from each nudge to the block that plays it: p50 4.9 to 6.6 ms, p95 8.7 to 13.1 ms idle; p50 4.8 to 6.2 ms, p95 8.6 to 13.2 ms busy.
  - A write the disk refuses is taken back (G11, with `.music2/tx/` read-only, and `a_durable_failure_swaps_the_accepted_data_back`).

## Render

### Offline

**RENDER-1.** Offline renders (Export Audio, `m2 render`, `m2 bounce`) MUST be exact. Engine time equals transport time, both start at sample 0, and every instance starts from init. Rendering from sample `s` is rendering from 0 and dropping what comes before `s`.
- In the app, an offline render of a song with hosted plugins pauses live playback and reuses the live instances through `PluginHost`: each one that holds its node's committed blob and the parameters its code sets. One that holds anything else (a value its code no longer sets, [HOME-5a](#homes-of-values); a blob the plan that plays never loaded), one that failed and one waiting for a restart aren't reused: their nodes play new instances from the committed blob. The engine is held first: it fades out over 5 ms and processes nothing, which it publishes before any host call. Each reused instance is deactivated, loaded with the committed blob (skipped when it holds it, [HOME-6](#homes-of-values)), set to offline mode and activated, and is reset on the render thread before its first `process`. Afterwards each is deactivated, set to realtime and activated, and is left holding the committed blob, with its code-owned parameters sent again at the next block ([HOME-4](#homes-of-values)). The engine resumes where it held, fading in over 5 ms, and each reused instance gets a note-on again for every note the song still holds there, as the export ended them. Once plugin windows ship, an export first commits any pending state autosave ([HOME-6](#homes-of-values)). The cost: playback pauses while such an export runs, and the UI says so, and a note held across it starts again at the resume, so its attack plays twice. A pure song's export runs beside playback. The CLI has no live engine and creates its own instances. Every render that isn't live runs its plugins in offline mode, and the live engine's run in realtime mode.
- *Why:* bounces must reproduce, and caches need a key. A second set of instances would double the memory of sample-based instruments and can hit per-instance licence limits. CLAP's `reset` needs an active instance. A reused instance holds the committed blob, and the export sends the parameters its code sets at its first call, so the file is what new instances make; loading a saved state back into the instance that produced it is what [HOME-6](#homes-of-values) forbids. One that holds a value no file records (a parameter its code released keeps its value, [HOME-5a](#homes-of-values)) would bake that value into the file, and loading the blob into it would change what plays live, so a new instance plays its node: the export then depends on the files alone, not on the edits that led to them. A plugin may render differently offline, so `m2 render` and an export run the same mode.
- *Today:* matches for timing (the render specification at the top of `core/runtime/src/lib.rs`, `Renderer::seek`). Since step 7 an export borrows the live instances as an activation would keep them (`PlanInfo::lend` in `core/runtime/src/plan.rs`), in a renderer that resets each at its first call (`Renderer::lending`). On the export's thread (`Lent::take` in `crates/server/src/export.rs`) it holds the engine (`Msg::Hold`) and waits up to 2 s for the engine to say it has taken that hold (`Player::held`, published after the callback returns), then takes each instance offline. Then one `process` call, before the render, ends every note playback left sounding, a choke and a NoteOff for every key: CLAP's `reset` doesn't end them in every plugin (Surge XT keeps its voices, which rang on through the export), and the export doesn't know their ids (`an_export_ends_the_notes_playback_left_sounding`). The same call lets a plugin apply a state just loaded: Surge XT applies one at its next call, ending its voices and setting its parameters, which would take the export's first notes and the code's values with it (`an_export_that_loads_a_state_lets_the_plugin_apply_it_first`). A guard gives every instance back and resumes the engine on every path: done, failed, stopped, a panic, quitting. It tells the session from the actor's own job, so a job that fails after making the export still frees the session (`an_export_whose_job_fails_still_frees_the_session`). Meanwhile the session's settles prepare nothing for the engine (`Open.exporting`), and the one after the export plays what waited. `PlanInfo::lend` borrows only an instance whose plan says it holds the export's committed blob, and none whose code released a parameter (`PluginInstance::released`, set as the plan is prepared, cleared by a load that lands) or that failed; the actor skips one waiting for a restart (`an_export_after_a_released_parameter_is_what_m2_render_makes`, `an_export_never_changes_what_a_live_instance_holds`, `an_instance_waiting_for_a_restart_isnt_borrowed`). An instance whose host calls fail is given back at once and plays its node anew in the export, which carries `plugin.not-borrowed`; one that won't come back active is marked failed before the resume, so its node plays silence, and the settle after replaces it from its committed blob (`a_plugin_that_doesnt_come_back_after_an_export_is_replaced_as_playback_goes_on`). New instances of a render that isn't live (`Renderer::new`, `Renderer::lending`, `PluginInstance::another`) are set to offline mode before they are activated; the live engine's stay in realtime mode, CLAP's default (`renders_that_arent_live_run_their_plugins_offline`). When playback doesn't pause within 2 s (a stalled device), the export touches no live instance and renders beside playback, saying so. The engine view and `/api/graph/status` say `paused: "exporting"` while held, and the web's top bar says "Paused for export" under the song's name. The web says an export's problems in plain words after its done toast. Tested by `an_export_borrows_and_gives_back_the_live_instances` (G7e's probe test, with its negative control), `an_instance_that_cant_be_borrowed_plays_anew_in_the_export`, `an_export_whose_playback_cant_pause_renders_beside_it`, `a_second_export_waits_for_its_own_hold`, `settles_during_an_export_wait_then_apply_once` and `lane_previews_play_during_an_export` (`crates/server/src/graph/tests.rs`), and G7e's server gate (`m2-gates --server export`). At the resume, each plugin node whose instance the export took offline (which ended its notes) starts again the notes its lane still holds, at the first resumed block and with their own ids, and forgets the ones the lane let go meanwhile, also when the export failed before it rendered a block (`Renderer::resumed` in `core/runtime/src/lib.rs`, `a_note_held_across_an_export_plays_again_at_the_resume` in `core/runtime/src/tests/live/keep.rs`, `a_note_held_across_an_export_that_fails_at_once_plays_again` in `crates/server/src/graph/tests.rs`).

**RENDER-2.** Given the same project files, asset bytes, package contents, sample rate and runtime, a pure offline render MUST give the same bits. Package contents are the content hashes of every package file the build and the runtime read; each render's and bounce's provenance records them, and the package versions. The output MUST NOT depend on thread count or scheduling: every sum (buses, `poly` voices, overlay mixes) runs in plan order in the consuming partition. Host code that makes audio for a render, and song code in QuickJS, compute every transcendental function with the `libm` crate, never the OS's math library ([PLAT-4](#platforms)). Song code reads no clock and no randomness, and makes no code from text while it runs (`eval`, the `Function` constructors), which would skip the build's lowering of `**`.
- *Why:* determinism is what makes caching, tests and reproducible bounces possible. A version requirement such as `std = "0.1"` admits many builds, so only hashes identify what ran. A sum in completion order would make renders differ from run to run.
- *Today:* matches for pure songs, on one thread. Since step 4 each revision records the hash of every package file its build read, and a bounce's provenance records each package's version and the hash of every package file the build and the runtime read (`apps/m2/src/main.rs`). `m2 render` and Export Audio write no provenance yet. Since the platform step host math on the render path is `libm` (`core/runtime/tests/host_math.rs` bans host math in `core/runtime/src` and `core/play/src`), and so are QuickJS's `Math` and `**`, so `examples/resample` renders the same bits on macOS and Linux. The sandbox removes `Date` and makes `Math.random` throw, saying why; since the platform step it also removes `performance`, and `WeakRef` and `FinalizationRegistry` (when garbage is collected differs between OSes), and `eval` and the `Function` constructors throw (`PRELUDE` in `core/script/src/lib.rs`, `song_code_cannot_make_code_from_text`). A `**=` whose target wears TypeScript's types (`x! **= y`) is lowered too. Song code can't have an `enum` (refused at its place, `an_enum_is_refused_at_its_place`). Each build runs on a thread of its own, with a 32 MB stack and numbers read as C reads them whatever the app's locale (`JSON.parse` once read "0.5" as 0 in a German Linux app; `core/script/tests/locale.rs`). So no real song reaches QuickJS's stack limit (16 MB of C stack, about 15,000 calls, which each compiler spends differently; `deep_recursion_builds_alike_on_every_os`). A song that recurses that deep, or reaches the 256 MB memory limit (counted as each OS's `malloc` counts), or catches those errors, may build differently on another OS.

**RENDER-3.** Export and bounce MUST use the offline renderer, never the live engine or a range render. Only agent listening ([RENDER-4](#range-render)) may use a range render. Renders read committed files only: no previews, no overlays.
- *Why:* what is exported must not depend on what someone was listening to, and a bounce must be exact to reproduce.
- *Today:* matches. Export renders the accepted revision offline (`Graph::export` in `crates/server/src/graph.rs`): with instances of its own, or, for a song whose plugins play, in a renderer that borrows the live instances while playback is held ([RENDER-1](#offline)); never through the live engine. A commit's preview ([PLANE-5](#planes-of-change)) reaches only the live engine; an export waits for the commit and renders the accepted revision (`an_export_after_a_taken_back_write_renders_the_accepted_data`).

### Range render

**RENDER-4.** A range render takes `(range, preroll)` and is asked for explicitly (an agent's listen, `m2 render --preroll`). The engine starts from init at engine time 0 with the transport at `max(0, range.start − preroll)`. It renders the preroll, then returns `range`. It uses live jump semantics (no note chasing). It is built in step 3a.
- *Why:* an agent must be able to "listen from bar 64" without minutes of replay.
- *Today:* not built. `m2 render --from` replays from 0 (`core/session/src/render.rs:104-106`), which stays the exact way to render a section.

**RENDER-5.** A pure range render MUST be deterministic given the project files, `range` and `preroll`; an impure one reports `reproducible: false`, as bounce does. Its result MUST say whether it is exact: it is exact only when `range.start − preroll ≤ 0`, and approximate in its tails otherwise. An approximate result MUST NOT be written to `assets/` or placed on a lane.
- *Why:* agents need to know when they hear the export and when they hear an approximation, and an approximation must never become part of the song.
- *Today:* not built.

### Live engine and its two clocks

Live playback may differ from export after a seek, a loop wrap or an edit (owner decision 1).

**RENDER-6.** Live playback MUST be a persistent engine with two clocks:
- The **engine clock** is monotonic. It drives the 128-sample block grid, feedback rings, voice age and kernel and plugin time such as CLAP `steady_time`.
- The **transport clock** is the song position. It may jump at any frame. It drives lanes, `time.beats`, `time.seconds`, note scheduling and the transport plugins see.
- *Why:* with one clock, every seek or loop wrap would reset every reverb, delay and plugin.
- *Today:* matches since step 3a (the module doc of `core/runtime/src/lib.rs`). The engine clock (`Engine.clock` in `core/runtime/src/engine.rs`) is each block's `engine` frame: it fixes the block grid, feedback rings read and write at the engine clock modulo a block, a voice's note ends at the engine sample of its Off, and a plugin's `steady_time` is the engine clock at its call. The transport (`Transport` in `core/runtime/src/transport.rs`) is an integer sample position; each block is one or two runs of it, which drive lanes, notes, `time` and what plugins are told ([HOST-6](#pluginhost)). Offline both start at 0 and stay equal. An activation hands both clocks to the new plan ([RENDER-25](#plans-data-and-arrangement-swaps)). Tested by `a_jump_never_resets_a_kernel` and `stopped_lanes_and_time_hold_while_kernels_run` (`core/runtime/src/tests/live.rs`) and `plugins_are_told_the_transport` (`steady_time` against the engine clock). std's chorus, phaser and tremolo run their LFOs on engine time, so after a stop they play from another phase than the export; the owner chose to change that at the `sounds` merge, with its std version bump (2026-10-15).

**RENDER-6a.** The engine MUST keep processing while the device is open, playing or not. Stop is a transport event: every sounding note gets an Off, the transport freezes, control lanes hold their value at the stop position, and `time.beats` stops. Kernels and plugins keep running on that input, so tails decay. Audition and live input work while stopped. The engine MAY idle only once every kernel reports `!active` and the output has been silent for 8 blocks; any message wakes it. Except while held for an export with hosted plugins ([RENDER-1](#offline)): the engine then processes nothing, and resumes where it held.
- *Why:* an engine that pauses on stop freezes delay and reverb tails mid-echo and brings them back as a ghost at the next play, from a different position.
- *Today:* matches since step 3a. Stopped, the engine keeps processing: the transport, control lanes and `time` hold at the stop position while kernels run on (`stopped_lanes_and_time_hold_while_kernels_run` in `core/runtime/src/tests/live.rs`), and tails decay (`tails_decay_after_stop` in `core/play/tests/live.rs`, G7). It idles only when stopped, after 8 silent blocks, when nothing can sound (`Renderer::can_idle`, `the_engine_idles_only_when_nothing_can_sound`), and any message wakes it. Since step 3b, a renderer that hosts plugins may idle too, once every top-level plugin's last `process` returned sleep, or "continue if not quiet" with a quiet output (`Renderer::can_idle`); a plugin's `request_process` wakes the idle engine at the next block line (`Renderer::woken`). Surge XT and Airwindows never sleep, so `examples/with-plugins` never idles (measured by the gates' G7). Since step 7 a hold (`Msg::Hold`, `core/runtime/src/engine.rs`) fades the output out over 5 ms, then renders nothing: the engine clock and the transport stand still and its kernels and plugins aren't called; a resume fades back in where it held, a tape pause (`a_hold_freezes_and_resumes_without_a_step`, `core/play/tests/live.rs`). While held, an activation and a panic wait for the resume, a lane swap applies, transport commands apply to the frozen transport, and cell writes wait in their slots.

**RENDER-7.** `time.beats` and `time.seconds` MUST be transport time, never engine time.
- *Why:* songs describe music in song time.
- *Today:* matches: each frame's beat and second come from the block's transport runs through the tempo map (`Renderer::block` in `core/runtime/src/lib.rs`), never from the engine clock; stopped, they hold (`stopped_lanes_and_time_hold_while_kernels_run`).

**RENDER-8.** Live playback MUST NOT replay from sample 0, for any reason.
- *Why:* replay costs 20.5–24.9 s per seek, note edit, effect add or undo at 1:00 into a 16-track song, and 84.7 s at 50 tracks (measured 2026-10-12). Playback also jumps back by the rebuild time.
- *Today:* matches: live playback never replays. A seek, a loop wrap and a stop are transport events ([RENDER-9](#seek-and-loop)). An edit or an undo reaches the engine as a cell write, a lane swap, or an activation that keeps every instance that continues ([RENDER-25](#plans-data-and-arrangement-swaps)). A project loaded into a new player, a rate change and a refused activation's recovery start a new engine from init at the playhead, by moving its transport there, not by playing up to it (`Open::load` and `Way::Replace` in `crates/server/src/graph/actor.rs`, `Player::replace` in `core/play/src/lib.rs`). Only offline renders replay: `Renderer::seek` (`m2 render --from`).

### Seek and loop

**RENDER-9.** A seek or a loop wrap MUST be a transport event, never a DSP reset. At the jump frame:
1. every sounding note gets a note-off, and its voice goes into release;
2. note cursors are re-sought by binary search;
3. plugins get a transport event at the jump frame, with the new position, the playing and loop flags, and the meter from the arrangement;
4. kernels, feedback rings and plugin instances keep their state, so tails ring through;
5. each audio lane crossfades over 5 ms from its old position to its new one.

Nothing else is declicked at a jump: synth and plugin output ends through note-offs and releases, and control lanes step to their new value, as in other DAWs. This deliberately narrows the plan's 5 ms declick of the whole output, which would also dull every loop's downbeat.
- *Why:* a 4-bar loop must keep its reverb tails for as long as it runs.
- *Today:* matches since step 3a. A transport command lands at the next block line (`Transport::apply`), and a block is split into runs where it jumps (`Runs`, `Jump` in `core/runtime/src/transport.rs`). At a seek, a stop or a wrap, each notes lane's scheduler sends an Off for every note it holds, at the jump's frame, and finds its place in the new position's notes by binary search (`NoteScheduler::run` in `core/runtime/src/sched.rs`; `a_jump_ends_notes_and_never_chases`). A plugin is called once per run, and each call is told its own run's position, playing flag, loop, tempo, meter and bar ([HOST-6](#pluginhost)). Nothing is reset: a delay's echoes ring through a seek as if nothing happened (`a_jump_never_resets_a_kernel` in `core/runtime/src/tests/live.rs`), and a 4-bar loop at 127 bpm keeps its tails for 10 minutes (`a_loop_keeps_its_tails_for_10_minutes` in `core/play/tests/live.rs`, G2). Each audio lane crossfades over 5 ms from its old position to its new one at a seek or a wrap, fades out on stop, and fades in on play from inside a clip (`core/runtime/src/audio.rs`; `an_audio_lane_crossfades_at_a_wrap`, and G6's `audio_lanes_never_click`). While held for an export, a seek moves the frozen transport (`a_seek_while_held_is_where_playback_is`). Offline, `Renderer::seek` still resets and replays from 0, as [RENDER-1](#offline) defines a render from a point.

**RENDER-9a.** The transport MUST be an integer sample position; beats are derived from it through the tempo map. A loop wrap computes the loop end's frame from its absolute beat, `round(samples_at(beat))`, at every wrap, and never by adding up loop lengths. A wrap falls at that frame, mid-block if need be.
- *Why:* at 127 bpm a 4-bar loop is 362,834.6 samples at 48 kHz; rounding and accumulating each wrap drifts notes and audio lanes off the grid within the 10-minute loop gate.
- *Today:* matches since step 3a. The transport's position is a `u64` sample count (`Transport` in `core/runtime/src/transport.rs`), and beats come from it through the tempo map. A loop's start and end frames come from their beats by the notes' own formula (`frame_of`), when the loop is set and again whenever the tempo map or the rate changes (`Transport::retime`), never by adding up laps; a wrap falls at the end frame, mid-block when it must, so a block is at most two runs. A loop shorter than two blocks, or than an audio lane's 5 ms crossfade, is refused (`Transport::loop_refused`). Tested by `wraps_fall_on_their_frame` and `a_loop_at_127_bpm_runs_10_minutes_without_drift` (`transport.rs`), and recorded on p16 by `p16_loops_ten_minutes_without_drift` (`core/play/tests/live.rs`).

**RENDER-10.** Engine state MUST be reset only: on panic; on stop, when the user chose "reset on stop"; at the start of an offline or range render; and per voice, when the `poly` allocator retriggers a voice ([RENDER-16](#voices)). An instance that a plan activation doesn't match starts from init ([RENDER-25](#plans-data-and-arrangement-swaps)); that is a new instance, not a reset of kept state. A plan activation never resets a kept instance, except one whose output went non-finite or that trapped ([RENDER-25](#plans-data-and-arrangement-swaps)).
- *Why:* any other reset cuts tails the user is listening to.
- *Today:* since step 7 an activation moves every instance it keeps into the new plan untouched (`Renderer::take_over` in `core/runtime/src/plan.rs`); a box marked as gone non-finite or trapped is reset as it moves, and counted in the plan's `Stats`, not in `Renderer::resets`, which counts a panic's resets and an offline replay's. A reused voice is reset (`PolyNode::process` in `core/runtime/src/lib.rs`).

**RENDER-11.** Notes already sounding at a seek target are not chased (deferred). After a jump, only notes that start at or after the new position sound.
- *Why:* chasing needs preroll per instrument; it waits for its trigger.
- *Today:* matches since step 3a: after a jump only the notes that start at or after the new position sound (`NoteScheduler::run`; `a_jump_ends_notes_and_never_chases` in `core/runtime/src/sched.rs`). Offline, a render from a point replays from 0 (`Renderer::seek`), so its held notes sound as in the export.

### Events

**RENDER-12.** Notes MUST reach instruments as per-block, sample-stamped event buffers. A notes lane node is a scheduler that fills its buffer each block from the transport. `poly` and plugins consume buffers. `Events<Note>` is the view of a buffer that holds only note events.
- *Why:* live input, audition, code-generated patterns and event-producing kernels all plug into the same buffers.
- *Today:* matches since step 3a. Each notes lane is a scheduler (`NoteScheduler` in `core/runtime/src/sched.rs`) that fills its lane's event buffer (`Events` in `core/runtime/src/event.rs`, sized when the plan is prepared) from the block's transport runs, before the graph runs. `poly` and plugin nodes read that buffer; a plugin node turns it into the host's CLAP-shaped list without allocating (`plugin_events` in `core/runtime/src/lib.rs`). There is no separate `Events<Note>` type: the one buffer holds `Event`s, and only notes are made so far.

**RENDER-13.** Voices MUST gate on note-on and note-off events, not on comparing the transport with note times.
- *Why:* a jump must end notes through note-offs, and live notes have no end time when they start.
- *Today:* matches since step 3a: a voice's gate opens at its note's On and closes at the engine sample of its Off (`VoiceNote` and `PolyNode::process` in `core/runtime/src/lib.rs`), so a jump ends a voice's note only through the Off its scheduler sends ([RENDER-9](#seek-and-loop)). Plugins get the same Ons and Offs, as CLAP note events.

**RENDER-14.** The event shape is a tagged enum, reserved whole now and built only as far as notes:

```rust
enum Event {
    On  { frame: u32, id: u32, pitch: f32, velocity: f32, from_pitch: Option<f32> },  // from_pitch: glide and legato
    Off { frame: u32, id: u32, velocity: f32 },                                         // release velocity
    NoteExpression { frame: u32, id: u32, kind: Expression, value: f32 },             // MPE, per-note pitch, pressure, timbre (later)
    Param { frame: u32, id: u32, value: f32 },                                         // sample-accurate parameter events (later)
    Midi  { frame: u32, bytes: [u8; 3] },                                              // CC, pitch bend, sustain from MIDI input (later)
}
```

Live input and audition merge into a lane's buffer (later). The IR reserves a `const-events` op for events generated by code ([ABI-4](#kernel-abi-reservations)).
- *Why:* one shape for every source of notes, and room for expression, controllers and parameter events without bumping the kernel ABI or the IR event type again.
- *Today:* matches since step 3a: `Event` in `core/runtime/src/event.rs` is this enum, whole, with `Expression` naming `Pitch`, `Pressure` and `Timbre`. Only `On` and `Off` are made, with `from_pitch` always `None`. At one frame Offs come before Ons, so a key can be struck again where it was let go. Live input and audition aren't built.

**RENDER-15.** Code that builds the graph MUST NOT read timeline data.
- *Why:* data edits must never need a compile.
- *Today:* matches. Lanes are graph inputs (`core/script/sdk/core.ts:408-449`).

### Voices

**RENDER-16.** The `poly` op MUST carry an allocator:

```ts
poly(notes, voice, { voices: 16, mode: "poly", retrigger: true, steal: "oldest", glide: 0 })
//                               "poly" | "mono" | "legato"   "oldest" | "quietest" | "none"   seconds
```

The default MUST reproduce today's output bit for bit. A `poly` is kept or replaced whole; a kept pool's voices keep their slots, which are their RuntimeIds. The op shape is fixed now; mono, legato and glide are built later ([Deferred](#deferred-with-triggers)).
- *Why:* a fixed reset-on-reuse policy rules out mono, legato and 808 slides. Voices are most of a song's instances; moving each pool as one box keeps an activation's work in proportion to the top-level graph.
- *Today:* one policy: the first free slot, else the oldest (`PolyNode::process` in `core/runtime/src/lib.rs`). A reused voice is reset. The only option is `voices` (`core/script/sdk/core.ts`). Since step 7 a poly's voices are one box (`VoicePool`), which an activation moves whole into a poly of the same shape: its voices, channels and voice graph, without its cells' values, origins and names (a plain number written inside the voice is part of it); any other poly is new.

### Latency

**RENDER-17.** The engine MUST own latency, per instance. It measures it after state is loaded, and again when a plugin reports a change.
- Offline measures the total `L` once, after init and state load, and keeps it for the whole render. A change reported mid-render raises the Warning `latency.changed` and takes effect only in the next render.
- Live applies a new latency only at a plan activation, through `deactivate` and `activate` (which CLAP's `request_restart` needs anyway), with the crossfade of [RENDER-25a](#plans-data-and-arrangement-swaps).
- *Why:* a plugin's latency often depends on its loaded preset, and a delay plan that changes mid-render would make the export depend on when the change arrived.
- *Today:* in part. A new instance's latency is measured when it is activated, after `create` loaded its state (`PluginHost::activate` in `core/plugins/src/host.rs`), and isn't used: a new instance whose saved state adds latency plays uncompensated, and nothing says so. The check refuses a plugin whose latency at its default state isn't 0 ([RENDER-21](#latency); `describe_plugin` in `core/runtime/src/packages.rs`). Since step 7 a state load into a kept instance measures it again, and a nonzero one plays uncompensated with the notice `plugin.latency-uncompensated` ([RENDER-26b](#plans-data-and-arrangement-swaps)). A change a plugin reports (CLAP's `latency.changed`) is measured again on the plugin main thread, and the session only logs it. Nothing is compensated, live or offline ([RENDER-18](#latency)), and the Warning `latency.changed` isn't built.

**RENDER-18.** The planner MUST insert compensating delays so every path into a node arrives aligned. Lanes, notes and time read downstream of a latent node MUST be delivered delayed by the same amount.
- *Why:* a lookahead limiter or pitch corrector must not move a track off the beat.
- *Today:* not built.

**RENDER-19.** The song's output is late by its total latency `L`. Offline renders MUST drop the first `L` samples and render `L` more at the end, so sample 0 of an export is song time 0 and the song's last `L` samples are kept. Live playback reports the transport position minus `L`.
- *Why:* exports and the playhead must line up with the timeline, and an export must not lose its ending.
- *Today:* not built (no latency is allowed).

**RENDER-20.** Latency inside a feedback loop MUST raise the `latency.in-feedback` Warning. The loop plays with the extra delay.
- *Why:* a loop's delay can't be compensated.
- *Today:* not built.

**RENDER-21.** Until compensation ships, the check-time refusal of nonzero latency stays. It is removed in the same change that ships compensation.
- *Why:* before then, latent plugins would play misaligned.
- *Today:* refused at check time (`core/ir/src/check.rs:497-499`).

### Cells

**RENDER-22.** An editable constant MUST be a cell. A cell is written into kernel input memory (or a constant buffer) once when its plan activates, and again only on `SetCell`. Previews, monitoring overlays and value commits target cells. None of them rebuilds.
- *Why:* thousands of knobs must cost nothing per block, and a knob turn must be heard in the next block.
- *Today:* matches for previews since step 5 (`core/runtime/src/cells.rs`). Every const with an origin that a renderer plays is a cell. Its value is written into its node's buffer, and from there into each kernel input it feeds once, at the kernel's first call, and again only when the cell's slot brings a new value, so a steady cell costs nothing per block. A value written while playing is heard at the renderer's next block line with no rebuild. A lease's update is a cell write to the cells of its value in the renderer that plays (`Player::set_cells`), and a renderer built while a lease lives gets its value in those cells before it is sent (`Renderer::set_cells`, by the renderer's `CellMap`). A committed value reaches the engine as a cell write when only constant values changed (`value_writes` in `crates/server/src/graph/actor.rs`), an inherited control's first edit included; with other changes, in an activation that keeps every instance and applies each changed continued cell as a `SetCell` from its old value would be ([RENDER-22a](#cells), `Cells::carry` in `core/runtime/src/cells.rs`). Monitoring overlays come in step 8.

**RENDER-22a.** A `SetCell` on a control declared `smooth` ([PKG-14](#component-descriptors)) MUST ramp linearly from the old value to the new over one block: the host writes the ramp into the cell's buffer, then the constant. A `SetCell` on an overlay gain cell ([MON-1](#monitoring-overlays-and-mute-in-song)) MUST glide: the overlay op moves its gain toward the new value by `1 / round(0.010 × rate)` a frame, so a full mute or unmute takes 10 ms, and the host writes no ramp. Other cells step, and a kernel that needs smoothing does its own. Offline renders never receive `SetCell`, so they are unaffected. A glide in flight when an activation lands ends there as a step of what is left of it: the new plan starts at the value it was given.
- *Why:* a mute toggle or a gain jump written as a step clicks. A one-block ramp is too short for a mute on a low note by the triangle bound: at 50 Hz a sine moves 0.0065 a sample, gate 8 allows 0.0131, and a 128-frame ramp adds up to 0.0078; a 10 ms glide adds 0.0021.
- *Today:* matches since step 5 for declared controls: a cell whose origin names a control declared smooth (`Origin.control.smooth`) ramps from its old value to the new over the next block, ending exactly on the new value, and the others step (`Cells::apply` in `core/runtime/src/cells.rs`). A ramp is applied at a block line like a step, so it is the same live and offline. Since 8b.4 an overlay cell's value goes to its overlay node's target, and the node glides there (`Exec::Overlay`, `core/runtime/src/overlay.rs`; `an_overlay_glides_over_ten_milliseconds`). Gate 8's click test passes at 440 Hz and 50 Hz with device buffers of 128, 37 and 512 frames (`core/play/tests/mute.rs`). The two terms of the bound above peak at different phases, so a one-block ramp would pass it too, and only a step fails it: the glide's length is pinned by the runtime test.

**RENDER-23.** Cells are addressed by a `CellId` from the active plan, mapped from a ControlId, or from a module key for mute and solo. A CellId MUST NOT outlive its plan.
- *Why:* build-local numbers never outlive their build ([ID-12](#derived-identity)).
- *Today:* since step 5 a cell is its index in its renderer's cell table (`CellId`), written through that renderer's slots (`CellTarget`, `Renderer::cell_slots`), so it can't reach another renderer's cells. Since 8b.4 each overlay site has a cell, numbered after every value cell, so value cells keep their ids; `PlanInfo.overlays` maps each site to its track's key, the module that reads it, and its cell. A plan not yet sent takes its overlays' values with `Renderer::set_overlays`, which writes no slot. A lease aims at a `CellTarget`: the server maps its control's origin to `CellId`s by the `CellMap` of the renderer that plays, and maps again when that renderer takes a value edit or another renderer replaces it (`PlaysView::target_of` in `crates/server/src/graph/lease.rs`). Cells stay per plan. Leases are re-aimed at each activation, under the control plane's lock in the step that sends it; a continued cell whose value changed is applied at activation as a `SetCell` would be ([RENDER-22a](#cells)), after the old plan's ramps end (`Cells::end_ramps`), so a smooth control ramps through a mixed edit and a ramp in flight never moves into the new plan with its voices.

**RENDER-24.** Kernels MUST treat input memory as read-only ([ABI-1](#kernel-abi-reservations)).
- *Why:* a cell is written once; a kernel that wrote its input would corrupt it.
- *Today:* checked since step 5, as [ABI-1](#kernel-abi-reservations) says.

### Plans, data and arrangement swaps

**RENDER-25.** Plans MUST be prepared off the audio thread and activated at a block boundary. Activation keeps every instance whose RuntimeId and shape match. The shape is the kernel id, the content hash of the kernel's wasm module, the channel counts, the state ABI and the settings; for a hosted plugin, its plugin id and plugin version. The others start from init. Replaced objects are retired off the audio thread. Instances are matched when the plan is prepared, off the audio thread, against the plan the engine will be playing; `Activate` carries the moves and names that plan. The audio thread checks that plan's id and each move's shape before moving anything, and refuses the whole activation on a mismatch. A kernel's module hash is the SHA-256 of its package's wasm module, which also fixes its state ABI; in ABI v0 its only setting is its channel count. A `poly`'s shape is its voices, channels and voice-graph structure without cell values. An instance whose output was non-finite in its last block, or that trapped, is reset as it moves.
- Preparing a plan includes creating, loading and activating every new plugin instance on the plugin main thread. The old plan keeps playing until all of them are ready, and the UI shows "loading <plugin>" meanwhile. The code plane's 200 ms budget doesn't count plugin loads.
- *Why:* an edit must not cut the tails of what it didn't touch. A rebuilt package that keeps a kernel's id but changes its memory layout must never inherit old memory, and a sample-based instrument can take seconds to load.
- *Today:* matches since step 7. The server prepares each plan against the plan it sent last (`Renderer::prepare` with `Basis::Keep`, `core/runtime/src/lib.rs`): the session names which nodes continue (`m2_session::tx::continues`: keyed plugins by module and state path, every other node by its name in step 6's delta, its op and its occurrence counts, [ID-13](#derived-identity), [ID-14](#derived-identity)), and the runtime keeps a continuing node only when its `Shape` matches (`core/runtime/src/keep.rs`), so every instance of an untouched file, and of each call of an edited file whose `(` no change touched, a wrapped instrument included, is kept. New plugin instances are created and activated on the plugin main thread while the old plan plays; a prepare that fails changes nothing that plays. At the block line the audio thread verifies every move (the plan's id, each box filled and of its stored shape hash, each new slot empty), then makes them all by `mem::swap` with no allocation (`Renderer::take_over` in `core/runtime/src/plan.rs`): boxes (a kernel instance with its own `Store`, a voice pool, a plugin instance, a feedback ring), lanes, the transport, the engine clock and note ids, cell values. A refused activation is retired unplayed, counted (`Engine::refused_activations`) and stamped (`Applied::refused`), and the server's next settle replaces the engine at the same beat (`Way::Replace`). Every box nothing moved leaves with the old renderer, which is retired off the audio thread once the stash has room for three retirements, checked before the activation applies; one that can't be retired is forgotten and counted (`Engine::leaked`), never dropped there. Live, each top-level box whose output held a non-finite sample in its last block, or that trapped, is marked (`Graph::poisoned`), and reset as it moves. Tested by `core/runtime/src/tests/live/keep.rs` (G7d's `a_rebuilt_kernel_module_starts_from_init` among them), G7b (`m2-gates tails`) and G7c (`core/play/tests/bit_identity.rs`).

**RENDER-25a.** An activation crossfades, linearly over 5 ms, every input of a kept node whose source changed, and the song output when its source changed. A new node's audio input from a node that plays on fades in from silence over 5 ms first, and the activation's crossfades wait for it, so that window is 10 ms. A replaced or removed node runs on in the new plan for that window as a ghost, its notes ended, reading what it read, then is retired. Nothing else fades; equal signals stay bit-identical. An edit that would make that window's graph cyclic (a reorder of kept nodes) replaces the nodes on the cycle.
- *Why:* switching from old to new output in one sample clicks on every structural edit made while playing; fading at module outputs would need kept instances processed twice, and fading only changed edges leaves an untouched track's tail bit for bit. A delay or reverb inserted on a sounding track would take a step into its memory and play it back as a click (its first echo, G6); its input fades in before anything crossfades to it, so a wrap that changes no sample (`vca(x, 1)`) still changes no bit.
- *Today:* matches since step 7 (`core/runtime/src/keep.rs`, `Exec::Fade` and `fade.rs`): a fade node reads the old source (a continuing node, a ghost or a constant; silence for a fade-in) and the new one and gives `xfade` of them, after `wait` frames for a crossfade that waits for fade-ins (`Plan.wait`), then copies the new side exactly, taking its version, so a steady cell behind it costs nothing per block. Ghosts are the old sources of the changed edges that don't continue, and what they read that doesn't; a ghost reads no notes, and a control or audio lane only ghosts read moves in for the window as a ghost lane. The window's order is Kahn's over the new nodes, ghosts and fades (feedback inputs aren't counted); a cycle found there demotes the continuing nodes on it and the plan is wired again. At the window's end (`Renderer::end_fade`) the ghosts, ghost lanes and replaced renders leave in `Retired::Nodes`, and the order without ghosts plays on. `LiveFade` in `core/play` crossfades a whole engine only where one replaces another (an open, a rate change, a refused activation's recovery).

**RENDER-26.** `SwapLane` MUST replace one lane's data in the running nodes at a block boundary, without touching any kernel. Step 3a uses it when the old and new `Flat` graphs are equal. From step 6 the Tx delta decides.
- *Why:* a note edit must be audible within 20 ms with no tails cut.
- *Today:* matches since step 6: the server takes the delta from the revision the playing renderer was built from (or took since) to the accepted one, and swaps the lanes it lists when nothing structural, no state, asset or arrangement changed, and each notes lane fits its scheduler (`reach` in `crates/server/src/graph/actor.rs`); a change that never reached the engine (a build that failed) is never skipped by a later lane edit (`a_failed_build_then_a_lane_edit_rebuilds`). When a change's renderer doesn't build, the version before it plays on, and a notice says so in plain words, once for each revision, though the catch-up tries again every 300 ms (`a_change_that_cant_get_ready_to_play_says_so_once`); running out of memory is named as such there, and in a failed open or export, with wasmtime's words as the detail (`running_out_of_memory_is_said_plainly`). Since the G11 fix, a data Tx's swaps are sent as a preview between its pre-check and its journal ([PLANE-5](#planes-of-change)), and what plays is its candidate until the settle after the commit adopts the accepted revision, sending nothing, or swaps the accepted data back by the same delta from what plays (`reach_to`). Audio lanes and assets take [RENDER-27](#plans-data-and-arrangement-swaps)'s path, as does notes data that outgrows its scheduler (an activation grows it). Since 8b.4 a module muted or unmuted in the song is no structure there: what plays takes it as overlay cell writes ([MON-5](#monitoring-overlays-and-mute-in-song)).

**RENDER-26a.** Each notes-lane scheduler MUST own the set of notes it has turned on and not yet off: each with its runtime note id and its `(clip, pitch, start beat)`, where an anonymous clip is named by its start. Then:
- On `SwapLane` it compares that set with the new data. A sounding note that is gone, or whose new end is at or before the transport, gets an Off at the swap frame. One whose end moved is rescheduled. A new note that started before the transport is not chased.
- Each notes lane's scheduler persists across plans with its sounding notes, keyed by `LaneAddr`, and note ids are unique across the engine. An activation that replaces a note consumer, or keeps one whose notes input now reads another lane, first ends every note sounding into it.
- A stop, a seek or a wrap on an activation's block line is handled as on any block. An arrangement switch reconciles every scheduler with its new data, which recomputes each pending Off from its beat.
- A stop, a seek or a loop wrap sends an Off for every sounding note ([RENDER-9](#seek-and-loop), [RENDER-6a](#live-engine-and-its-two-clocks)).
- *Why:* a scheduler that takes its Offs only from the new data leaves a deleted or shortened note hanging forever.
- *Today:* matches since step 7. An activation moves each lane's scheduler into the new plan by `LaneAddr`, with new data when the data or the tempo map changed (a reconcile at its first block, as a swap), or into a bigger scheduler that takes over its sounding notes when the new data needs more room (`NoteScheduler::take_state`, `core/runtime/src/sched.rs`). A ghost and a kept poly or plugin whose notes lane changed get their notes ended at entry (`Entry.release`: a voice's Off at the activation's first frame, a plugin's NoteOff at its next call); a new consumer of a kept scheduler gets Offs for notes it never had, which it ignores. A plan's first block (`Jump::Enter`) ends nothing, but a start, stop, seek or wrap on that block line is that jump (`Transport::advance`). Note ids are the engine's (`Renderer::next_note`, taken over at entry), so no id repeats into a kept instance. Adoption and the step 3b design's clarification C7 are withdrawn: nothing adopts.

**RENDER-26b.** A change to a plugin's state from outside the instance (an undo of a state write, `m2 plugin-state`, a git checkout, an agent writing the blob) MUST reach the running instance as a state load on the plugin main thread into the instance that plays, made while the plan for that revision is prepared. It is skipped when the blob's hash equals the state the instance holds ([HOME-6](#homes-of-values)). The parameters code owns are sent again at the instance's next block ([HOME-4](#homes-of-values)). A removed blob makes the instance new. Until compensation ships, a latency that becomes nonzero raises `plugin.latency-uncompensated` and plays uncompensated. A changed asset takes the path of [RENDER-27](#plans-data-and-arrangement-swaps): the affected clip renders are prepared off the audio thread and switched at one block boundary.
- *Why:* a state or asset change must have a route to the engine that doesn't rebuild the song. CLAP's state load is a main-thread call, allowed while the plugin is active; there is nothing to re-plan while [RENDER-21](#latency) refuses latency.
- *Today:* matches since step 7. A state-only revision is an activation of the same code (`Continues::identity`). Its prepare, as its last step once every new instance exists, compares each kept plugin's committed blob with the one its instance was last given (`PluginAt.blob` in `core/runtime/src/plan.rs`), node by node, so a key paired across paths loads the right blob though no file changed, and loads one that differs (`Renderer::prepare` in `core/runtime/src/lib.rs`). The node's next two calls, in the old plan or the new, send every parameter code owns again (`PluginInstance::take_reloaded`): Surge XT applies a loaded state at its next `process` call, over the values that call brings, and ends every voice there, so only the call after keeps them. A note that starts in that first call doesn't sound in such a plugin. A blob taken away makes the instance new (`keep::wire`): CLAP has no "load defaults". A load that fails never fails the prepare, as the loads before it have landed: that plugin plays on as it left itself, and a notice names it by its plugin and its track and says why. The plan records the refused blob as given, so no later plan tries it again or says so again until another blob is committed; the host then holds nothing known, so the blob it held before loads if it is written back (`a_refused_state_is_said_once_by_the_plugins_name` in `crates/server/src/graph/tests.rs`). The latency warning is a notice, not an entry in the problems list. Tested by `a_changed_state_loads_into_the_same_instance`, `a_state_load_resends_code_owned_parameters` (with the probe applying a loaded state as Surge XT does, too) and `a_state_that_fails_to_load_never_fails_the_prepare` (`core/runtime/src/tests/live/keep.rs`), `a_state_change_loads_into_the_running_instance` and `swapping_two_plugin_keys_moves_the_instances` (`crates/server/src/graph/tests.rs`), and with-plugins' changed state gate (`m2-gates plugins`: one load into the same Surge, the new patch's volume, the code's filter type kept).

**RENDER-27.** An arrangement change (tempo, meter) MUST prepare the new timing tables and every affected clip render off the audio thread, then switch them together at one block boundary. The old arrangement plays until then. The switch keeps the transport's beat position, and its sample position is recomputed under the new tempo map. An audio-lane change that needs a render (a new clip, moved warp markers, a warped clip moved across a tempo change) takes the same path, with the old clip playing until its render is ready. The switch is an `Activate` of the same structure, which keeps every instance. Each audio lane with new renders crossfades from its old renders linearly over 5 ms, exactly where the two are equal. A tempo change re-renders every clip, warped or not, since the tempo map places and sizes each one.
- *Why:* re-rendering warped clips can't fit in 20 ms, and half-switched timing would desync audio. One path for code and data keeps a tempo change from cutting a tail or leaving audio off the grid.
- *Today:* matches since step 7. The server prepares an arrangement, audio, asset or state change as an activation of the same code (`Continues::identity`), with every lane's renders built through the session's cache while the old plan plays (`LanePlan::new` in `core/runtime/src/plan.rs`): an audio lane whose renders changed swaps them in its persistent player (`AudioPlayer::swap` in `core/runtime/src/audio.rs`), which plays both for one window, the old ones at their own position, and crossfades them sample by sample with `xfade`, so a clip the edit didn't change is the same bits on both sides; the transport keeps its beat (`Transport::retime`). Tested by `a_tempo_change_keeps_every_kernel_and_the_beat`, `an_audio_swap_of_unchanged_clips_changes_no_bit` and `a_clip_gain_edit_stays_between_its_two_levels` (`core/runtime/src/tests/live/keep.rs`).

**RENDER-27a.** A tempo drag is a lease ([WRITE-22](#gesture-leases)). Each update reaches notes, control lanes, time and plugins at the next block. Warped audio switches when its render is ready, so it may lag behind during the drag; this is the one place timing may be half-switched, and only in a preview. Release commits one Tx that writes `data/arrangement.json`.
- *Why:* re-rendering every warped clip before each drag step is heard would make the tempo bar unusable.

**RENDER-28.** The audio thread MUST NOT allocate, lock, do I/O or wait on a compile.
- Cell values travel in per-cell slots: the latest value wins, and the audio thread reads the slots marked changed at each block. They never use the queue.
- Structural messages (`Activate`, `SwapLane`, `Transport`, `Panic`, `Hold`) go over a bounded queue and are never dropped. Activations are never coalesced: each applies after the previous one's fade window, against the plan it names. A sender waits up to 500 ms, then reports the player stalled; the next change opens a new player. `Hold` pauses the engine for an export that borrows the live plugin instances, and resumes it ([RENDER-1](#offline)).
- A player is stalled when a sender waited 500 ms, when its device hasn't called back for a second, or when the device reports it is gone (its stream invalidated, or the device unavailable). Nothing else the device reports stalls it. An xrun (a dropout) is counted, and play goes on. A change of output device makes a new player, which opens at the new device's rate and period. The device's error callback only adds to a count per kind: on some OSes it runs on the audio thread.
- Debug builds and CI run the audio thread under an allocation and lock trap (in the style of `assert_no_alloc`).
- *Why:* any of these can glitch the output, and a dropped `Activate` would leave the engine on an old plan for good.
- *Today:* the queue is bounded (`core/play/src/lib.rs`); a sender retries for 500 ms, then reports `Stalled` and the message is not sent, never silently. Structural messages apply in order, one at a time (`Engine::try_apply`): an activation waits at the head for the window before it to end and for stash room, and none is coalesced. A resume (`Hold(false)`) applies as soon as it is read, unless its hold still waits: an activation sent while held waits for it, and before, the resume queued behind that activation and held the engine for good (`a_resume_never_waits_behind_an_activation_waiting_for_it` in `core/play/tests/live.rs`). The audio thread allocates, frees and locks nothing: buffers, event lists and an activation's moves are sized when a plan is prepared, and every move is a swap. Since step 3b the host's side of a plugin call allocates and locks nothing either: event lists are sized when a node is built, the host's audio side (`core/plugins/src/audio.rs`) is kept free of locks, allocation and thread-locals by a grep test, and `core/play/tests/no_alloc.rs` runs two probe plugins under the trap through an activation that moves both (a real plugin's own allocations are its own), and, from step 7, an activation that keeps kernels, a voice pool, a ring and an audio player, grows a lane, swaps the audio lane's renders, plays out a ghost reading a ghost lane, panics in its window, ends it, and refuses a stale activation. Since step 5 cell values travel in per-cell slots and never use the queue (`CellSlots` in `core/runtime/src/cells.rs`, `Player::set_cells` in `core/play`): the latest value wins, writers are serialised by a lock only control threads take, and the audio thread reads the slots marked changed at each block line with atomics alone. `core/play/tests/no_alloc.rs` writes cells from another thread while the callback runs under the trap. Since step 7's finish the player sorts cpal's errors by kind, the same on every OS (`DeviceEvent::of` in `core/play/src/lib.rs`): the error callback only adds to an atomic count per kind, and the player's thread logs the counts once a second while they grow. Only an invalidated stream or an unavailable device stalls the player (`Player::stalled`). A change of output device (`Player::changed`) makes the server let the player go, as after a stall: the action that meets it fails and says why, and the next settle loads the project into a new player where it was, stopped (`Inner::device` in `crates/server/src/graph.rs`). When the watcher's catch-up lets a playing player go first, a notice says "Playback stopped:", why, and "Press Play to go on." (`playback_the_device_stopped_is_said`). The engine view and `/api/graph/status` carry the counts since the player started (`xruns`, `device_errors`). Tested with injected errors, no device: `the_devices_errors_are_sorted_by_kind`, `an_xrun_is_counted_and_play_goes_on`, `a_device_change_asks_for_a_new_player_and_plays_on_meanwhile` and `a_device_that_is_gone_stalls_the_player` (`core/play/src/tests.rs`), `the_device_error_callback_never_allocates` (`no_alloc.rs`), `an_xrun_is_counted_and_the_player_plays_on` and `a_device_change_or_loss_makes_a_new_player_where_it_was` (`crates/server/src/graph/tests.rs`). Before, any error marked the player stalled, so one xrun (a CoreAudio overload) let it go at the next action and cut every tail, and the callback printed on ALSA's audio thread. Since step 7 debug builds of the app install a counting allocator (`m2_play::alloc` in `core/play/src/alloc.rs`): the callback marks its thread (in debug builds only, so a release callback touches no thread-local, whose first touch can allocate on macOS), every allocation and free there is counted and never panics, and a thread of its own logs the count once a second while it grows (`an_allocation_in_the_callback_is_counted`). `no_alloc.rs` also holds and resumes the engine, with a panic deferred to the resume.

**RENDER-29.** Previews and transport MUST NOT take the session lock. See [gesture leases](#gesture-leases).
- *Why:* a knob preview waited 20 s behind a rebuild (measured).
- *Today:* matches since step 3b. The session runs as an actor (`crates/server/src/graph/actor.rs`), and a knob drag's updates are lease updates that take only the control plane's short lock, which the actor never holds over a compile or a build, and go straight to the engine ([WRITE-22](#gesture-leases)). Seek, the loop and status never touched the session since step 3a. Measured: during a 1.5 s compile, updates are heard as fast as the others (`m2-gates --server previews`, G8), and `crates/server/src/graph/tests.rs` (`previews_never_wait_for_a_compile`) checks that the engine hears them before the compile ends.

### Audio lanes

**RENDER-30.** Audio lanes are streamed. Decoded and warped renders are cached in the OS's cache folder ([FMT-16](#assets-and-hashes)), keyed by content hash and memory-mapped. A prefetch thread reads around the transport and ahead of seeks. The audio thread reads only ring buffers. This is built on its trigger; until then, clips rendered into memory are allowed.
- *Why:* a stem-heavy song must not need all its audio in RAM. Caches are rebuildable and can be gigabytes, so they stay out of the project folder, where git and sync services would carry them; keyed by content, they are safely shared between projects.
- *Today:* every clip is rendered into memory when a renderer is built (`core/runtime/src/audio.rs:1-5`, 235).

### Sample rate

**RENDER-31.** The live engine MUST run at the `sample_rate` in [the manifest](#manifest-and-versions). It opens the device at that rate, or resamples at the device boundary. It is built in step 4, with `sample_rate`.
- *Why:* live and export must run the same DSP at the same rate.
- *Today:* matches since step 4: the player runs the engine at `sample_rate` and converts to the device's rate at the boundary when they differ (`core/play/src/resample.rs`), and Export Audio, `m2 render` and `m2 bounce` render at `sample_rate`.

**RENDER-31a.** Offline renders MUST run at `sample_rate`. An export at another rate goes through one fixed, deterministic sample-rate converter after the render. 16-bit output uses TPDF dither from a fixed seed; 24-bit output rounds; 32-bit float is written as rendered. RENDER-2's bits are the render at `sample_rate`, before conversion and dither, and the export's provenance records the rate, the converter and the dither.
- *Why:* re-running the DSP and plugins at another rate would sound different, and unseeded dither would make exports differ from run to run.
- *Today:* offline renders run at `sample_rate` (step 4); `m2 render` and `m2 bounce` refuse `--sr` rather than run the DSP at another rate. Exporting at another rate (the converter) isn't built. Exports are 24-bit, rounded, with no dither and no provenance (`core/session/src/render.rs`); bounces are 32-bit float.

|---|---|---|---|
| **Saved** | track keys, lane keys, plugin keys, `key()` frames | yes, written in code | readable, validated, never normalised |

### Keys

**ID-1.** Every key MUST match `^[a-z0-9]([a-z0-9-]{0,30}[a-z0-9])?$`: 1 to 32 characters, lowercase letters, digits and inner hyphens. A leading digit is allowed (`808`).
- *Why:* keys are readable in file names, and lowercase-only keys can't suffer a case-only rename on a case-insensitive disk.
- *Today:* matches since step 4: one key rule, in `m2_ir::key` for the build and the checker and in `m2_song::Key` for paths and data.

**ID-2.** Keys MUST be validated, never normalised. An invalid key is the compile error `key.invalid`, which suggests a valid spelling.
- A writer (the app's add track, an agent) MAY propose a key from a label once, when it creates the thing: fold to ASCII, lowercase, turn every run of other characters into one `-`, trim to 32 characters and the key rule, and fall back to `track-2`, `track-3`… when the result is empty or taken. It shows the key, writes it into the code, and never derives it again. One shared helper in `crates/editor` does this.
- *Why:* normalising is what lets two names share files. A key proposed once and then written down is just a default the person can see and change.
- *Today:* matches: keys are checked, never normalised, and `key.invalid` suggests a spelling (`m2_ir::key::suggest`). Since step 6 the one helper is `keys::propose` in `crates/editor`; automating a knob uses it once, for the new lane's key, which it shows and writes into the code.

**ID-3.** `song` is reserved for the root module.
- *Today:* matches (`core/script/sdk/core.ts:464`).

**ID-4.** These have keys: tracks (modules), lanes (unique within their module), plugins that have saved state, and `key()` frames.

```ts
track("lead-vox", { name: "Lead Vox" }, ({ lane }) => ...)   // label "Lead Vox"
track("kick", ({ lane }) => ...)                             // label "kick"
lane.notes("hook", { name: "Hook" })                         // .control(key, unit, fallback, opts?), .mask(key, opts?), .audio(key, channels?, opts?)
plugin("clap:org.surge-synth-team.surge-xt", { key: "lead", notes })   // replaces `state:`
key("chain-l", () => vocalChain(x))                          // a frame: composes state paths, and pins what it holds
```

**ID-5.** A key used twice where it must be unique MUST be the compile error `key.duplicate`: a track key anywhere in the project, a `key()` frame key within its parent frame, a plugin key within its frame. The message names both evaluations: the call site, plus the stack of the second, since a `track()` in a helper or a loop has one site that runs twice.
- *Why:* the error must say exactly what to rename.
- *Today:* matches since step 4: `key.duplicate` names the call site and the stack of both evaluations (`core/script/sdk/core.ts`).

**ID-6.** A lane declared again with the same kind and settings is the same lane. A redeclaration with another kind or other settings is the compile error `lane.conflict`. A lane key declared from two different `key()` frame chains is the compile error `lane.shared`, unless the declarations say `shared: true`. Lanes are addressed by module key and lane key only, never by frame.
- *Why:* helpers may read the same lane twice, but `key("chain-l", …)` and `key("chain-r", …)` must not share one automation lane by accident, the way [ID-8](#keys) forbids for state. Keeping lanes out of frames keeps them flat on the timeline and lets code be wrapped in `key()` without moving data.
- *Today:* matches since step 4 (`declareLane` in `core/script/sdk/core.ts`).

**ID-7.** `key(k, fn)` opens a frame. Keys MUST be unique within their parent frame ([ID-5](#keys)). A frame composes plugin state paths. A `key()` frame is named by its key in every identity below it; nothing positional above the innermost one is part of an InstancePath. It is also reserved as a later place for monitoring overlays inside a module ([MON-1](#monitoring-overlays-and-mute-in-song)).
- *Today:* matches: `key()` frames compose plugin state paths since step 4, and since step 7 a node's delta name keeps, above its innermost `key:` segment, only the other `key:` segments (`Side::chain` in `core/session/src/tx/delta.rs`), so moving the code around a `key()` keeps what it holds (`names_ignore_everything_above_a_key_frame`).

**ID-8.** A plugin needs a key only once it has saved state, and then it MUST have one. Until then it has an in-memory RuntimeId. The state path is the module key, then the `key()` frames, then the plugin key: `data/vox/chain-l/tune.state`. Two stateful instances that resolve to one path are the error `plugin.state-collision`, whose message says "wrap one in `key()`". The same error applies when a plugin without its own key takes its frame's key while that frame directly holds another stateful plugin (plugins in frames nested inside it don't count). `key` is a reserved plugin port name.
- The app's first state save is a Tx built in `crates/editor`. It inserts `key: "<k>"` at the plugin call when that call is in a project file and runs once in its frame. Otherwise it goes outward along the instance's frame chain to the first call that is in a project file and runs once in its frame, and wraps that call in `key("<k>", …)`; the plugin then takes the innermost frame's key as its state file name, which is allowed only while that frame holds exactly one stateful plugin. If no call on the chain is in a project file (a plugin built inside a package), the save is refused before anything is written, with a message saying where to add `key()`.
- *Why:* most plugins never need saved state, and two plugins must never share it by accident. A key inserted at a call shared by two instances would collide at once.
- *Today:* matches since step 4, except that every plugin with a state path counts as stateful, since the build never reads data: a plugin's `key`, or else its innermost `key()` frame's, files its state at `data/<module>/<frames>/<key>.state` (`Op::state_path` in `core/ir`), and two that resolve to one path are `plugin.state-collision`. `key` is consumed by the SDK and is never a port. The app's first state save, a Tx, comes in step 6.

**ID-9.** Windows device names (`aux`, `con`, `nul`, `prn`, `com1`–`com9`, `lpt1`–`lpt9`) are legal keys. `DataPath` MUST add a trailing `-` to every path segment made from such a key (`data/aux-/`, `data/kick/con-.json`). Nothing else may map keys to paths.
- *Why:* producer names stay legal, Windows stays possible, and the mapping is reversible because no key ends in `-`.
- *Today:* matches since step 4 (`DataPath` in `core/song/src/path.rs`).

### Labels

**ID-10.** A label MUST be display text only: never an address, a file name or an import target. It defaults to the key. Changing a label is an `Identical` Tx: labels are ignored when graphs are compared. Code MUST NOT be able to observe a label: the track function's context exposes `key`, never the label, and no handle returns it. The label lives only in the IR (`Module.label`, a lane's `name`).
- *Why:* renaming a track must never silence it or hand its data to another track, and a song that branched on its label would change its sound when renamed.
- *Today:* matches: the context exposes `key`, labels live only in the IR, and no handle returns one (tested in `core/script/src/tests.rs`). A label change changes no data file, graph or sound (`core/session/src/gate_tests.rs`). Since step 6 renaming a label in the app, `m2 label` or `POST /api/graph/label` is an `Identical` Tx on the `track()` call's name (`crates/editor/src/rename.rs`).

**ID-11.** The IR module is `Module { key, label, muted }` (`muted` is "mute in song", [MON-5](#monitoring-overlays-and-mute-in-song)). The key is used by the import op, flat node names, lane addresses, `m2 bounce --track` and `--place`, bounce provenance, `TimelineTrack.module` and UI selection. `slug()` is deleted.
- *Today:* since 8b.4 `Module.muted` is in the IR, written only when true, so an IR without it keeps its JSON and its hash (`a_song_without_muted_has_the_same_ir_hash`). The checker refuses it on `song` and on a module that isn't a track, and lists the muted tracks in `Flat.muted` (`core/ir/src/check.rs`).

### Derived identity

**ID-12.** A number local to one build (site ids, call ordinals, node numbers, `Origin`, control ids such as `song.ts#2/0.hats.pan`) MUST NOT be used with any revision but the one it came from. To use a target in a later revision, resolve it again from its source position.
- *Why:* one inserted call renumbers every later site in the project.
- *Today:* `Origin.site` counts across the whole project in load order (`core/script/src/lib.rs:271`). At `92a19a3`, `revert()` carried the byte range forward but passed the stale origin to `apply()` (`core/session/src/edit.rs:752-761`): after one soundless call was added to `song.ts`, undoing a knob in `tracks/bass.ts` failed on every retry while `can_undo` said true. Step 1 fixed this: a value's undo records no origin. It finds the control written at the carried bytes in the accepted revision and uses that control's current origin, and both undo and `can_undo` refuse when those bytes no longer set a control in the same units (`core/session/src/edit.rs`: `carried`, `control_at`, `revertible`).

**ID-13.** A site's identity across two revisions is its file and the point of its argument list's `(`, in the reference coordinates of the comparison ([WRITE-8](#expectations-and-the-delta)). Nothing numbers sites. A Tx is judged in its own edits' coordinates; every other comparison, the engine's included, uses `Edits::between`: a line diff whose hunks a token-level Myers diff refines. A `key()` frame is named by its key. An unmatched or ambiguous site is new, and its state resets.
- *Why:* the arena keeps state by identity, and guessing would hand one oscillator's state to another. A `(` survives a wrap, a changed callee and an edited argument, wherever a diff puts the closing brackets. A session counter would be history: two processes would number one revision's sites differently and hash one Tx's delta differently, and the engine only ever compares what plays with what is accepted.
- *Today:* matches since step 7: `Site.open` is each call's `(` (`core/script/src/sites.rs`), delta names spell a call by it (`Side::called` in `core/session/src/tx/delta.rs`), and `Edits::between` refines each run of changed lines by a Myers diff over identifiers and numbers, strings and single punctuation characters; when more than 500 lines differ (a whole file re-indented, say), the token diff takes every line between the common first and last lines. Each run of inserted or deleted tokens is slid to start at a word. When it repeats a call's `name(`, the old `(` goes to the call whose arguments match the old call's: the inner one for a wrap in the same callee, the outer one for a call of the same callee put inside it. When neither matches, both calls are new (`slide` and `pick` in `core/session/src/text.rs`). So an effect wrapped around an instrument keeps the instrument, through the app's Tx or a file save (G7b's wrapped instrument); Add Effect and Remove Effect keep the user's own effect beside another of the same kind (`crates/editor/src/effect_tests.rs`); and two literals edited on adjacent lines are two value changes. What still resets: a call cut and pasted, one whose own tokens a reformat reorders, and every call in a stretch of changed lines where more than 500 tokens differ. What can still keep the wrong call: a call of the same callee written on lines of its own, above another (`const pre = delay(hook, …)` above `delay(hook, …)`) or around it with the old call moved to the next line. There the line diff decides before the tokens are compared, and the new call takes the old one's instance. Sites are still numbered per build (ID-12), for the tables of one build only.

**ID-14.** For repeated unkeyed sites in one parent instance (loops, `map`), state is kept by index only while the occurrence count and the surrounding structure are unchanged. If the count changes, every occurrence resets. `key()` or a keyed iteration helper keeps state through reorders.
Applied when the engine matches instances; a `key()` frame has no occurrence; a plugin with a state path is matched by that path ([ID-15](#derived-identity)).
- *Why:* an index alone would hand state to a neighbour.
- *Today:* matches since step 7: each delta name carries how many times each positional segment's call ran in its parent and how many nodes share it but for its occurrence (`Facts.counts`), and `continues` keeps a pair only while those are the same (`core/session/src/tx/continues.rs`). std's mixer runs its strips in a `map`, so adding a channel resets every strip; that is inaudible today (`std:gain`'s smoother starts at its target, and pan holds no state), and keying each strip by its channel is a std follow-up. A plain function (not a `component()`) makes no frame, so when one parent calls it more than once, its calls are matched by call order: swapping two such calls swaps their state. Make it a `component()`, or wrap each call in `key()`, to keep them apart.

**ID-15.** Derived ids are built as follows:
- SDK frames record `{ site, componentId, occurrence, key? }`. The frame chain continues inside component bodies, packages included.
- InstancePath = module key / frame chain.
- ControlId = InstancePath + the slot the callee declares ([PKG-3](#component-descriptors)).
- RuntimeId: a plugin with a state path ([ID-8](#keys-and-names)) has its module key and that path as its RuntimeId, whatever its place. Any other node's RuntimeId is InstancePath / the site of its `kernel()`, `plugin()`, `poly()` or `feedback()` call, matched by the same rules as [ID-13](#derived-identity) and [ID-14](#derived-identity); segments are `key:<k>` or `<ComponentId>@<file>:<point>#<occurrence>`. A body that calls `kernel("std:svf")` twice has two sites, so two RuntimeIds. A voice's RuntimeId is its slot in its kept pool.
- CellId = a cell's index in the active plan.
- *Why:* the arena key must be defined by the same matching as every other site, with no separate notion of a kernel's "role".
- *Today:* since step 5 the IR's `Module.frames` lists every component call and `key()` frame a module's build evaluated, as `{ site, component, occurrence, key, parent }` (and, for a component call with options, which argument held them, `options`), and a node names its innermost frame (`Node.frame`); a declared control's const names its frame and slot in its origin (`Origin.control`), and its delta name, InstancePath / `@<slot>`, is its ControlId (`core/session/src/tx/delta.rs`). A call site is taken only by the call it was set for: the SDK compares the arguments it received with what the call's instrumentation recorded, so a function native code calls (`xs.map(lowpass)`) takes no site and makes no frame (`core/script/src/sites.rs`, `takeSite` in `core/script/sdk/core.ts`). Sites are still numbered per build (ID-12). The session groups the view and recognises effects by frame chains (`Module::chain` in `core/ir`, `calls_of` in `crates/editor/src/effect.rs`), and `Node.within` (the component sites of the chain) is deleted.

**ID-16.** A project file MUST NOT contain a derived id. The saved roots are module keys, lane keys, plugin keys and `key()` frames. An optional editor index may live in `.music2/`; it is rebuildable at any time and used only for layout continuity. Seeds and musical defaults MUST NOT be derived from derived ids. Every id-bearing field in the format v1 schemas is a key, a clip id or a CLAP parameter id, and strict parsing ([FMT-8](#strictness)) admits no other field.
- *Why:* derived ids change with every refactor; saved ones must not. A schema that has no field for a derived id is checkable; "no file contains one" by looking at the files is not.
- *Today:* matches: nothing derived is saved, and a test refuses a derived id in every schema (`core/song/src/data/tests.rs`).

### Renames

**ID-17.** Renames work like this:
- **A label rename** in the UI is an `Identical` Tx.
- **A key rename** in the app is one Tx that edits the code and renames `data/<key>/`. It may also write `layout.json` ([WRITE-3](#the-two-write-primitives)).
- **A key rename by hand** leaves the data unclaimed: `data.unclaimed`, with a Relink fix ([DIAG-6](#fixes)): for a track key, of the whole `data/<key>/` folder; for a lane key, of one lane file.
- *Today:* matches for label renames and renames by hand: a label rename is an `Identical` Tx (step 6); a track key renamed in code leaves its folder `data.unclaimed`, offered whole as one `Rename` of the folder on its directory hash ("Move all to …"), and a lane key its lane file, in the app and in every CLI command that opens the project ([DIAG-4](#delivery), [DIAG-6](#fixes)). The app's key rename and Restore aren't built.

**ID-18.** Mixer channel keys are dictionary slots where the user's key is identity on purpose. The app writes the track key as the channel key of a new channel, but finds a track's channel by following the graph edge from the track's export into the mixer, never by comparing keys. A key rename Tx renames a channel key only when it equals the old track key, and says so in its label.
- *Why:* a channel whose key differs from its track's (written by hand, or after a rename) must still be found.

## Project format v1

### Layout

```
music2.toml                  [project] name, entry, format = 1, sample_rate = 48000
                             [dependencies] "@m2/core" = "1", std = "0.1"
song.ts  tracks/*.ts  lib/   code
data/arrangement.json        {"tempo": [{"beat", "bpm"}], "meter": [{"beat", "beats", "unit"}]}   a beat is a quarter note
data/<module>/<lane>.json    one lane's clips
data/song/<lane>.json        lanes of the root module
data/<module>/<frames>/<plugin-key>.state   a CLAP state blob, with its .state.json sidecar
assets/<path>                audio files, never overwritten; <path>.json is a bounce's provenance
layout.json                  shared presentation, keyed by track key; never part of a revision
.music2/                     local and gitignored: overlays, loop range, zoom, selection, lock, tx journal, editor index
<cache folder>/music2/       outside the project, in the OS's cache folder (FMT-16): decoded and warped renders, the hash cache
```

**FMT-1.** Projects MUST use this layout. This app has no reader for format 0, today's layout: the 5 fixtures are converted once by script ([FMT-21](#conversion)). Formats after 1 follow [FMT-3a](#manifest-and-versions).
- *Why:* every project's bytes on disk are cheapest to fix before projects exist in the wild.
- *Today:* matches since step 4: the 5 fixtures are converted, and a project without `format` is `format.missing`.

### Manifest and versions

```toml
[project]
name = "Starter beat"   # required: the project's label
entry = "song.ts"       # optional, default "song.ts"
format = 1              # required: the version of the file layout
sample_rate = 48000     # required: the rate the engine runs and exports at

[dependencies]
"@m2/core" = "1"        # required: the SDK version the code is written against
std = "0.1"             # every package the code imports from must be listed
```

**FMT-2.** `format` versions only the file layout. `[dependencies] "@m2/core"` versions only the code API. A data addition bumps only `format`; an SDK break bumps only `@m2/core`. Each reader checks only its own field. A requirement follows Cargo's caret rule: `"0.1"` means at least 0.1.0 and below 0.2.0, and `"1"` means at least 1.0.0 and below 2.0.0. A package declares its own version in `m2pkg.toml`.
- *Why:* the two change for different reasons and at different times, and a requirement needs one meaning.
- *Today:* matches since step 4 (`core/song/src/manifest.rs`).

**FMT-3.** Opening MUST read `[project] format` first, on its own and leniently, before anything else in the manifest. A missing `format` is `format.missing` (a format-0 project: convert it with the script), an older one `format.older`, a newer one `format.newer`. In each case the project does not open, and the message says what to do. Then the build checks every `[dependencies]` entry: an unsatisfied `@m2/core` is `sdk.unsatisfied`, any other unsatisfied package `pkg.unsatisfied`, each naming the required and the installed version. An import from a package not listed is the compile error `pkg.undeclared`.
- The app bundles one std. A std release that changes the bits of any existing render MUST bump its version (the minor version while it is 0.x), and CI checks this against the fixtures' recorded renders. So an old project gets `pkg.unsatisfied`, never a silent change in its sound, and that release is the trigger for the lockfile and for shipping several std versions ([Deferred](#deferred-with-triggers)).
- *Why:* an old app must never rewrite a newer project, a strict parse must not hide a newer format behind `manifest.invalid`, and code must never run against an SDK or a std it wasn't written for.
- *Today:* matches since step 4: `format` is read first, `sdk.unsatisfied` and `pkg.unsatisfied` are checked at compile, and `pkg.undeclared` by the build. A test records each pure fixture's render under std's version and fails when one changes while the version stays (`core/session/tests/renders.json`).

**FMT-3a.** After format 1, a format or SDK break MUST ship with a migrator outside core (`m2 migrate`). Migrating is explicit, journaled like a Tx, and never applied on open. The app keeps the previous `@m2/core` major for at least one release after a break.
- *Why:* "no backwards compatibility" holds only while the fixtures are the only projects. Once people have songs, a break must not orphan them.

**FMT-4.** After `format`, the manifest MUST be read strictly: unknown keys are the error `manifest.invalid`. It blocks acceptance (the last accepted revision keeps playing, or on open nothing plays), but never `save()`, so the manifest can be fixed.
- *Why:* the lenient reader drops unknown fields when a file is rewritten.
- *Today:* matches since step 4 (`core/song/src/manifest.rs`).

### Paths

```rust
enum DataPath {
    Manifest, Code(PathBuf), Arrangement, Module { module: Key }, Lane { module: Key, lane: Key },
    PluginState { module: Key, path: Vec<Key> }, Asset(AssetName), Presentation, Local, Unknown,
}
impl DataPath { fn path(&self) -> PathBuf; fn parse(p: &Path) -> DataPath; fn class(&self) -> Class }
```

| Path | `DataPath` | Class | Plane |
|---|---|---|---|
| `music2.toml` | `Manifest` | Manifest | code |
| `*.ts` outside `data/`, `assets/`, `.music2/` and `node_modules/` | `Code` | Code | code |
| `data/arrangement.json` | `Arrangement` | Arrangement | arrangement |
| `data/<module>/`, the folder itself | `Module` | Data | data (renamed only by a `Rename` op) |
| `data/<module>/<lane>.json` | `Lane` | Data | data; prepared data for an audio lane |
| `data/<module>/…/<plugin-key>.state` and its `.state.json` | `PluginState` | Data | prepared data |
| `assets/<path>` | `Asset` | Data | prepared data |
| `layout.json` | `Presentation` | Presentation | none |
| `.music2/**`, a commit's staging folder `.music2/tx/<id>/` included | `Local` | Ignored | none |
| anything else, `.js` and `.mjs` files included | `Unknown` | Ignored | none |

**FMT-5.** `core/song` MUST be the only place a project path is spelled or classified, through `DataPath`. The canonical lane writer moves there, beside the reader.
- *Why:* every copy of a path rule drifts.
- *Today:* matches since step 4: paths are spelled only by `DataPath` (`core/song/src/path.rs`), and lane files are written by `m2_song::canonical`.

**FMT-6.** A snapshot MUST read only Manifest, Code, Arrangement and Lane files and `.state.json` sidecars. Assets and state blobs are not part of a snapshot; revisions record their hashes.
- *Why:* only those files define the song, and binary files are too big to snapshot.
- *Today:* matches since step 4: revisions record the hashes of the assets their lanes name and of state blobs (`core/song/src/lib.rs`).

**FMT-6a.** The build MUST read project code only from the snapshot. A project import resolves only against the snapshot's Code paths, byte for byte (the path, then with `.ts`, then `/index.ts`), with no filesystem probe and no case folding. Any other import (a `.js` file, anything under `data/`, `assets/` or `.music2/`, a path outside the project, or a spelling that differs in case) is the compile error `import.outside-code`, naming the file. Package files are read from disk, and each revision records the content hash of every package file its build read ([RENDER-2](#offline)). A package import that leaves its package, or differs in case from the file on disk, is also `import.outside-code`; a package file that simply doesn't exist is `code.build`.
- *Why:* a revision must be a function of its snapshot. A file read from disk would change what compiles without making a revision, and a case-insensitive disk would compile `./Tracks/bass` on a Mac and fail it on Linux CI.
- *Today:* matches since step 4: project code comes only from the snapshot, and every revision records the package files its build read (`core/script/src/lib.rs`).

**FMT-7.** A file under `data/` that `DataPath` can't parse raises the Notice `file.unknown`. Other unknown files are ignored silently.
- *Why:* a typo in a data path should be visible; a README should not.
- *Today:* matches since step 4, except that the notice reaches a running session only with its next revision, since the unknown file alone makes none ([PLANE-3](#planes-of-change)).

### Strictness

**FMT-8.** The manifest, lane files, clips, notes, the arrangement and state sidecars MUST reject unknown fields.
- *Why:* a lenient reader silently drops what it doesn't know when the file is rewritten.
- *Today:* matches since step 4 (`core/song`).

**FMT-8a.** Data files MUST have one canonical form, written by the canonical writer in `core/song`: a fixed key order per schema; numbers in their shortest round-trip form, never `-0`; one clip per line and one note per line; clips sorted by `(start, id)` and notes by `(start, pitch)`. Readers put clips and notes in the same order before use, so the order of an array never changes the sound; overlapping control clips with the same start are decided by id, never by file order. Reading and then writing a canonical file gives the same bytes.
- *Why:* files must diff cleanly, two writers must agree byte for byte, and a sort, a merge or a hand reorder must never change the sound with no value changed.
- *Today:* matches since step 4 (`core/song/src/lane.rs`); a test checks that every fixture's data files are canonical (`core/song/tests/fixtures.rs`). The reader and writer were made about 3 and 6 times faster for G11 (no copies of each clip, a pitch read without an error made per name, the sort's lines made only for ties, one buffer); the old ones are kept as test oracles (`core/song/src/lane/oracle.rs`), and the fast ones give the same data, the same errors and the same bytes on every lane file in the repository and on generated ones (`the_fast_read_is_the_old_read`, `canonical_bytes_are_unchanged`).

**FMT-9.** Only manifest, code and arrangement errors block acceptance. The arrangement is a deliberate addition to the plan's "only code and manifest", because every clip's timing depends on it. A lane file that fails to parse, or doesn't match its declaration, MUST NOT stop anything else, and raises an Error (`lane.invalid` or `lane.unit-mismatch`) that names the file, the field and the fix:
- when the session has accepted data for that lane, the last accepted data keeps playing, and the message says so;
- when it has none (on open, or for a new lane), the lane plays empty.

A file or folder that can't be read at all (permissions, an I/O error) is reported with the code of its class, and the message carries the system's error: `lane.invalid` for a lane file or a folder under `data/` (including one no lane reads), `state.unverified` for a state blob, its sidecar or a folder holding them, `arrangement.invalid` when `data/` itself can't be listed, `code.build` for a code file or a folder that may hold code, and `manifest.invalid` when the project folder can't be read. No separate code is needed: the fix is the same as for a file that doesn't parse.

Export renders the accepted revision, as it does for code.
- *Why:* one bad hand edit must not silence the whole song, and a lane file caught half-written must not drop out of a running session.
- *Today:* matches since step 4 (`Project::data` in `core/song/src/data.rs`, given the last accepted data by the session).

**FMT-10.** Lane files carry no `kind`. Notes and audio clips fail as the wrong shape, and a file with no clips fits any kind. Control lanes record their `unit`; a unit that differs from the declaration raises `lane.unit-mismatch` with Retag and Convert fixes.
- *Why:* the kind is in the code; writing it twice invites disagreement.

### Lane files and clip ids

```json
{"clips": [{"id": "k3f9q2zt", "start": 0, "length": 16,
            "notes": [{"pitch": "A1", "start": 0, "length": 0.5, "velocity": 0.9}]}]}
```

```json
{"unit": "hz", "clips": [{"id": "q7m2c8xa", "start": 32, "length": 8, "points": [[0, 500], [8, 2500]]}]}
```

```json
{"clips": [{"id": "z1b4r9td", "start": 64, "length": 4, "asset": "vox/lead.wav", "hash": "9f2c3a1be07d44c1",
            "offset": 0, "gain_db": -3, "fade_in": 0.01, "fade_out": 0.05, "reverse": false, "pitch": 0, "warp": []}]}
```

Notes, control (masks are control lanes in `unit01`) and audio lanes, in that order. Fields are today's (`core/song/src/lib.rs:217-317`) plus `id`, `unit` and `hash` (the first 16 hex digits of the asset's SHA-256).

**FMT-11.** A clip id is chosen by whoever builds the op that writes the clip, and travels in the Tx; core never mints one during `check` or `commit`. Ids are 8 characters from the lowercase Crockford base32 alphabet (`0-9a-z` without `i`, `l`, `o`, `u`). A builder outside a sandbox MAY draw them at random. A sandboxed package tool, the CLI and a fix derive them: the first 8 Crockford characters of SHA-256(`tx.id` ‖ lane address ‖ n), so `tx.id` is the only random input. Readers MUST accept any id matching `^[0-9a-z]{1,16}$`.
- *Why:* random ids survive merges, other processes and git. A sandbox has no randomness, `check` and `commit` must write the same bytes, and a scripted run given its `tx.id` must be reproducible.
- *Today:* matches since step 4. The app draws ids at random; the CLI and fixes derive them from SHA-256 of the Tx id, a NUL, the lane address `module/lane`, a NUL and `n` in decimal (`ClipId::derive` in `core/song/src/key.rs`).

**FMT-12.** A clip id is unique within its lane, and a clip's address is `(LaneAddr, ClipId)`. Moving a clip to another lane keeps its id. Copying or duplicating a clip always mints a new id, and a writer that finds its id taken in the target lane mints another.
- A clip without an id is anonymous: it can be addressed only within one revision, and raises the Notice `clip.anonymous` with an AssignClipIds fix.
- An id that breaks the rule, including one that isn't a string, is read as anonymous and kept as written, and raises the Notice `clip.invalid-id` with the same fix. "Kept as written" keeps the JSON value; the canonical writer may re-space it (`{"a": 1}` becomes `{"a":1}`).
- A duplicate id raises the Warning `clip.duplicate-id` with a RenumberClips fix, never a parse failure.
- Ids are never assigned on read. Note ids come later.
- *Why:* one hand edit must never make a lane unreadable.

### Arrangement

**FMT-13.** `data/arrangement.json` holds `tempo` (`[{beat, bpm}]`) and `meter` (`[{beat, beats, unit}]`, the time signature `beats`/`unit`). A beat is a quarter note.
- Tempo: the first entry is at beat 0, each is 20–999 bpm, and beats strictly increase.
- Meter: an empty list means 4/4 from beat 0; otherwise the first entry is at beat 0. `beats` is 1 to 64, and `unit` is 1, 2, 4, 8, 16 or 32. A bar lasts `beats × 4 / unit` quarter notes. Each change falls on a bar line of the meter before it, and beats strictly increase.
- Anything else raises `arrangement.invalid`, naming the entry, and blocks acceptance.
- *Why:* time signatures are needed for bars, plugins and the tempo bar, and every reader must count bars the same way. Two entries at one beat would be decided by file order.
- *Today:* matches since step 4 (`core/song/src/arrangement.rs`).

### Assets and hashes

**FMT-14.** An asset MUST never be overwritten: a new version gets a new name, and assets are created with create-only semantics (`O_EXCL`). An asset name is a relative path under `assets/`, with `/` between folders. It is NFC, and has no empty, `.` or `..` segment, no segment that starts with `.`, and no `\` or control character. An import whose name is taken gets a numeric suffix (`kick 2.wav`). An asset is always inside the project: importing copies the file. `m2 bounce --force` is removed.
- *Why:* an overwritten asset can't be undone and silently changes every clip that uses it. Sample-heavy projects need folders, and a reference outside the project breaks when the project moves.
- *Today:* matches for what writes assets today: `m2 bounce` creates its asset create-only and `--force` is gone, an exact render that `m2 render` or Export Audio writes into `assets/` is created, never written over (`Render::write_for` in `crates/editor/src/render.rs`, since step 6), a Tx's `Write` of an asset must have the base `Absent`, and names are checked as `AssetName`s (`core/song/src/path.rs`). Importing isn't built.

**FMT-15.** A clip's asset reference carries a `hash` pin: the first 16 hex digits of the SHA-256 of the file's bytes. The app always writes it.
- A reference without a pin is read, and raises the Notice `asset.unpinned` with a RepinAsset fix.
- A pin that differs from the file raises the Warning `asset.changed` with a RepinAsset fix, and the clip plays the file as it is.
- A reference MUST equal an entry of `assets/` byte for byte, found by listing the folder, never by `open()`. A name that differs only in case is `asset.missing`, with a fix that rewrites the reference to the exact name. A file whose name on disk isn't NFC can't be referenced at all ([FMT-14](#assets)), so a name that differs only in Unicode normalisation is `asset.missing` whose message says to rename the file to its NFC form; a fix that renames the file waits for step 6, when a Tx can rename a path into `assets/`.
- A missing or unreadable asset raises the Error `asset.missing`, and that clip is silent.
- *Why:* an asset changed behind the project's back must be visible, and a case-insensitive disk must not make a clip play on a Mac and go silent elsewhere.
- *Today:* matches since step 4 (`core/song/src/data.rs`).

**FMT-16.** A hash cache keyed by `(path, size, mtime, ctime, inode)`, in the OS's cache folder (`m2_os::dirs::cache`: `~/Library/Caches/music2/` on macOS, `~/.cache/music2/` on Linux), refreshed by the watcher, covers assets and state blobs. An entry whose mtime lies within the volume's timestamp resolution of the moment it was cached is unverified, and is hashed again on next use (git's racy-timestamp rule). Compile MUST NOT decode audio.
- *Why:* every compile decoding every WAV makes data edits slow. On exFAT, with 2-second timestamps, a same-length file rewritten in place would otherwise keep its old hash.
- *Today:* matches since step 4, with the racy window at 2 s on every volume, since a volume's resolution can't be read portably. The CLI and the app keep the cache in `hashes.json` there (`core/song/src/hash.rs`).

### Plugin state and parameters

**FMT-17.** A plugin's state is the CLAP blob in `data/<module>/<frames>/<plugin-key>.state`, with a required sidecar `<plugin-key>.state.json` that holds exactly `{plugin, plugin_version}`: no parameter values and no hash. A missing state file means the plugin's defaults. A blob whose sidecar names another plugin than the code does raises the Error `state.plugin-mismatch`; a blob without a sidecar raises the Error `state.unverified`. Either way the blob isn't loaded, the plugin plays its defaults, and the fixes are Relink (when another key now has that plugin) and DeleteData. A state write always writes both files in one Tx.
- *Why:* state belongs to its module's data, and parameter values belong to code or the blob, never both ([HOME-4](#homes-of-values)). One plugin's state loaded into another crashes many plugins, and a hash beside the blob is a second truth that a merge can split from it.
- *Today:* matches since step 6: `m2 plugin-state` writes the blob and its sidecar as one Tx, undone as one step (`plugin_state` in `crates/editor/src/data.rs`).

**FMT-18.** A plugin parameter is addressed in code as `<name>_<id>`: its display name, lowercased, with other characters turned to `_`, then its CLAP parameter id (`mix_12`). The build binds by the id alone, and the name part is a label: when it differs from the plugin's current display name, that is the Notice `plugin.param-renamed`, never a rebind. A name without an id (`mix`) is the compile error `plugin.param-unaddressed`, which suggests the full address. Editors and Tx builders always write the full form. The IR stores CLAP parameter ids, and the runtime binds by id.
- *Why:* a display name is not identity (P1). A plugin update that renames parameters, swaps two names or adds one with a clashing name must not rewire anything, and code that compiled must keep compiling.
- *Today:* matches since step 4. The IR keeps each address as written; `PackageSet::bind_plugins` binds it by its id before the check, so the runtime binds by id (`core/runtime/src/packages.rs`).

**FMT-18a.** A plugin that isn't installed MUST NOT stop the song. It raises the Error `plugin.missing`, which doesn't block acceptance. Its node is typed from the code as written: stereo audio in and out, and each `<name>_<id>` port a plain control. An instrument (no `in`) outputs silence; an effect passes its `in` through to its `out`. Its code and its state blob are never rewritten. An export made while a plugin is missing carries `plugin.missing`.
- *Why:* a project opened on a collaborator's Mac, in CI or in an agent's sandbox without one plugin must play everything else, as in every DAW.
- *Today:* matches since step 4 (`core/runtime/src/packages.rs`; the node in `core/runtime/src/lib.rs`).

### Presentation and local files

**FMT-19.** `layout.json` holds shared presentation keyed by track key: track order and colour, later canvas positions. It is never part of a revision and never read by the build. Unknown keys in it are ignored.
- *Why:* presentation must never trigger a compile or change the sound.
- *Today:* `layout.json` is classed Presentation and never makes a revision (step 4); nothing reads or writes it yet.

**FMT-20.** `.music2/` is local to one machine. New projects MUST get a `.gitignore` line for it. Caches live outside the project ([RENDER-30](#audio-lanes), [FMT-16](#assets-and-hashes)). A project in a synced folder (iCloud Drive, Dropbox) works with these rules:
- The app marks `.music2/` for the sync services that honour a marker (Dropbox's ignore attribute), and raises the Notice `project.synced` when the project is under a known synced folder.
- The lock file and every journal record the host name. A journal from another host is reported as `tx.foreign`, with no fix ([WRITE-16](#commit-journal-and-recovery)).
- Another machine editing the project is an outside writer ([WRITE-19](#outside-writers)).
- *Why:* overlays, locks, journals and caches are not the song, and a lock or a journal synced from another machine means nothing on this one.
- *Today:* new projects, from the app and `m2 new`, get a `.gitignore` with `.music2/`, and `.music2/` is Local to `DataPath` (step 4). Since step 6 the first writer also puts a `.gitignore` of `*` in `.music2/`, and the lock file and every journal record the host name, with the machine id (`m2_os::host::machine_id`: the hardware UUID on macOS, `/etc/machine-id` on Linux) as what tells another host's journal (`core/session/src/lock.rs`; the step 6 design's C18). The sync marker and `project.synced` are not built. `~/.music2/session.json` is per user, not per project (`apps/music2-desktop/src/main.rs:112-115`).

### Conversion

**FMT-21.** A throwaway script converts the 5 fixtures from format 0 to format 1. Core MUST NOT contain migration code; later migrations live in `m2 migrate` ([FMT-3a](#manifest-and-versions)).
- *Why:* there are no users yet, so there is nothing to migrate but fixtures. Once there are, migrating is an explicit tool, never a side effect of opening.

## Writes

### The two write primitives

**WRITE-1.** Every write to a project file through music2 MUST be a `save()` or a `Tx`, except creating a new asset with create-only semantics ([WRITE-18](#the-project-lock)). A file music2 creates outside a Tx (a new asset, a bounce's provenance, a new song's files) is made durable, its bytes pushed and its folder synced, before anything names it. These bypasses close: `write_whole` becomes private, `PUT /api/graph/file` becomes `save()`, `m2 bounce --place` becomes a data Tx, and `m2 plugin-state` becomes a Tx that writes the state and its sidecar. That Tx may replace existing state as one undoable step, so `m2 plugin-state --force` goes away.
- *Why:* each bypass skips the lock, the journal or the diagnostics.
- *Today:* matches since step 6: the only writer is the commit's staging (`core/session/src/tx/stage.rs`); `PUT /api/graph/file` is `Session::save` (`crates/server/src/files.rs`); `m2 bounce --place` and `m2 plugin-state` commit Tx, and `--force` is gone (`crates/editor/src/data.rs`, `apps/m2/src/main.rs`); an exact render into `assets/` is created, never written over. `the_write_bypasses_are_closed` (`crates/editor/tests/crate_graph.rs`) keeps it so.

**WRITE-2.** `save(file, base_sha, text)` is a draft write: compare-and-swap on `base_sha`, then an atomic write. It is never rejected for errors. The change is then taken in like an outside write ([WRITE-19](#outside-writers)), and recorded for undo only if it compiles. Code editor saves and agents' free-form edits use it.
- *Why:* a half-typed file must be saveable, and agents keep writing files directly (owner decision 5).
- *Today:* matches since step 6: `Session::save` compares and swaps on the bytes' hash, writes through the commit's staging, takes in the settled draft with that one file (never a fresh read of the folder), and records an undo step only when it was accepted as written (`core/session/src/take.rs`). A file that isn't UTF-8 is saved over from the lossy text the code editor shows (`crates/server/src/files.rs`).

**WRITE-3.** Every other write is a `Tx`:

```rust
Tx   { id, base: Map<Path, Base>, label: (before, after), ops: Vec<Op>, expect: Expect, hint: Option<CodeRev> }
Base = Sha | Absent | WithText { sha: Sha, text: String }                    // the base text itself (WRITE-12)

Op   = TextEdit { file, edits: Vec<{ start: Pos, end: Pos, expected, text }> }
     | Write { file, bytes }                                                  // JSON: "text" or "base64"
     | Remove { file }
     | Rename { from, to }                                                    // a file, or a folder data/<module>/
     | Clips { lane: LaneAddr, put: Vec<Clip>, delete: Vec<ClipId> }          // at most one per lane
Pos  = Byte(u32) | LineCol { line: u32, utf16_col: u32 }
```

- Bases live only in `Tx.base`: every file an op reads or writes has exactly one, and a `Rename`'s `to` must be `Absent`.
- A `TextEdit` position is a UTF-8 byte offset into the base text, or a line and a UTF-16 column, which core resolves to bytes against the base text. `expected` still guards each edit: a mismatch rejects the Tx.
- `Clips` puts whole clips, in the lane format's schema, and deletes clips by id. It applies to a lane file newer than its base when every clip it puts or deletes is the same in the base and the current file, byte for byte, or absent from both. It is the only data op, so a new data feature changes the lane format, never the op set. The arrangement, plugin state (blob and sidecar) and new lane files are written with `Write`.

A Tx may touch several files. It is journaled and is one undo step. A Tx MAY also write `layout.json`; that write is journaled with the Tx but is never part of a revision or a delta.

The same JSON serves the server, `m2 tx`, MCP and later TypeScript tools. This Tx automates the hats pan in `examples/first-song/song.ts`: it gives the song function its `lane`, replaces the literal, and creates the lane file.

```json
{"id": "tx-7k2m9q4c",
 "base": {"song.ts": "sha256:4be1…", "data/song/hats-pan.json": null},
 "label": ["hats pan 0.3", "hats pan automated"],
 "ops": [{"op": "text_edit", "file": "song.ts",
          "edits": [{"start": 327, "end": 329, "expected": "()", "text": "({ lane })"},
                    {"start": 422, "end": 425, "expected": "0.3", "text": "lane.control(\"hats-pan\", \"bipolar\", 0.3)"}]},
         {"op": "write", "file": "data/song/hats-pan.json", "text": "{\"unit\": \"bipolar\", \"clips\": []}\n"}],
 "expect": {"confined": {"ranges": {"song.ts": [[327, 329], [422, 425]]}, "lanes": [["song", "hats-pan"]], "modules": []}}}
```

- *Why:* the next gestures (add track, automate, relink, delete track) all touch several files. A closed op set keeps core from growing with every data feature, and one base per file leaves nothing to disagree. Agents and TypeScript count in UTF-16, so a byte offset alone would make every Tx on a file with `é` or `ベース` in it fail.
- *Today:* matches since step 6 (`m2_song::tx` in `core/song/src/tx.rs`; `Session::check` and `Session::commit` in `core/session/src/tx/`), with what the step 6 design's C1 and C3 add for the owner to confirm: `Payload::Local` (a staged file or a before-image, for recovery and the undo of a binary write), `"whole"` in `Confined` ranges, and `Expect::Journal`. Every gesture is a builder of Tx in `crates/editor`; agents send any Tx to `POST /api/tx/check` and `/api/tx/commit`, or `m2 tx`.

**WRITE-3a.** Every path in a Tx (the keys of `base`, `file`, `from`, `to`, and a `Clips` lane) MUST be relative and `/`-separated, with no empty, `.` or `..` segment, and MUST parse through `DataPath::parse` to Code, Manifest, Arrangement, Module, Lane, PluginState, Asset or Presentation. A Local or Unknown path is refused with `tx.path`, and so is a target that is a symlink or whose parent resolves outside the project. `Tx.id` is metadata matching `^[0-9a-z-]{1,32}$`; core names the journal file itself.
- *Why:* Tx JSON comes from agents, MCP and later sandboxed tools, and `../../song` must never name a file. Ops that carried unparsed paths would also break [FMT-5](#paths).
- *Today:* matches since step 6: `Tx::validate` and `TxPath` check every path and the shape before anything is read, and the commit checks on disk, under the lock, links (a target that is one, or a folder on its way that is one, inside the project or not), names in other capitals, text that isn't UTF-8, and that every path, whatever its base, is spelled as the disk spells it: on a disk that ignores capitals or Unicode forms, `Song.ts` for `song.ts` would change the real file while the delta saw another (`core/song/src/tx.rs`; `hostile_paths_and_ids_are_refused` in `core/session/src/tx/props.rs`, `hostile_targets_on_disk_are_refused` and `a_file_spelled_another_way_is_refused` in `core/session/src/tx/tests.rs`).

**WRITE-4.** `check(tx)` compiles the candidate in memory and writes nothing. A Tx whose files are all class Data or Arrangement skips QuickJS, as an outside write to such files does ([WRITE-19](#outside-writers)). It returns the `GraphDelta`, the delta's hash and the diagnostics.

**WRITE-5.** `commit(tx)` returns one of:

```rust
Committed { code_rev, data_rev, delta: GraphDelta, diagnostics, patches }
Conflict  { files: Vec<{ file, current: Sha }> }   // every base that no longer matches
Rejected  { diagnostics, unexpected: Option<GraphDelta> }
```

### Expectations and the delta

**WRITE-6.** Core MUST verify a Tx against a `GraphDelta` it computes itself, using this closed set of expectations:

```rust
Expect = Identical                                  // an empty delta: source positions, labels, node numbering, site numbers
                                                    // and whether a control was written or inherited are ignored
       | Values(Vec<(Anchor, f64)>)                 // only these constants change, to these values (the same things ignored)
       | Confined { ranges: Map<Path, Vec<Range>>, lanes: Vec<LaneAddr>, modules: Vec<ModuleChange> }
       | Seen(DeltaHash)                            // commit only if the delta equals the one check() returned
Anchor = Written { file, range }                    // a value written in the code
       | Slot { site: { file, range }, slot }       // an inherited (unwritten) control, named by its slot (PKG-3)
```

`Confined` holds when, after nodes are matched by their delta names ([WRITE-8](#expectations-and-the-delta)): every node that differs was made by a site written inside a declared range (by its origin, `within` or `src`), or differs only in edges to such nodes; lane data differs only for the declared lanes; modules are added, removed, re-keyed or muted only as declared; and every byte outside the declared ranges is unchanged. A new kind of expectation needs a design review that changes this page.
- *Why:* gesture-shaped expectations would make core grow with every feature, and checks supplied by tools would take the guarantee out of core. Inserting an omitted argument turns an inherited control into a written one, which must still count as `Values`.
- *Today:* matches since step 6: core judges every Tx by its expectation on the delta it computes (`core/session/src/tx/expect.rs`), with the step 6 design's C1 (`Confined`'s rules on bytes and on states, assets and the arrangement) for the owner to confirm; each planner's own assertion stays in `crates/editor`.

**WRITE-7.** Core MUST take structured anchors, never `file#ordinal` strings. Those become debug labels made by `crates/editor`.
- *Why:* ordinals shift with every inserted call ([ID-12](#derived-identity)).
- *Today:* matches since step 6: core takes `Anchor`s; `file#ordinal/arg` ids are the editor's handles within one code revision (`crates/editor/src/controls.rs`), carried from an older one by the call's range (`controls::carry`).

**WRITE-8.** The `GraphDelta` lists nodes added and removed, inputs rewired, constants changed, lanes changed, plugin states changed, assets changed, whether the arrangement changed, and modules changed (added, removed, re-keyed, `muted`). Nodes are named so that inserting one can't rename another:
- A node made at a site is named by its module key; then its frame chain, each frame its ComponentId and its call's point ([ID-13](#derived-identity)), with nothing positional above a `key()` frame ([ID-7](#keys-and-names)); then the call that made it; then its argument path; then its occurrence within that site. Points are in the comparison's reference coordinates: through the Tx's own `TextEdit`s, or for an outside write and between revisions through `Edits::between` ([WRITE-12](#bases-and-revisions)). Sites inside packages keep their package offsets, since packages don't change within a Tx.
- A lane, `time` or import node is named by what it reads. A `time` node made inside a component call (or a `key()` frame) is named under that call's frame chain: each call that reads song time has its own.

`DeltaHash` is the SHA-256 of the delta's JSON in RFC 8785 (JCS) form, with nodes sorted by name. The delta drives the engine: values → `SetCell`, or an activation when other things change; notes and control lanes → `SwapLane`; audio lanes, assets, plugin states and the arrangement → prepared renders and loads, then an `Activate` of the same structure; a module's `muted` → its mute-in-song cell; structure → `continues`, prepare and `Activate`.
- *Why:* the engine needs to know exactly what changed, not guess. Names by walk order would let one inserted node rename every node after it: `Confined` would fail, the engine would replace instances it should keep, and two equal changes would hash differently.
- *Today:* matches since step 6 (`core/session/src/tx/delta.rs`, `delta_between`), with calls named by their `(` since step 7, in the base text's coordinates (the step 6 design's C17, now in the rule's words). Of what the delta drives, the server writes the cells of changed constants and swaps changed lanes into what plays when that is all the delta from what plays holds; for anything else it prepares an activation against what plays, which keeps every instance that continues, loads each changed plugin state into the instance it keeps, renders what audio needs, and switches the arrangement with it (`crates/server/src/graph/actor.rs`). The guess is gone.

**WRITE-9.** What a gesture means ("the wrap wrapped", "the named outlet is wired") MUST be asserted by planners in `crates/editor` and their tests, never by core. Adding a gesture MUST NOT change core: no core crate may depend on `crates/editor` (the crate graph checks this), and a change that adds a gesture and touches `core/*` changes this page first.
- *Why:* core stays small, and its guarantee stays the same for every client.

**WRITE-10.** Gestures map onto expectations as follows. Step 6 ports the 7 gestures that exist today (set a value, connect, disconnect, add an effect, remove an effect, write a notes lane, a code editor save) and step 1's two fixes; automate a knob, add a track, rename a label and mute in song are new builders.

| Gesture | Expectation |
|---|---|
| set a value | `Values` |
| connect, disconnect, add or remove an effect | `Confined`; the planners keep excise, rewire and wrap as their own assertions |
| write a notes lane | `Confined { lanes }` |
| relink unused data | `Confined { lanes: the lane it moves to }` |
| delete unused data | `Identical` |
| automate a knob | `Confined { the literal's range, a new lane }` |
| add a track | `Confined { a new file, ranges in song.ts, a new module }` |
| rename a label | `Identical` |
| mute in song | `Confined { the track call's options, modules: that module's muted }` |
| code editor save | `save()` |

Core keeps `save`, `Tx`, `GraphDelta` and its checkers, undo, the journal, the raw site, origin and control tables, and diagnostics. `crates/editor` gets `view.rs`, `timeline.rs`, `lens.rs` (with unit spelling generated from `core.ts`), the cable and effect planners, labels, the helpers at `core/script/src/sites.rs:268-317`, and `render.rs` (export at host level).

**WRITE-11.** Agents opt in to verification by calling `check`, showing the delta, and committing with `Seen(hash)`.

### Bases and revisions

**WRITE-12.** A Tx's base MUST be the content hash (SHA-256 of the bytes) of each file it touches, or `Absent` for a file it creates. Anchors are positions in those texts.
- A base equal to the file's current hash always applies.
- Otherwise core carries the ranges from the base text into the current one, failing when a change touched them. The base text is the one the Tx carries (`WithText`, whose hash core checks), or else the one in the session's store of recent texts keyed by hash, which is only a cache. With neither, the Tx is a `Conflict` naming the file.
- So a Tx that carries its base texts has the same outcome in every process, whatever versions a session happened to see. Agents and `m2 tx` SHOULD send them.
- A directory's hash (for a `Rename` of `data/<module>/`) is the SHA-256 of the `\n`-joined lines `<path>\0<sha256 hex>`, one for each file under it that `DataPath` parses as Lane or PluginState, with paths relative to the folder, `/`-separated and sorted bytewise. Dot files such as `.DS_Store` aren't hashed and move with the folder; any other file makes the `Rename` refuse, naming it.
- A revision number is only a hint.
- *Why:* a revision number means nothing outside the session that issued it, the 300 ms poll can miss versions, and the Rust and TypeScript tools must compute the same directory hash.
- *Today:* since step 6 bases are content hashes, `Absent` or `WithText`, found in a 32 MiB store of recent texts when a Tx doesn't carry them (`core/session/src/texts.rs`), and carried by `Edits::between` ([ID-13](#derived-identity)): a line diff whose runs of changed lines a token-level Myers diff refines, each hunk trimmed to bytes, so a change on another part of the same line doesn't stop a range (`core/session/src/text.rs`); the editor's control ids, leases and cables carry by it too (`crates/editor/src/controls.rs`, `cable.rs`); the directory hash is `m2_song::dir_hash`. Except: the editor's notes write, relink and delete-data still name the revision they were planned at and plan on the session's remembered snapshot of it (`Session::snapshot`, the last 64), so the piano roll sends no lane hash.

**WRITE-13.** A revision is a pair `(code_rev, data_rev)`. A change to Code or Manifest files bumps `code_rev`. A change to only Data or Arrangement files bumps only `data_rev` and stores lane diffs, not full snapshots. Control ids, gestures and carrying are scoped to `code_rev`, and a lease is re-resolved at every new `code_rev` ([WRITE-22](#gesture-leases)).
- *Why:* a lane edit must not invalidate a knob drag.
- *Today:* matches since step 6: a `Revision` is numbered `(code_rev, data_rev)` beside its sequence `number` (`core/session/src/session.rs`), and the server's leases and ids follow the session's `code_rev`. Except that the last 64 revisions each keep a full snapshot, not lane diffs.

**WRITE-14.** While the draft code is broken but the session has an accepted code revision, a data Tx MUST still work. It writes data files only and is checked against the last accepted lane declarations. Without an accepted code revision, a data Tx is rejected.
- *Why:* fixing code must not block editing notes.
- *Today:* matches since step 6 (`the_draft_rule`, `outside_data_is_taken_in_while_the_code_is_broken` in `core/session/src/tx/tests.rs`).

### Commit, journal and recovery

**WRITE-15.** A commit runs these steps, under the project lock:
1. compare-and-swap every target against its base;
2. write the journal `.music2/tx/<id>.json` and sync it. It holds the host name, the before and after hashes of every target, and the before bytes of every text target. A binary target's before bytes (a plugin blob) are stored once, by content, in `.music2/tx/blobs/<sha>`;
3. stage every write in `.music2/tx/<id>/`, which is on the same volume, then rename each into place;
4. accept the new revision;
5. remove the journal and the staging folder.

Between steps 1 and 2 the engine may hear the candidate as a preview ([PLANE-5](#planes-of-change)); nothing is accepted before step 4.
- *Why:* several files can't be replaced atomically, and the journal makes an interrupted commit recoverable. Staging beside each target would put temporary files under `data/`, where the watcher and `git status` see them. A 50 MB plugin blob must not be copied into the journal twice per save.
- *Today:* matches since step 6 (`core/session/src/tx/stage.rs`): the journal, then the staged files, pushed with `fsync`; one barrier (`m2_os::fs::barrier`: `F_FULLFSYNC` on macOS, `fsync` where a volume refuses it; `fsync` on Linux, where each push is already durable); renames checked at each step with an exchange and a create-only rename (`m2_os::fs::rename`: `renamex_np` on macOS, `renameat2` on Linux), rolled back in process when one finds an outside change. A volume without them (FAT, exFAT, SMB, NFS; NTFS always) reads and compares the target, then renames the staged file over it in one rename, so every target always holds its before or its after bytes; a rollback renames the before bytes back over it the same way. Step 5 comes later than this page says (the step 6 design's C9): a commit's journal and staging are removed after the next commit's barrier, or at close, and a completed journal found when the lock is taken only after its commit's folders are pushed and a barrier, so the removal is never durable before the renames are. A barrier that fails removes nothing: such a journal waits for the session's next barrier, as its own commits' do, and a close whose barrier fails leaves its journals to the next lock (`a_completed_journal_whose_barrier_failed_goes_after_the_next`, `a_close_whose_barrier_fails_keeps_its_journal_until_the_next_lock`). A folder sync that can't be done is skipped by every writer alike (`m2_os::fs::sync_dir`): on a volume with no folder sync (`vboxsf`), and for a folder that can be written but not listed, which can't be opened to sync it. Any other error (`EIO`) fails the write, except in step 8's push after the renames, which can't undo a commit that landed. A rollback pushes the folders it renamed into before its barrier; a staging folder is removed before its journal, and what a killed commit left half made (temporary files, a staging folder whose journal went) is swept when a writer next takes the lock. Killing the process at every disk call of a commit is tested (`core/session/src/tx/kill_tests.rs`). Since the G11 fix the pre-check (step 1) passes into a callback before the journal's first byte (`stage::commit`), where the session's host may send a data-only candidate to the engine; commits whose disk work fails there are swapped back ([PLANE-5](#planes-of-change)). A rollback whose barrier fails leaves its journal and staging to the next barrier, never tidied before the rollback is durable (`a_rollback_whose_barrier_fails_keeps_its_journal_until_the_next`).

**WRITE-16.** A journal left behind raises `tx.interrupted`, with FinishTx and DiscardTx fixes, when a process on the same host next takes the lock. Finish uses the staged files; Discard uses the recorded before bytes. Each fix is allowed only while every target still matches the hash the journal recorded before or after the Tx. If a target matches neither, the journal is set aside and reported, with no fix, and no project file is touched. A journal from another host (a synced folder) is `tx.foreign`, reported with no fix. Recovery never runs by itself.
- *Why:* recovery must never overwrite someone else's later edit, and a commit interrupted on another machine is that machine's to recover.
- *Today:* matches since step 6 (`core/session/src/tx/journal.rs`), with the step 6 design's C9 and C18 for the owner to confirm: a journal whose every target is at its after hash is a completed commit, tidied silently when the lock is taken next, a target at a newer journal's start or end (one that started where it ended, such as its undo) counting as at its after hash; another host is told by its machine id ([FMT-20](#presentation-and-local-files)), and its journals' before-images, and those of journals set aside, are kept. A Tx overlapping an interrupted commit's targets (a folder holding one included) waits for it. Finish and Discard apply while the interruption left code that doesn't compile (P3), and every CLI command that opens the project says them with their `m2 fix` commands, `m2 check` and `m2 render` included (`killed_at_every_commit_step_the_project_recovers`, `apps/m2/tests/recovery.rs`). The kill test runs every case twice: on a disk that swaps, and on one that can't (`Recorder { plain: true }`); one case writes `music2.toml`.

### The project lock

**WRITE-17.** A process that writes a project through music2 MUST hold an exclusive OS advisory lock on `.music2/lock` (the std file lock `core/session/src/render.rs:166-174` already uses) for as long as it may write: the app while the project is open, a CLI write command for its run. So one process at a time writes. The file holds `{pid, program, host, token, since}` only to make messages clear. The OS releases the lock when the process exits, so a crash leaves no stale lock.
- When the app opens a project another process holds (a long `m2 bounce --place`, a second app), it opens it read-only: it plays, shows a banner naming the holder, and offers to retry. Read-only means no `save()` and no Tx.
- When the volume can't lock (`ENOTSUP` or `ENOLCK`, as on some SMB, cloud and FUSE volumes), the project opens read-only with the Error `lock.unsupported`. music2 never writes unlocked.
- *Why:* two writer processes with no lock race between compare and rename.
- *Today:* matches since step 6 (`core/session/src/lock.rs`). The app opens a held project read-only with a banner naming the holder and Retry (`POST /api/graph/lock/retry`), and answers every write route 423 meanwhile (`crates/server/src/routes.rs`). On a network volume (`m2_os::fs::is_local`: no `MNT_LOCAL` on macOS; on Linux an NFS, SMB, CIFS, 9p, Ceph, AFS, Coda or FUSE file system) it takes the lock and raises the Notice `lock.local`, as the step 6 design's C2 proposes. A lock whose file was removed while held (`git clean -fdx` takes `.music2/` away) excludes nobody, so every write checks it first: it is taken again, or, when another process took it meanwhile, the session turns read-only naming it (`a_lock_whose_folder_was_removed_is_taken_again`).

**WRITE-18.** A writer that can't take the lock MUST fail before changing anything, with a message that names the holder and what to do:

```
error: nothing was changed: this project is open for writing in music2 (pid 4121, since 14:02).
Make the edit there, or close the project in music2 and run this again.
```

The CLI's commands sort like this:
- `check` (and its alias `build`), `render`, `graph`, `controls`, `cables` and `effects` only read. They never take the lock, and open their own session.
- `kernels` and `plugins` open no project, and `new` creates a new folder. None needs the lock.
- `bounce` without `--place` only creates a new asset and its provenance, with create-only semantics ([FMT-14](#assets-and-hashes)). That can't race, so it needs no lock and works while the app is open.
- Every other command that changes a project takes the lock: `set`, `connect`, `disconnect`, `add-effect`, `remove-effect`, `bounce --place`, `plugin-state`, `relink`, `delete-data` and `tx`. The message for `bounce --place` also names the lane file, and says the clip can be added by writing that file directly.

Forwarding writes to the holder is [deferred](#deferred-with-triggers).
- *Why:* owner decision 10: the lock now, forwarding when a workflow needs it. While raw file writes are allowed (owner decision 5), the safest writer must not be the one blocked.
- *Today:* matches since step 6 (`apps/m2/src/main.rs`; `apps/m2/tests/lock.rs`), with `automate` and `label` among the writers, and readers taking the lock for a journal scan when it is free, never while they read (the step 6 design's C19).

### Outside writers

**WRITE-19.** Outside writers (text editors, agents writing files, git, another machine through a synced folder) are first class. The watcher picks up their changes, classifies the paths with `DataPath`, and takes the same plane a Tx would. It waits for changes to settle: it batches them until the folder has been quiet for 150 ms and every changed path's `(size, mtime, hash)` is the same on two polls in a row, and while `.git/index.lock` exists. It then reads one snapshot and accepts it as one revision, on the slowest plane of the batch ([PLANE-2](#planes-of-change)). The lock can't stop an outside writer; compare-and-swap narrows the race between an outside write and a commit but can't close it.
- *Why:* files are the truth, whoever wrote them. A checkout, an editor's save-all or an agent writing several files arrives over several polls, and accepting a half-applied state plays wrong music and makes diagnostics flap.
- *Today:* matches since step 6: the settle rule (`core/session/src/watch.rs`) is fed by the server's watcher (`crates/server/src/graph/watcher.rs`); a batch that settled is read once, its paths alone (`Snapshot::read_paths`, `a_settled_batch_reads_only_its_paths_and_takes_in_the_same`), and taken in whole, each path only while it reads as it settled (`Session::take_in_only`); the session's own writes are told to the rule by their stamps; a path there for one poll only settles as gone. Since the G11 fix, on a local volume the OS's file-system events name what changed (`m2_os::watch`: FSEvents on macOS, in-tree over CoreServices for `FSEventStreamFlushSync`; inotify on Linux, one instance per process, read at most every 10 ms as FSEvents' latency groups events, and an event is queued before the writer's call returns, so a flush is a read that never waits), and a tick stats only the named paths, the open batch's and what the session just wrote: an idle tick stats nothing. The whole project is walked at open, every 5 s, when events were dropped or more than 4,096 paths came at once, and whenever a batch is due: only a poll that saw every path makes a batch ready, so a change whose other half an event names late is never taken in half (`a_late_event_never_readies_half_a_change`; `a_scoped_poll_sees_what_a_full_poll_sees` replays the full-poll tests' scenarios). The watcher ticks every 50 ms, at once when an event names a change while no batch is open, and when a batch's quiet ends. A tick holds the watch lock only to plan and to apply, never over a stat (`the_watch_lock_is_never_held_over_a_stat`); what the session wrote meanwhile is left out of that tick, and every file the session wrote is looked at again by the next, so an outside write right after it is taken in (`an_outside_replace_right_after_an_own_write_is_taken_in`). A path is stat'd only through names spelled as the disk spells them (`a_case_only_rename_settles_as_one_path`), and a folder moved or renamed in is walked (`a_folder_moved_into_the_project_is_taken_in`, `an_assets_folder_replaced_by_a_rename_is_taken_in`). On a network volume (its events name only this computer's writes), when events won't start (inotify's per-user limits included), with `M2_WATCH=walk`, or once events missed changes twice in 10 minutes (a change a walk found that no event named within 60 s; `events_that_miss_changes_give_way_to_walks`), a walk of everything is the only source: every tick while a batch is open, else every 50 ms to 1 s (20 times the last walk's time). A walk lists an asset no lane names from its folder entry, with no stat. A walk that lost events asked for (a Rescan) counts no missed events (`a_burst_past_the_hint_limit_is_walked_and_never_missed`); a folder made, filled or renamed after open is watched from its events (`a_folder_made_after_open_is_watched`, `a_folder_made_and_filled_at_once_is_watched`, `a_folder_renamed_in_the_project_is_watched_by_its_new_name`). On Linux a folder put where the project's folder was (a restore, or the folder removed and made again) is watched from the next walk, and a folder that could be read only after it was made is watched once its mode changes (`m2_os::watch`'s tests); a change of a file's change time alone (a hard link to it made elsewhere) is no miss (`a_change_of_the_change_time_alone_is_no_miss`). With a 5,000-file `assets/` on p16 (`m2-gates --server watcher`, G11's watcher; release, M1 Pro, five runs; before: the step 6 watcher, three runs):
  - Idle, its ticks use 0.18 to 0.27% of a core: two walks of everything in 10 s, 4.6 to 7.4 ms each, and no stat in between (before: a walk every tick, 32 to 33%). By walks alone, 3.8 to 4.3%.
  - A walk of everything takes 4.2 to 4.7 ms at p50, and 6.0 to 7.2 ms with 1,000 of the files named by a lane (before: 14.8 to 16.5 ms and 17.7 to 18.9 ms).
  - An outside write of a lane file, in place or as an atomic save, is played 172 to 181 ms after its last byte at p50 and 180 to 190 ms at p95, of which 150 ms is the quiet (before: 210 to 233 ms and 267 to 295 ms; 10 writes each). By walks alone, 205 to 254 ms at p50 and 247 to 326 ms at p95 (5 writes each).

### Opening a project

**WRITE-20.** `Session::open` MUST NOT fail because of code, manifest content, arrangement or data errors. A project whose code doesn't compile opens with diagnostics and no accepted code revision: the code editor works, and playback is silent until the code compiles. Opening fails only when the folder can't be read, has no `music2.toml`, or its `format` is missing, older or newer than this app's ([FMT-3](#manifest-and-versions)). A project whose lock is held elsewhere, or can't be taken, opens read-only ([WRITE-17](#the-project-lock)).
- *Why:* a project with a half-typed `song.ts` must be fixable in the app (owner decision 6).
- *Today:* matches since step 6: `Session::open` opens a broken project with the empty revision and `draft_errors`, and the app opens it silent, in its code, and plays it once a save compiles (`a_broken_project_opens_and_plays_once_saved_fixed` in `crates/server/src/graph/tests.rs`).

### Undo

**WRITE-21.** Undo applies the stored inverse Tx. One Tx is one undo step. History stays in memory. An inverse undoes only what its Tx did, or it is a `Conflict`:
- a `TextEdit` is located by the carried range plus the recorded value;
- a `Write`, `Remove` or `Rename` applies only while its target's hash is the one the Tx left (or still `Absent`);
- a `Clips` op applies only while every clip it touches has the content hash the Tx left (or is still absent); otherwise the `Conflict` names the lane and the clip id;
- the undo of a `save()` is a `Write` whose base is the hash the save wrote.
- *Why:* undo must restore the edit, not an old copy of the file over someone else's work.
- *Today:* matches since step 6: every step is a stored inverse Tx on one history, at most 500 steps and 64 MiB of retained text (`core/session/src/session.rs`, `TxStep` in `core/session/src/tx/mod.rs`); the inverse of a `Clips` op that meets an outside change to its clip is a `Conflict` naming the lane file and the clip (`undoing_a_clip_after_its_outside_change_conflicts`).

### Gesture leases

**WRITE-22.** A drag uses a lease:
- `begin(anchor, code_rev)` resolves once through the session and returns the lease, its cells and the current value;
- `update(lease, seq, value)` goes straight to the engine as `SetCell`, never through the session, and out-of-order updates are dropped;
- `commit(lease, seq, value)` and `cancel(lease)` go to the session. A commit is one coalesced `Values` Tx, and the engine installs the committed value in the same step that ends the lease;
- at a `code_rev` change, the session carries the lease's anchor into the new revision ([WRITE-12](#bases-and-revisions)). If it carries and still reads the accepted value, the lease stays, with its cells mapped into the new plan. Otherwise the lease ends and the accepted value is put back.

The session runs as an actor on its own thread, so nothing that waits on a compile blocks the engine, the transport or a lease's updates.
- *Why:* previews must never wait on a compile, and an agent saving `tracks/drums.ts` must not snap back a knob being dragged in `tracks/bass.ts`.
- *Today:* matches since step 3b (`crates/server/src/graph.rs`, `graph/lease.rs`, `graph/actor.rs`), and its cells since step 5, with these differences until step 6:
  - `begin` resolves against what the session last published: a revision among the last 64, through its code revision, or an id of one of the two code revisions before the accepted one's, through aliases the session carries once per code change. Only a client further behind waits for the session, and so does one a code revision or two behind while a settle hasn't yet carried the aliases to the code revision it published (they are read only once they carry to the accepted one's). Its cells are a `CellTarget`, the `CellId`s of its value in the renderer that plays (`Begun.cells` counts them), and what can be leased is a literal written in code or a declared control a call leaves out, which plays its default until its commit writes it in (both `home: code`).
  - `update` is a cell write straight into the slots of the renderer the lease aims at (`Player::set_cells`, by its `CellTarget`), never through the queue, so it is never dropped or kept waiting (RENDER-28). It is written under the control plane's lock, as everything else for a lease is, and a renderer built while the lease lives gets its value before it is sent, so an activation loses no update. Its seq answers `Graph::applied` once a block has heard it: a block late at most, never early.
  - `commit` is one `Values` Tx since step 6 (`Gestures::set` in `crates/editor`), one undo step; for a control its call leaves out, it writes the argument in (the step 5 design's D5). An outside change in the knob's own file that compiles rides along in the commit's baseline, and doesn't end the drag (`a_knob_commit_after_an_outside_edit_in_its_file_keeps_both`). The committed value reaches the engine in the step that ends the lease: in a new plan prepared with it, else as a cell write.
  - At a code change, a lease is carried by its whole call (WRITE-12's carry, by `Edits::between`), which is stricter than its literal's range. A lease's value is written into every new plan before it is sent, so it plays from its first block, window included. When the new plan fails to prepare, the lease's control moves to the accepted revision while its updates go on to the plan that plays, by its own origins.
  - Pending the owner's decision on the step 3b design's clarifications: `cancel`, idle expiry and "the window closed" act on the control plane at once, never through the session (C2); a commit refused only because the draft doesn't compile is pending, the value plays on and the session writes it once the draft compiles, or cancels it after 30 s (C5); a lease ends when idle for its TTL (10 s, renewed by updates and the web's keepalive every 2 s while a knob is held; `ttl_ms` on `POST /api/graph/lease/begin`, at most 60 s), or when the WebSocket of the window that began it closes (`?client=`); the news and `GET /api/graph/leases` list every live lease, so an agent can cancel one (C6). A pending commit that ends unsaved (its 30 s, the project closing or another opening, an outside save that changes its control, a cancel) is said in a toast.
  - The knob routes (`/preview`, `/set`, `/preview/cancel`) find a lease by its gesture string and the control the request names, so a string holds a lease per control: a script that sends `"script"` for every knob reaches each one's own. A late request of a lease that ended says why, unless its own `/preview/cancel` ended it. `GET /api/graph` lists the live leases with their controls' ids as its view names them, so the page keeps a dragged knob mounted when a save renumbers it.
  - Measured: `crates/server/src/graph/tests.rs` (an outside save to another file during a drag never plays the code's value, not for one frame of the crossfade; saves above and below the dragged call keep it; a begin between a settle's phases; one gesture string on two controls; a pending commit that ends unsaved; a broken save then a release; a renderer that fails to build; a cancel during a commit; expiry and a closed window), and `m2-gates --server drag` (G9, p16: a drag through 12 saves, each a new renderer).

**WRITE-22a.** A lane edit made while playing (dragging a note, drawing automation) uses a lane lease: `begin(lane, clip)`; `update` sends a preview `SwapLane` straight to the engine with no file write, under the sounding-note rules of [RENDER-26a](#plans-data-and-arrangement-swaps); `commit` is one `Clips` Tx; `cancel` swaps the accepted data back. A tempo drag is a lease too ([RENDER-27a](#plans-data-and-arrangement-swaps)).
- *Why:* a dragged note must be heard where it is during the drag, without a journaled commit, a revision and an undo entry for every step.
- *Today:* not built: a drag is heard on release. Since the G11 fix, the release's write is heard as its commit's preview, before it is durable ([PLANE-5](#planes-of-change)), through the `SwapLane` path a lane lease's `update` and `cancel` will use (`crates/server/src/graph/preview.rs`).

## Diagnostics

### Model

**DIAG-1.** Every problem MUST be reported as:

```rust
Diagnostic { severity: Error | Warning | Notice, code: &'static str, message: String,
             src: Option<Src>, module: Option<Key>, fixes: Vec<Fix> }        // fixes: the likeliest first
Fix        { code: &'static str, title: String, likely: bool, tx: Tx }       // a ready-to-commit Tx, bases included
```

The message is plain words, and names the file, the field and the fix where they apply.
- A fix is built by whoever raised the diagnostic: `core/song` for data fixes, the journal code for FinishTx and DiscardTx, `crates/editor` for Restore. Applying it is `commit(fix.tx)`, and a stale base gives `Conflict`, as for any Tx.
- `likely` marks the one fix the problem plainly calls for, which the app offers in one click. Others are a choice.
- Fix codes are a closed vocabulary, the kebab-case of the names this page uses: `relink`, `restore`, `delete-data`, `repin-asset`, `fix-asset-name`, `retag`, `convert`, `assign-clip-ids`, `renumber-clips`, `finish-tx`, `discard-tx`. A new fix adds a code here, never a type to core.
- *Why:* agents and the app need to act on a problem, not parse prose. A fix that is a Tx is checked, journaled and undone like any edit, and a new data feature never grows core's types.
- *Today:* matches since step 6: a fix is `{ code, title, likely, tx }`, its Tx's id derived from the problem and the hashes of the files it was raised on, and applying it is committing its Tx (`core/song/src/diag.rs`). Build and check errors are `m2_ir::Diagnostic`, with a severity and a code but no fixes. The codes the step 6 design's C2 adds (`tx.invalid`, `tx.expected`, `tx.unexpected`, `lock.held`, `lock.local`, `git.locked`) are raised but not yet in the table below, pending the owner.

A swap within one change (two tracks trading keys in one save) isn't detected: no site has a number to compare. Comparing the `(` point of each module's `track()` call ([ID-13](#derived-identity)) would detect it; that is deferred until a swap is seen to mislead.
- *Why:* a claim that changed hands should be visible, but only what can be detected is promised, and what a project read says must not depend on how long a session has run.

### Delivery

**DIAG-4.** Diagnostics MUST be sent with every revision over the WebSocket, returned to agents by project reads, and printed by every CLI command that opens a project.
- *Why:* a problem nobody sees is the silent data loss this contract exists to end.
- *Today:* matches for what exists. The session's problems are in the project state the app fetches, and in every `{"t":"graph"}` event over the WebSocket, together with the accepted revision and the draft's errors (`Graph::news` in `crates/server/src/graph.rs`; `graph_changed` in `crates/server/src/lib.rs`). Since step 6 the session's own (`tx.interrupted`, `tx.foreign`, `lock.*`) come first, and an outside write's `data.claimed` is a toast. The app shows them in a "Needs attention" strip above the timeline (`web/src/components/Attention.tsx`). Every CLI command that opens a project prints them, each with the commands that apply its fixes (`m2 relink`, `m2 delete-data`, `m2 fix`). Since step 5 a package module that doesn't load (`pkg.invalid`, the session's) comes first among them, in the state, the news and every CLI command's output (`Session::problems`; `package_problems` in `apps/m2/src/main.rs` for the commands that only compile). The draft's errors are still a separate list, `diagnostics`, and there is no MCP yet.

### Fixes

**DIAG-5.** A fix MUST NOT be applied automatically: not on open, read, watch or commit. It runs only when a person or an agent asks (a button, `m2 relink`, committing the fix's Tx). Applying a fix is a Tx: journaled and undoable.
- *Why:* only the files on disk decide what is accepted (P3).

**DIAG-6.** Reconciliation proposes and never applies. It works from the files of one revision, never from history:
- **A lane key changed:** a lane file no declared lane reads is offered to every declared lane that can read it (a file with no clips fits any kind) and has no data yet. Likeliest first: the same lane key on another track (its track was renamed), then another lane of its own track, then the rest.
- **A track key changed:** when exactly one `data/<k>/` folder is claimed by no module and exactly one declared module has no folder, `data.unclaimed` on that folder offers Relink of the whole folder first (`DataPath::Module(k)` to `Module(new)`: lanes and state together, one `Rename`). It is likely when the folder's lane files match the new module's declared lanes. The per-lane offers follow.
- A fix is `likely` only when it is alone in first place and on the data's own track or lane.

The app shows these in its "Needs attention" strip, with Relink, Restore (rename the key back, a Tx built by `crates/editor`) and Delete.
- *Why:* a rename by hand must be one click from sounding again, and the offer must be the same in the app, the CLI and an agent's read.
- *Today:* matches since step 4, except Restore (`core/session/src/unclaimed.rs`). A renamed track's folder is offered whole, then lane by lane (lane by lane only while it holds a file that is neither a lane nor a state, which keeps it from moving whole, and the problem names that file); plugin state no plugin reads is offered to a plugin of its kind. Since step 6 each fix is a Tx built where its problem is raised (`core/session/src/unclaimed.rs`, `core/song/src/data.rs`), and applying it is committing it: `m2 fix` and `POST /api/graph/fix`; `m2 relink`, `m2 delete-data`, `POST /api/graph/relink` and `/api/graph/data/delete` commit the offered fix, or build the same Tx (`crates/editor/src/data.rs`). A fix whose base went stale is a `Conflict`. Restore isn't built.

## Component descriptors

The package API is the component descriptor, written in TypeScript. `m2pkg.toml` keeps only the ABI side: kernels, their ports and the wasm file.

```ts
export const delay = component({
  id: "delay", label: "Delay",
  inputs: { in: port.audio() },
  controls: { time: control.secs(0.25).range(0.001, 2).log(), feedback: control.frac(0.3), mix: control.frac(0.3).smooth() },
  settings: {},                  // build-time values: changing one rebuilds
  output: port.audio(),
  positional: [],                // sugar, e.g. ["cutoff", "q"], so lowpass(x, 1000) keeps working
  editor: { category: "Delay & Reverb", insert: { time: 0.25 } },
}, (x, { time, feedback, mix }) => kernel("std:delay", { in: x, time, feedback, mix }));
```

**PKG-1.** A package's components MUST be declared with `component(descriptor, body)`. Plain functions keep working, with fewer editor features.
- *Why:* every package and song call is written against this, and it defines the ControlId slots.
- *Today:* since step 5 `@m2/core` 1.1.0 has `component(descriptor, body)` with `port`, `control`, `setting`, `each` and `signature`, and derives each component's call type from its descriptor, so the editor checks calls against it (`core/script/sdk/core.ts`; `core/script/sdk/check/calls.ts`), and its signature help and hover list a call's options. The build takes every form the type does: a helper may forward options it wasn't given, since `undefined` where the options go is no options (`options_left_out_may_be_forwarded` in `core/script/src/tests.rs`). Every std component is declared this way (`std/src/*.ts`; `std_is_declared_with_descriptors` in `core/script/tests/std.rs`), and `core/script/sdk/check/std.ts` checks std's calls as the editor does. The old form, `component({ controls: ["1.cutoff"] }, fn)`, still works; std no longer uses it.

**PKG-2.** `m2pkg.toml` MUST NOT describe TypeScript. `[[effect]]` entries and their `args` text are deleted; the descriptor's `editor` field replaces them.
- *Why:* TypeScript written as text in TOML can't be checked.
- *Today:* since step 5 std's `m2pkg.toml` describes its kernels only. Each effect's category, description and `insert` (the old `args`, value for value) are in its descriptor's `editor` (`std/src/filter.ts`, `std/src/fx.ts`, `std/src/dsp.ts`; `std_effects_are_the_manifests_old_effects` in `core/script/tests/std.rs`). The runtime keeps no effects of its own: a manifest that still has `[[effect]]` fails to load, naming PKG-2 (`core/runtime/src/packages.rs`), and editors read effects from the descriptors (`Session::effects`).

**PKG-3.** Every declared control that isn't optional ([PKG-5](#component-descriptors)) and isn't connected to a signal MUST become exactly one const node whose origin is `(instance, slot, written | inherited)`, and that const is a cell. The body always receives a signal, whether the caller wrote a value, connected a signal or left it out.
- *Why:* one cell per control makes inherited controls addressable (`Anchor::Slot`) and keeps every use of a control live.
- *Today:* matches for components declared with descriptors since step 5 (`normalise` in `core/script/sdk/core.ts`): a written number's origin is its argument path, a quantity's is its own call, and a left-out control's is its instance's call with no path, marked inherited. A call made by native code has no site, so its controls are consts with no origin, which the checker folds. Every std component is declared with a descriptor, so every control a std call leaves out is a const too. The session shows each as a knob at its default (`Control.written` false, its id `file#call/@slot`), whose first edit writes it into the call as a plain number, positionally when it is the next argument, else in the options object (inside the braces of one with no properties, keeping what is in them), verified against the graph, and undone by finding the inserted text where later edits carried it (`Insertion` in `core/session/src/edit/lens.rs`, `Undo::Inserted` in `edit.rs`). Which argument holds the options is the one the call's run read them from (`Frame.options`), since only the run can tell `lowpass(x, opts)`'s options from a cutoff. A call that can't take it (its place holds `undefined`, its options aren't an object in the call) shows it read-only (`every_declared_control_is_a_knob` in `core/session/src/gate5_tests.rs`, `options_the_call_reads_are_where_controls_go` in `edit/insert_tests.rs`). The edit's message shows the call before and after, with each long argument it doesn't touch cut to `…` when the call doesn't fit on a line (`master(…)` → `master(…, { ceiling: 0 })`), and so does a cable written into a call.

**PKG-4.** The descriptor's default is what songs see. A kernel port default in `m2pkg.toml` applies only when a kernel is called directly with that input unset. When std is rewritten on descriptors, each descriptor default MUST equal today's effective default, so every fixture renders the same bits.
- *Why:* one place states what a song gets when it says nothing.
- *Today:* matches since step 5. Each std default is in its descriptor, made by the expression that gave it before (`control.ms(45)` is `ms(45)`; `control.scalar(0.707)` reads the same decimal as the port default did), and `m2pkg.toml`'s port defaults reach only direct `kernel()` calls. `std_defaults_are_todays` (`core/script/tests/std.rs`) compares each with the kernel port default or `??` fallback it replaced, and every pure fixture renders the same bits.

**PKG-5.** A control whose presence changes the graph (the mixer's `pan`, which adds a panner only when written) MUST be declared optional. Absent means no node. Adding or removing it is structural; changing its value is not.
- *Why:* normalising every optional control to a signal would change the sound of existing songs.
- *Today:* matches since step 5. `control.<unit>(…).optional()` declares such a control: left out, it makes no node and the body gets `undefined`. The mixer declares its `db` and `pan` so, and adds a gain or a panner only for a channel that writes one (`std/src/mix.ts`).

**PKG-6.** Dictionary slots, such as the mixer's `channels: each({ in, db, pan })`, make the user's key the identity on purpose ([ID-18](#renames)).
- *Today:* `each()` exists since step 5: an entry's controls are named `<slot>.<key>.<control>` (`channels.hats.db`), so the keys follow the key rule (ID-1), and an entry may be a bare signal when it declares one input.

**PKG-7.** `editor.category` is a free string that the UI groups. Core MUST NOT hold a list of categories.
- *Why:* core holds no UI vocabulary (P10).
- *Today:* matches since step 5: a category is what a descriptor's `editor.category` says, and core lists none (`the_deleted_items_are_gone` in `core/session/src/gate5_tests.rs`). The web's effect browser keeps an order and an icon for the categories it knows, and lists any other as a group of its own after them (`web/src/components/EffectBrowser.tsx`).

**PKG-8.** A control's `.range()` is a display hint. It is a validation constraint only when declared as one, and a value is never clamped silently.
- *Why:* a knob's preferred range must not rewrite what the code says.
- *Today:* matches since step 5. A descriptor declares `.range()` and `.strict()`, and at build the SDK refuses a value outside the strict range declared for its unit (the control's own, or the one `accepts` gives that unit), never clamping it (`a_strict_range_holds_for_the_values_unit` in `core/script/src/tests.rs`). A knob's range and log scale are the ones its control declares for the knob's unit, which is its constant's (`accepts` gives another unit's: `osc.saw(semis(60))` shows 0..127); a raw `kernel()` input shows its port's `in lo..hi`; otherwise, or when one literal feeds controls that declare different ranges, the knob has none (`Knob.range` null), and the web picks a span for its unit and widens any span to show the value written (`web/src/lib/graph.ts`). Core guesses no range from a unit.

**PKG-9.** Frames MUST record the ComponentId: the package and the descriptor's `id`, never the module file it is in. An `id` is unique within its package; a duplicate is a package load error. So `import { delay as echo }` is recognised, and moving `delay` from `std/fx.ts` to `std/delay.ts` changes nothing.
- *Why:* recognising a component by how it is spelled, or by the file it lives in, breaks on any alias or move (P1).
- *Today:* since step 5 frames record the ComponentId, `<package>:<id>` or a project component's bare id, from the package the defining file belongs to (`__m2_home` in `core/script/src/lib.rs`), so an alias or a move changes nothing in the IR; two definition sites with one id are a build error, and `m2_script::describe` reports them as `pkg.invalid`. The session recognises an effect by its call's frames, never by the name it is called by, so `echo(x)` after `import { delay as echo }` is the Delay effect with delay's knobs (`effect_at` in `core/session/src/edit/effect.rs`; `an_import_alias_is_the_component`, `moving_a_component_keeps_its_id` in `effect_tests.rs`).

**PKG-10.** Units are a closed core enum. Packages MAY add spellings (unit constructors) for existing units, never units.
- *Why:* units are part of the IR type system that the checker enforces.
- *Today:* matches (`core/ir/src/kind.rs:8-58`). The SDK's spellings are one table, `UNITS` in `core/script/sdk/core.ts`, with exactly one canonical spelling per unit.

**PKG-11.** The build MUST emit the descriptors and a table of unit constructors generated from `core.ts`. Editors and gestures use that table; no other copy exists.
- *Why:* a hand-kept copy drifts from the SDK.
- *Today:* since step 5 the unit constructors are made from one table in `core/script/sdk/core.ts`, and every build returns it (`Build.units`) with the descriptor of every component its modules declare (`Build.components`), numbers in base units with their spelling (`core/script/src/component.rs`); `m2_script::describe` catalogues every package's components module by module. The session keeps both with each revision (`Compiled.components`, `Compiled.units`) and the catalog with the session (`Session::catalog`): the cable planner writes a default in its descriptor's spelling from the build's table, `ms(45)` with `ms` imported when the file lacks it, and no other copy of the table exists; the effect browser and planner read the catalog. Every call form the planners write is listed in `core/session/tests/forms/forms.ts` (`planned_call_forms_are_current`), which `tsc -p core/session/tests/forms` checks as the editor does, as `tsc -p core/script/sdk/check` checks the SDK's and std's own call forms; web's `npm run typecheck`, and so `npm run build`, runs both.

**PKG-12.** Descriptors and cells land in step 5, before Tx in step 6.
- *Why:* Tx anchors must be able to name inherited controls, or step 6's anchors and ported gestures would be redone.

**PKG-13.** An audio input that only listens (a detector or key input, such as `follow`'s `in` or a compressor's side input) MUST be declared `port.audio({ sidechain: true })`. A hosted plugin's audio inputs other than its main one are sidechain ports. Monitoring mute and solo never act on a sidechain port ([MON-2](#monitoring-overlays-and-mute-in-song)).
- *Why:* muting the kick must not un-duck a bass whose compressor is keyed from the kick's audio.
- *Today:* since step 5 a frame records the signal each of its sidechain inputs received (`Frame.sidechain`), a dictionary entry's by its path (`others.hats.side`, `an_entry_sidechain_input_is_recorded`), whatever order the calls ran in, and the checker carries each as a port into `Flat.sidechain`, or a voice's `Voice.sidechain` when a voice made it (`core/ir/src/check.rs`). std declares `follow`'s `in` and `duck`'s `side` as sidechain inputs (`std/src/dsp.ts`, `std/src/fx.ts`). Since 8b.4 the checker also lists where overlays go (`Flat.overlays`, [MON-1](#monitoring-overlays-and-mute-in-song)) and leaves out every sidechain input: an input made inside a frame that recorded a sidechain, which reads the signal that frame received; a plugin's audio inputs other than `in`; and a voice's capture that such an input reads (`core/ir/src/overlay_tests.rs`).

**PKG-14.** A control MAY be declared `.smooth()`: a gain, a mix or anything else that clicks when it steps. Its cell then ramps over one block on every change ([RENDER-22a](#cells)).
- *Why:* the descriptor knows which controls click; the engine doesn't.
- *Today:* since step 5 std marks smooth the controls its kernels read every sample without smoothing, where a step jumps the output: every filter's `cutoff` and `q`, `delay`'s `time`, `feedback` and `mix`, `drive`'s `amount`, `pan`, `vca`, `scale`, `add`, `blend`, `when` and `choose`, `range`'s and `xrange`'s `lo` and `hi`, `lfo`'s `phase`, the square's `width`, the mixer's `pan`, and the instrument controls that reach them (`bass`'s `cutoff` and `drive`, `pluck`'s `brightness`, `pad`'s `cutoff`). `std_smooth_controls_are_the_per_sample_ones` (`core/script/tests/std.rs`) holds the list, and `a_range_bound_ramps` (`core/play/tests/knobs.rs`) hears a range's bound ramp where it sets a gain. A control whose step only changes a rate steps, as the phase runs on: an oscillator's `freq`, `mtof`'s `pitch`, the envelopes' times (and `adsr` approaches a new `sustain` at its decay rate). The effects' kernels, `gain` and `duck` glide their own levels (`compress` reaches its through its envelope). `.smooth()` helps only a kernel that reads the control every sample, and only where a ramp is a glide: `limit` reads `ceiling` once per block, where a one-block ramp arrives as one value, and `lfo` divides the song's beats by `period`, so a ramp of it would sweep the LFO through many cycles in one block; neither is marked, and gliding either would be a kernel change. A one-block ramp of `delay`'s `time` (about 3 ms) still moves the read head, so it removes the hard step but not the pitch chirp.

## Homes of values

| Home | Holds | Example |
|---|---|---|
| **Code literals** at declared slots | std knobs, mixer faders and pan, effect settings, "mute in song": the code is the preset | `reverb(x, { mix: 0.25 })` |
| **Lanes** | values that change over time | `data/bass/cutoff.json` |
| **Plugin state blob** | a plugin's internals | `data/lead/lead.state` |
| **`layout.json`** | shared presentation: track order and colour, keyed by track key | `{"tracks": {"kick": {"colour": "#e4572e"}}}` |
| **`.music2/`** | local state: mute and solo, override latches, loop range, zoom, selection | `.music2/overlays.json` |

**HOME-1.** Every value MUST have exactly one home, and the UI MUST show which. Every value that `controls()`, the view and leases return carries `home: code | lane | state | layout | local`, and a test checks it for every control of every fixture.
- *Why:* each new feature (mixer, reorder and colour, automation, plugins) would otherwise pick its own convention.
- *Today:* matches since step 5: `m2_session::Home` is on every `Control`, knob, read-only value, lease (`LeaseInfo`) and lease begin (`Begun`), and is `code` for each (a literal, or a declared default whose edit writes the code) until lanes, latches and plugin state have knobs. `every_value_names_its_home` (`core/session/src/gate5_tests.rs`) checks the view as it is sent, for the five fixtures and a song that calls every std component.

**HOME-2.** "Automate this knob" MUST be a `Confined` Tx that replaces the literal with `lane.control(key, unit, <the old literal>)` and creates an empty lane file. Dragging a knob that a lane or a cable drives sets an override latch ([MON-6](#monitoring-overlays-and-mute-in-song)); it never edits the fallback, the lane or the cable.
- *Why:* the fallback keeps the song sounding the same where no clip is, and a drag must not quietly rewrite automation.
- *Today:* matches for "Automate" since step 6: one `Confined` Tx on the value's expression and the track function's parameters, with the empty lane file (`crates/editor/src/automate.rs`; renders before and after are the same bits). Override latches aren't built ([MON-6](#monitoring-overlays-and-mute-in-song)).

**HOME-3.** Presentation MUST NOT go in files that define behaviour: no colours in `track()` options, no canvas positions in code.

**HOME-4.** For a plugin parameter, precedence is: a signal connected in code, then a literal in code, then the state blob. The state's value for a parameter owned by code is ignored.
- *Why:* what saved state means must be decided once.
- *Today:* matches since step 7. A literal or a port is sent whenever it differs from the value last sent, and every parameter code owns is sent again at the first call after a reset, and at the first two after a state load or an export (`plugin_events` and `PluginNode::process` in `core/runtime/src/lib.rs`): a plugin may apply a loaded state at its next call, over what that call sends (Surge XT does). So the blob's value for one plays for at most two blocks (`a_state_load_resends_code_owned_parameters`). A plugin that applies a loaded state later than that needs [HOME-5a](#homes-of-values)'s revert, which comes with plugin windows.

**HOME-5.** A gesture in a plugin window on a parameter that is a code literal MUST write the literal through a coalesced Tx. On a parameter driven by a signal, it sets an override latch ([MON-6](#monitoring-overlays-and-mute-in-song)).
- *Why:* a plugin's GUI can't refuse a gesture, and a cable must not be overridden silently.

**HOME-5a.** The host MUST treat parameters that code owns like this:
- Between the plugin's gesture begin and end on such a parameter, the host stops sending it the code value, until the coalesced Tx commits. If the Tx is rejected, the host sends the code value again.
- A change the plugin reports outside a gesture (a preset loaded in its own browser) is set back to the code value at the next block, and the session raises the Notice `plugin.param-reverted`, listing the parameters.
- When code stops owning a parameter (its literal or cable is deleted), the plugin keeps its current value, and the next state save records it.
- *Why:* during the 100 ms or more before the Tx is accepted the host would fight the user's hand, a preset load must not silently overrule the code, and a released parameter must not jump.
- *Today:* the third point only, since step 7: a kept instance whose code stops setting a parameter keeps the value it was last sent, as nothing sends it another. It is flagged (`PluginInstance::released` in `core/runtime/src/plugins.rs`) until a state load lands, so an export plays its node with a new instance from the committed state, as `m2 render` does ([RENDER-1](#offline); `a_released_parameter_keeps_its_value_and_its_instance_isnt_lent`). Gestures aren't seen and nothing is set back: plugin output events are collected, not used ([HOST-4](#pluginhost)). Both come with plugin windows.

**HOME-6.** State autosave, once plugin windows ship, is a coalesced data-plane write: one Tx after a gesture ends, or after about 1 s of quiet following the plugin's `mark_dirty`, which is how CLAP reports many changes (a wavetable or a modulation edit) that have no gesture. It takes the prepared-data plane, outside the 20 ms budget, and the journal stores its before bytes once ([WRITE-15](#commit-journal-and-recovery)). A saved state is never pushed back into the instance that produced it: a load is skipped when its blob's hash equals the state the instance holds, the one it last saved or last loaded, at creation included.
- *Why:* state blobs are often 1–50 MB, and a write per parameter change would flood the disk and the undo history. A load skipped against the last save alone would skip a redo: save S, load C (an undo), load S.
- *Today:* autosave isn't built (it comes with plugin windows). The host keeps the hash of the state each instance holds, set by every load, at creation too, and by every save, and cleared by a load that fails, which may have landed in part (`MainSide.holds` in `core/plugins/src/inprocess.rs`); tested by `a_load_of_the_held_state_is_skipped`, `a_reload_after_another_load_is_never_skipped` and `after_a_refused_load_the_old_blob_loads_again` (`core/plugins/src/tests.rs`).

## Monitoring overlays and mute in song

**MON-1.** Mute and solo MUST be engine overlays: gain cells keyed by module key, on track modules. They work for every song, whatever shape its code has inside its tracks. The planner puts one overlay gain cell on each consumer port that a track's audio export feeds. The root module (`song`) can't be muted or soloed, and neither can parts within one track; `key()` frames are reserved as a later place for that.
- The consumer ports are the checker's sites (`Flat.overlays`): each input of a node, each capture of a voice and each feedback that reads the audio of a track other than its own module, except sidechain inputs ([MON-2](#monitoring-overlays-and-mute-in-song)); and the song's output when it reads a track directly. The same code gives the same sites.
- The overlay is a built-in op, in every plan, offline renders included. At 1 it copies its input, so it changes no bit; at 0 it writes +0.0. One node and one cell per site.
- In an activation's window every audio edge that crosses tracks reads through an overlay: a fade on a site's input has the site's overlay on its new side; a fade's old side and a ghost's input that the plan before read through one get one of their own for the window, at the new plan's value for the same track and consumer.
- *Why:* a song written by hand or by an agent, with no mixer, still needs mute and solo.
- *Today:* the engine half is built in 8b.4 (`core/ir/src/check.rs` `overlays`, `core/runtime/src/overlay.rs`; `core/runtime/src/tests/overlay.rs`, including `an_edit_while_muted_keeps_the_track_silent`). Each overlay runs right after its source, so a feedback consumer reads this block's. The server's mute and solo come next.

**MON-2.** Mute MUST silence its module's audio export at every consumer port except sidechain ports ([PKG-13](#component-descriptors)), which always get the unmuted signal. Control exports such as `kick.env` keep flowing. So muting the kick still ducks the bass, whether the ducking reads `kick.env`, `follow(kick.out)` written in `song.ts`, or a compressor keyed from `kick.out`. The mixer shows this.
- *Why:* muting the kick must not suddenly un-duck the bass, and a refactor that keeps the sound must not change what mute does.

**MON-3.** Solo MUST keep every audio export on a path through a soloed module, and mute the others, with the same exception for sidechain ports.
- The paths are over the sites: a site `m → c` (track `m`'s audio read in module `c`) is heard when no track is soloed, or when some soloed `s` is `m` or feeds `m`, or is `c` or is fed by `c`. Sidechain inputs aren't sites, so they are no edges here. Each site has its own cell, so soloing a bus keeps a vocal's way into it and mutes the same vocal's direct way to the song.
- Mute wins over solo on the same track, mute in song included: a track muted in the song stays silent when soloed.
- *Today:* built in 8b.4 (`values` in `crates/server/src/graph/overlay.rs`; `solo_keeps_a_bus_fed_and_its_sources`, `mute_wins_over_solo`, `a_track_muted_in_song_stays_silent_when_soloed`).

**MON-4.** Mute and solo persist in `.music2/`. Overlays MUST NOT change files, revisions, exports or agent renders. An export made while overlays are active carries the `overlays.active` Warning.
- The file is `.music2/overlays.json`, `{"mute": [keys], "solo": [keys]}`, sorted, written whole (a temp file, then a rename). Entries of a track that is gone stay, so it comes back as it was; a track renamed in code (`Rekeyed`) keeps its entries. A window open read-only keeps its mutes and solos in memory only.
- *Why:* owner decision 4: mute and solo are for listening only.
- *Today:* built in 8b.4. `POST /api/graph/overlay` (`{session, mute?: {key: bool}, solo?: {key: bool}, exclusive?: key, clear?: true}`, not a write, so it works read-only) writes the cells of what plays under the control plane's lock and never waits for the session; the answer, and `overlays` in the graph state, say what is muted and soloed, which tracks are muted in the song, how each track is heard (`heard`, `muted`, `muted-in-song` or `silenced`) and whether this window saves them (`saved`). The file is read when the project opens, so the first renderer plays them from its first block; the server's `music2-tell` thread writes it after a change, off the lock. Every new plan gets the values before it is sent. An export carries `overlays.active` when any of them changes what is heard, and its file is byte-identical either way (`crates/server/src/graph/overlay_tests.rs`).

**MON-5.** "Mute in song" is saved in code and applies to every render, export included. It is a track option in `@m2/core`, so every song has it: `track("kick", { muted: true }, fn)`, carried in the IR as `Module.muted`. The planner applies it as it applies a monitoring mute ([MON-2](#monitoring-overlays-and-mute-in-song)), with the same cells and the same sidechain exception, in every render. Toggling it is a `Confined` Tx on the track call's options; the delta's `muted` change sets the cell, with a ramp and no rebuild.
- *Why:* owner decision 4 asks for a saved mute in every song. A mute that lived only in std's mixer would privilege one package (song-as-program principle 2) and leave a song without a mixer with none.
- *Today:* since 8b.4 the option is in `@m2/core` 1.2.0 (`core/script/src/mute_tests.rs`), the IR carries it, and every render starts each site of a muted track at 0 (`muted_in_song_silences_an_offline_render`). The delta reports the change as `ModuleChange::Muted` (`core/session/src/tx/muted_tests.rs`). The server takes a delta whose only module changes are `Muted` as overlay cell writes, which glide, with no new plan (`a_mute_in_song_toggle_is_a_cell_write`).

**MON-6.** A gesture, in the UI or a plugin window, on a control that a signal drives (a lane or a cable) sets an override latch. The control follows the gesture until "Re-enable" or "Write to code", and the UI marks it as latched. A latch is keyed by the ControlId of a descriptor control, or by the plugin instance and its CLAP parameter id. It persists in `.music2/` only when its whole key is saved keys (a keyed plugin's parameter: module key, frame keys, plugin key, parameter id); otherwise it lasts for the session. A latch never reaches an export.
- *Why:* a lane or a cable must not be overridden silently, and a ControlId, derived from where its calls are ([ID-13](#derived-identity)), doesn't survive a restart.

**MON-7.** Audition is not an overlay. It is a `Live(Event)` source merged into a lane's event buffer ([RENDER-14](#events)).

## PluginHost

```rust
trait PluginHost {
    // the host's main thread
    fn create(&self, id: &PluginId, state: Option<Blob>) -> Handle;
    fn activate(&self, h: Handle, sample_rate: u32, max_frames: u32);
    fn deactivate(&self, h: Handle);
    fn load_state(&self, h: Handle, blob: Arc<Blob>) -> bool;  // false: skipped, its hash equals the state the instance holds (HOME-6)
    fn set_render_mode(&self, h: Handle, mode: RenderMode);  // Realtime | Offline
    fn main_call(&self, h: Handle, call: MainCall);
    fn destroy(&self, h: Handle);
    // queued to the host's main thread; each result comes back as a message
    fn latency(&self, h: Handle);                            // -> Latency(h, frames)
    fn save_state(&self, h: Handle);                         // -> Saved(h, Blob)
    // the audio thread
    fn process(&self, h: Handle, io: &mut SharedBuffers, ev_in: &Events, ev_out: &mut Events, t: &Transport);
    fn reset(&self, h: Handle);                              // panic, and before an offline render: voices and tails cleared
}
```

As built in step 3b (`core/plugins/src/host.rs`), pending the owner's decision on the step 3b design's clarification C3, the signatures differ from the sketch:

```rust
trait PluginHost: Send + Sync {
    // the host's main thread; the caller waits (inline on the main thread itself)
    fn create(&self, plugin: &Found, state: Option<Arc<Blob>>, owner: &Owner) -> Result<(Handle, Info)>;  // init, state load, ports and params
    fn activate(&self, h: Handle, sample_rate: u32, max_frames: u32) -> Result<u32>;                  // -> latency, after the state load
    fn deactivate(&self, h: Handle);                                 // only while no renderer calls it, or every one that does is held (RENDER-1)
    fn load_state(&self, h: Handle, blob: Arc<Blob>) -> Result<bool>;  // skipped (false) when its hash equals the state the instance holds:
                                                                     // last saved or last loaded, creation included; none after a failed load (HOME-6)
    fn set_render_mode(&self, h: Handle, mode: RenderMode) -> Result<bool>;  // before activating; offline for every render that isn't live (RENDER-1)
    fn main_call(&self, h: Handle, call: MainCall) -> Result<Reply>;  // a parameter's value or text, its info, its log
    fn destroy(&self, h: Handle);                                    // queued: never waits
    // queued to the host's main thread; the one result comes back on the reply each returns
    fn latency(&self, h: Handle) -> Pending<Result<u32, String>>;
    fn save_state(&self, h: Handle) -> Pending<Result<Blob, String>>;
    // the audio thread (or an offline render's): never allocates, locks or waits
    fn process(&self, h: Handle, io: &mut SharedBuffers, ev_in: &Events, ev_out: &mut Events, t: &Transport) -> Status;
    fn reset(&self, h: Handle);
    fn take_process_request(&self, h: Handle) -> bool;               // CLAP's request_process: wakes an idle engine
    // any thread
    fn live(&self) -> u64;
}
```

- `create` returns the `Info` the checker types a plugin from, so describing a plugin is `create`, `activate`, `destroy`, with no second path around the host. It takes an `Owner`: where the instance's unsolicited events (`Restart`, `Dirty`, `Latency`) go, and the count of its live instances, so two sessions in one process never see each other's events.
- `latency` and `save_state` answer as one message on their own reply, which no other waiter can take.
- `Events` is the host's CLAP-shaped list, sized when built (`m2-plugins` can't depend on the runtime's `Event`); the runtime translates into it without allocating.

**HOST-1.** The engine MUST reach plugins only through `PluginHost`, and call each method only on the thread named beside it. Nothing may assume a plugin shares the app's process or threads.
- *Why:* plugins will move into a host process, and the threading model must not be built twice. CLAP needs `activate` with the rate and block size to apply a latency change, and calls `latency` and `save_state` on the main thread only.
- *Today:* matches since step 3b. The runtime's plugin nodes hold an `Arc<PluginInstance>` (a handle and its host) and call `process` and `reset` through the host; renderers create instances, `PackageSet::describe_plugins` describes them and `m2 plugin-state` saves them through `PackageSet::host()`, which is the process's in-process host unless set (`m2_plugins::host()`). `m2_plugins::Instance` is gone.

**HOST-2.** The in-process implementation (step 3) MUST make every main-thread call on the plugin main thread below, and process plugins on the audio thread. That plugin main thread runs the OS's main loop (`m2_os::main_loop`). On macOS, where plugins post work to the process's main run loop, it is the process's main thread: in the app AppKit's, reached through the main dispatch queue; in the CLI, the headless server and the gates, the main thread runs a `CFRunLoop`. On Linux, where plugins get main-thread time only from the host (CLAP's fd and timer extensions), it is the process's main thread in the CLI, the headless server and the gates, and in the app a loop thread of its own, since GTK owns the app's main thread. The host's thread checks answer truthfully, and `on_main_thread` runs on that thread, never inside `process`. The host process ([HOST-3](#pluginhost)) keeps the same rule inside itself.
- *Why:* plugins kept alive across rebuilds turn today's threading violations into crashes. Many commercial plugins (JUCE-based ones among them) post timers and work to the process's main run loop, so a separate "plugin main thread" would give them two main threads that race. The cost on macOS: until the host process ships, a slow plugin load blocks the app's main thread. Linux has no process-wide run loop for plugins to post to, so its app keeps plugins off GTK's thread.
- *Today:* matches since step 3b (`core/plugins/src/main_thread.rs`, `inprocess.rs`, `audio.rs`):
  - every main-thread call (create, init, state, activate, parameters, `on_main_thread`, deactivate, destroy) runs on the plugin main thread; callers on other threads wait for it, and `destroy` is queued. Libraries load on the calling thread, once per bundle, never on the main thread;
  - the app calls `m2_plugins::use_app_main_thread()` first thing in `main` (`plugin_host::install`, `apps/music2-desktop/src/main.rs`): AppKit's main thread through the main dispatch queue on macOS, a loop thread of its own on Linux (`tests/app_main_thread.rs` runs this hook on both). The app opens its launch project off the main thread, which must never wait on a thread that creates plugins. Its quit closes the project first (`Graph::close`), waiting up to 2 s while the main thread destroys the instances, and leaves without exit handlers when some are still alive (`apps/music2-desktop/src/actions.rs`). On Linux the check's app row runs the open inside the app, with the test plugins; on macOS neither has run inside the app, and quit's close has run in neither;
  - `m2`, the headless server example and the gates binary run under `m2_plugins::run_main`: the program on a worker with an 8 MiB stack, the main thread running the OS's main loop (a `CFRunLoop` serving the main queue on macOS, a job queue on Linux); on return it serves until every instance is destroyed (2 s at most), then refuses further work. Tests, where libtest owns the main thread, opt in to one dedicated thread instead (`m2_plugins::test_main_thread()`); nothing falls back silently: with none installed, creating a plugin is an error naming what to call. Using a dedicated thread in tests is the step 3b design's clarification C1, awaiting the owner's decision; `core/plugins/tests/main_thread.rs` (no libtest harness) runs the real one, with Surge XT when `CLAP_PATH` has it;
  - `is_main_thread` asks the executor (`m2_os::main_loop::Loop::is_current`: `pthread_main_np` for macOS's main thread, else the loop thread's token); `is_audio_thread` holds when the caller holds the instance's audio role, which `process` and `reset` take and the main thread takes only to `stop_processing` before deactivating. No thread-local is touched, so the audio thread never allocates for one;
  - a plugin's requests (`request_callback`, `request_restart`, `latency.changed`, `mark_dirty`, `params.rescan`) only raise flags; every 5 ms a tick thread has the main thread sweep them, so `on_main_thread` never runs inside `process`, and the rest goes to the instance's owner.

**HOST-3.** The host process, before plugin windows ship, uses shared-memory audio and event rings, message-based main-thread calls and its own main loop for windows (`m2_os::main_loop`: AppKit's on macOS; on Linux a loop over the X connection, the plugins' fds and timers, serving CLAP's `posix-fd-support` and `timer-support`). When it crashes, the affected instances become silence with `plugin.crashed`, and the app keeps running.
- *Why:* one plugin crash must not take down the session.

**HOST-4.** Plugin output events (parameter gestures) MUST come back through `ev_out`, to an override latch, a literal Tx or automation recording.
- *Today:* collected since step 3b, not yet consumed: each plugin node keeps what its last call output (parameter values, within 256 events; the rest counted), and `Renderer::plugin_out_events` counts them. Latches, the literal Tx and recording come with plugin windows.

**HOST-5.** Plugin instances persist across plans like every instance ([RENDER-25](#plans-data-and-arrangement-swaps)), by RuntimeId ([ID-15](#derived-identity)) and shape (id, version, channels). A state change is loaded into the instance ([RENDER-26b](#plans-data-and-arrangement-swaps)). An instance that asked for a restart is new at the next activation, created from the committed blob. So is one that failed live, which plays silence until then. Offline renders in the app share the live instances ([RENDER-1](#offline)); the CLI creates its own.
- *Today:* matches since step 7 (`continues` in `core/session/src/tx/continues.rs`, `Shape::Plugin` in `core/runtime/src/plan.rs`): a keyed plugin follows its key, wherever its call is; an unkeyed one keeps its instance by its name, which a wrap keeps ([ID-13](#derived-identity)), and one given a key continues by its name too. The shape doesn't hold the state: a changed blob is loaded into the kept instance ([RENDER-26b](#plans-data-and-arrangement-swaps)), and a blob taken away makes it new. A restart request (`HostEvent::Restart`) puts the instance in the actor's `Open.restarts`, and the catch-up activates at once with it new. A plugin that fails live (a processing error, or no activate after an export) is marked failed on the audio thread (`PluginInstance::kill`): its node plays silence and never calls it, the renderer plays on, and the session puts it in `Open.restarts` and says so (`a_plugin_that_fails_live_goes_silent_alone` in `core/runtime/src/tests/live/keep/plugins.rs`). One whose new instance fails within 10 s too is left silent, said once, until the song is opened again, so a plugin that fails at every call isn't made again every 300 ms (`Open.revived`, `a_plugin_that_keeps_failing_is_started_again_once` in `crates/server/src/graph/tests.rs`). Offline, a plugin's error still fails the render. Only an activation in the same engine keeps instances: a new player or a rate change creates every one. The app's export borrows the live instances while playback is held ([RENDER-1](#offline)); `m2 render`, `m2 bounce` and range renders create their own. The last plan holding an instance drops it off the audio thread, and its destruction is queued to the plugin main thread.

**HOST-6.** Plugins get the transport from the engine: the playing and loop flags, tempo, the meter from the arrangement, a transport event at the frame of every jump, and `steady_time` from the engine clock.
- *Today:* matches since step 3b. A plugin is called once per run of a block, so a call never spans a jump, and each call carries its run's transport: playing or not, the loop, the tempo, the meter and bar from the arrangement, and its song position; `steady_time` is the engine clock (`PluginNode::process` in `core/runtime/src/lib.rs`, `transport_event` in `core/plugins/src/audio.rs`). Tested by `plugins_are_told_the_transport` (`core/runtime/src/tests/live/keep/plugins.rs`), with the probe recording what each call was told: playing and stopped, the loop across a mid-block wrap (two calls, each told its own run), the tempo, a 7/8 meter and its bar, and `steady_time` against the engine clock.

**HOST-7.** Plugin windows, VST3 and AU MUST be built only behind `PluginHost`.

## Kernel ABI reservations

**ABI-1.** Kernel input memory is host-owned and read-only to kernels: `k_process` MUST NOT write it, and `k_reset` MUST NOT change it. Debug builds hash input memory after each process call and fail on a change. This holds for ABI v0 now.
- *Why:* cells are written once ([RENDER-22](#cells)).
- *Today:* matches since step 5. ABI v0 states it (`std/kernels-src/kernel/src/lib.rs`), and the Rust kit keeps it by construction. A kernel whose port buffers overlap is refused when it is instantiated, in every build, since one port's writes would change another's. Debug builds compare each kernel's input memory before and after every `k_process` and `k_reset` call (a copy and a compare rather than a hash: cheaper, and exact), and a change fails the render naming the kernel and the input (`KernelNode` in `core/runtime/src/lib.rs`); a test plays every std kernel through it (`every_std_kernel_keeps_its_inputs`).

**ABI-2.** Kernel ABI v1 reserves, without building yet:
- event-in and event-out ports, carrying buffers of [RENDER-14](#events)'s `Event`, of which `Events<Note>` is a filtered view;
- read-only asset blobs given at init (samplers, impulse responses);
- channel counts per port;
- state save and load;
- latency and tail queries;
- offline kernels: whole buffers in and out, with a time map (where clip stretching moves, out of `core/runtime/src/audio.rs`).
- *Why:* the sampler, arpeggiators and third-party kernels all need these, and their shape must not collide with v0.
- *Today:* events can't feed a kernel (`core/ir/src/check.rs:731-732`); kernels can't read assets.

**ABI-3.** Any reserved feature that ships bumps `m2_abi()` to 1. The runtime refuses a module built for another version.
- *Today:* matches for v0 (`core/runtime/src/packages.rs:247-279`).

**ABI-4.** The IR reserves a `const-events` op for events generated by code (`notes([...])`, `euclid()`, a seeded rng). The rule that build code never reads lane data stays.
- *Why:* owner decision 7: room now, built later.

## Platforms

**PLAT-1.** music2 MUST build and pass every check on macOS on Apple silicon (the reference platform: judged timings, the look, native menus) and on Linux x86_64 with the glibc it was built against (the development platform). Windows is designed for in every OS piece and built in its own step. Timings are judged on the [reference Mac](#acceptance-gates) only; other machines run the same gates and record their timings with the machine named.
- *Why:* the work moved to a Linux server; the Mac stays where music2 is used and timed.
- *Today:* since the platform step: Linux on the development server, macOS by the owner's run of `ci/check.sh`. Linux passes every check from that step's slice S8 ([PLAT-6](#platforms)).

**PLAT-2.** Rust code that differs between operating systems MUST live in the `m2-os` crate (`core/os`). Outside it, Rust code other than tests MUST NOT name an OS: no `cfg` on the OS, no `libc`, no `std::os`, no `extern "C"` block, no `$HOME`. The desktop shell (`apps/music2-desktop/src`) and the gates' fault injection are the exceptions. Tests may use OS-only fixtures under `cfg`. The web UI differs only in its keys and labels (⌘ or Ctrl, "Show in Finder" or "Show Folder"), each asked of `isMac` in `web/src/lib/native.ts`.
- *Why:* one place per OS to read, port and check; later steps write each OS piece once.
- *Today:* since the platform step's slices S5, S6 and S8: `m2-os` holds thread identity, the plugin main loop, the disk calls, the lock, the machine's identity, the folders and file-system events, and `core/os/tests/one_place.rs` checks the rule, with an empty allow-list.

**PLAT-3.** `m2-os` MUST do what the OS does, with the strongest call the volume accepts (`F_FULLFSYNC`, else `fsync`), or return `Unsupported` naming what. It never emulates: no copy for a clone, no compare-then-rename for a swap, no walk for events. Those fallbacks and their rules stay with the caller.
- *Why:* an emulation hidden in the OS layer would change a rule's meaning on one OS without the rule saying so.
- *Today:* since the platform step's slices S5, S6 and S8, for what `m2-os` holds (thread identity, the plugin main loop, the folders, the disk calls, the lock, the machine's identity, file-system events). The watcher's walks and its limit on names stay with it (`crates/server/src/graph/events.rs`, `watcher.rs`).

**PLAT-4.** A pure offline render MUST give the same bits on every supported OS and CPU. Host code that makes audio for a render, and song code run by QuickJS, MUST compute every transcendental function with the `libm` crate, the same code as `std.wasm`'s math. One record of render hashes serves every OS (`core/session/tests/renders.json`, `e2e/renders.sha256`).
- *Why:* an export must not depend on whose computer made it. Each OS's math library rounds some results differently in the last bit (glibc against `libm`: 0.04% to 9.7% of inputs, measured).
- *Today:* since the platform step ([RENDER-2](#offline)).

**PLAT-5.** `std/kernels/std.wasm` MUST rebuild to the same bytes in any folder on any supported OS with the toolchain `rust-toolchain.toml` pins, and hold no machine path. A commit that changes it says that the kernel hashes changed.
- *Why:* a kernel's hash is part of its identity ([RENDER-25](#plans-data-and-arrangement-swaps)); a rebuild must never change it by accident.
- *Today:* since the platform step: `m2-kernel` is a member of the kernels' workspace, and `std/build.sh --check` rebuilds it in another folder and compares.

**PLAT-6.** `ci/check.sh` is the full check, the same script on Linux and macOS: the build, every Rust test, clippy with warnings denied (on Linux also for the macOS target), the desktop app's tests, the web build, every browser suite, std's tests and rebuild, and the offline renders against `e2e/renders.sha256`; on macOS also the timing gates `ci/gates.txt` names. A check passes only with the test plugins present ("PASS without plugins" is not a pass). Every slice passes it on Linux. The owner runs it on a Mac at the end of each step, and before a branch that changes macOS-only code is merged. Until it passes there, the step's commit message and `HANDOFF.md` say "macOS: unverified since <commit>".
- *Why:* there are no hosted Mac runners; the owner's Mac is checked by hand, as rarely as is safe.
- *Today:* since the platform step. Linux passes it since that step's slice S8, first at `9f0b19a` (twice, with no retry); before S8 it failed only where `docs/designs/platform/design.md` §13.1 said a later slice fixes it. On Linux it also opens the desktop app on an invisible Xvfb screen. At the step's end Linux passed it at `63c45da`, with no retry, and both passed at `1750322`: the owner's Mac (MacBookPro18,1, macOS 26.6.2) on its second run, the gates included; its first run, at `b90bacf`, failed two tests that assumed Linux.

**PLAT-7.** Every folder music2 writes outside a project (songs, caches, the shell's `~/.music2`) MUST be under `$HOME` when `HOME` is set, so a test or a suite isolates itself by setting `HOME`. Outside the desktop shell those folders come from `m2_os::dirs`. Folders music2 only reads (the system's CLAP folders, files bundled with the app) are exempt. A new song's folder name MUST count as taken when its folder holds the same name in other capitals, on every OS, as on macOS: New Song numbers past it (a song called "Night drive" beside a folder `NIGHT DRIVE` goes into `Night drive 2`), and `m2 new` refuses it ("already exists").
- *Why:* a test must never write to the user's real folders. Song folders stay safe to copy between computers (the owner's answer to the platform design's Q1).
- *Today:* every such folder is under `$HOME`; they come from `m2_os::dirs` since the platform step's slice S6, which also moved Linux's cache folder from `~/Library/Caches/music2` to `~/.cache/music2`. `XDG_*` folders are not read yet. A name in other capitals is taken by New Song since slice S2 and by `m2 new` since S6 (`crates/server/src/project.rs`: `a_name_taken_in_other_capitals_is_taken`, `create_at_refuses_a_name_taken_in_other_capitals`). In a folder that can be written but not listed only the exact name can be checked (`a_song_is_made_in_a_folder_that_cant_be_listed`).

## Order of work

Steps 3 and 4 may run in parallel; everything else is in order.

1. **Close today's silent paths** (2 days). **Built.**
   - The session's warnings reach every client: the app's state and every graph event over the WebSocket carry them, the app shows them in a "Needs attention" strip, and every CLI command that opens a project prints them with the commands that fix them ([DIAG-4](#delivery)).
   - Lane data no lane reads, left behind when a track or a lane is renamed in code, is the Warning `data.unclaimed`, with Relink and Delete fixes: `m2 relink`, `m2 delete-data`, and the strip's Move and Delete. Each fix is a checked, undoable session edit, applied only when asked ([DIAG-6](#fixes)).
   - `revert()` uses the current origin of the control at the carried position, with the regression test ([ID-12](#derived-identity)).
2. **Write the contract** (this page) and have it reviewed.
3. **Live step A** (2–3 weeks). **Built.** Land 3a before 3b, and keep the offline path untouched.
   - **3a, runtime (built):** the engine and transport clocks, with the engine running while stopped; an integer transport and loop ends computed from beats; lane schedulers that fill event buffers and own their sounding notes; a jump that never resets kernels; a new renderer activated at the audio thread's own position, with a 5 ms crossfade; `SwapLane` for notes and control lanes when the old and new `Flat` graphs are equal; the range render for agents.
   - **3b, around the runtime (built):** gesture leases that survive saves which don't touch them; the session as an actor; `PluginHost` with its whole trait and the in-process executor on the real main thread; plugin instances carried across rebuilds.
4. **Format v1 and SDK keys, in one change** (1–2 weeks). **Built.**
   - Track, lane and plugin keys, and `key()` frames; `Module { key, label }`; a context that exposes the key, never the label.
   - `data/<module>/` with clip ids and lane units; the manifest with `format` read first, `sample_rate`, and caret requirements for every dependency; the live engine at `sample_rate`.
   - `DataPath` and its classes; snapshots that read the explicit set, and a build that imports only from them; the canonical form of data files, written in `core/song`; the arrangement and meter rules.
   - Per-lane data errors that keep the last accepted data; the asset hash cache and pins, so compile no longer decodes audio; asset names; plugin parameters addressed `<name>_<id>` and bound by id; `plugin.missing`; required state sidecars; the diagnostic model, with fixes still named session edits.
   - Convert the 5 fixtures by script, then delete `slug()`.
5. **Descriptors and cells** (about 2 weeks). **Built.**
   - `component()` with declared inputs, controls, settings, defaults and editor metadata, sidechain ports and smooth controls; std rewritten on it.
   - One const per declared control with an `(instance, slot)` origin; ComponentIds in frames; the unit table generated from `core.ts`; runtime cells, written through per-cell slots, ramped where declared.
   - Delete `[[effect]] args`, `EFFECT_CATEGORIES`, the `cable.rs` unit table and the `view.rs` range guesses.
6. **Tx and the write path** (about 3 weeks, then 1 week of mechanical moves). **Built.**
   - The `save`/`Tx` split, with validated paths, the `Clips` op and base texts; the project lock (no forwarding), its read-only open and `lock.unsupported`; content-hash bases.
   - `GraphDelta` with node names an insertion can't shift, and `Identical`, `Values`, `Confined` and `Seen`; the journal, with host names, staging in `.music2/tx/`, and recovery as a diagnostic.
   - `(code_rev, data_rev)`, and a data-only path that skips QuickJS, chosen by path class; the watcher's settle rule; `data.claimed` from Tx.
   - `Session::open` on a broken draft.
   - Port the 7 gestures, step 1's two fixes and the bypasses; fixes become Tx; delete the guess at `graph.rs:341-348`; make `write_whole` private.
   - First new builders: Relink of a whole module folder, rename label, automate a knob. Then the move into `crates/editor`.
6b. **The platform layer** (about 2 weeks). Development moved to a Linux server, so Linux is made green there first, natively, and the Mac stays green. **Built** when its gates pass.
   - `m2-os` (`core/os`), one folder per OS ([PLAT-2](#platforms)): renames and the durable sync, the lock and machine checks, file-system events (FSEvents, inotify), the plugin main loop, the folders.
   - The same render bits on every OS through `libm` ([PLAT-4](#platforms)); a reproducible `std.wasm` and a pinned toolchain ([PLAT-5](#platforms)); saves that a crash can't break on volumes without an atomic exchange, and new audio made durable before a song names it.
   - One check script for both OSes, `ci/check.sh`, run by hand on the owner's Mac, timing gates included ([PLAT-6](#platforms)).
   - Steps 8a and 9 add their OS pieces to `m2-os`; Windows is designed for in each piece and built in its own step.
7. **The engine** (4–6 weeks). **Built** on Linux; done once the owner's Mac run passes.
   - `Plan` split from `DataSet`; SiteId matching, InstancePath and RuntimeId.
   - The arena, with prepare and activate, keeping instances whose RuntimeId and shape (wasm hash included) match.
   - Arrangement switches prepared off the audio thread; persistent CLAP instances behind `PluginHost`, with state loads into them as a plan is prepared, and offline renders that reuse them.
8. **Partitions, then producer features.**
   - **8a:** parallel partitions on a thread pool, right after the arena, with renders that don't depend on the thread count.
   - **8b:** each a Tx builder or an engine feature on this base: add, duplicate, delete and rename track; the mixer with monitoring mute and solo plus the `muted` track option; automate a knob; the tempo bar, with its lease; clip editing by id, with lane leases; audition.
9. **After the core,** synth and plugin turns alternate with audio and sample turns:
   - synth and plugin: the plugin host process, then plugin windows (with state autosave and output events), then latency compensation, then mono, legato and glide, then MIDI input;
   - audio and sample: disk streaming, then kernel ABI v1 and the sampler, then stretching as an offline kernel, then recording.

   TypeScript package tools and the other deferred items come in when their triggers arrive.

## Acceptance gates
