# m2-gates

Measures step 3's acceptance gates ([architecture contract](../../docs/architecture.md#acceptance-gates)), as step 3a's design lays them out (its §15): seeks, a 10-minute loop, note edits, stuck notes, added effects, crossfades, tails after stop and range renders. Each gate plays a song, does what the gate names, and judges what it heard. It prints every number, so a recorded run is also the record.

Step 3b's two server gates are here too, through the server only: previews never wait on a compile (G8), and an outside save during a drag doesn't interrupt it (G9); and step 6's data plane, journaled lane writes from the request to the block that plays them (G11, `tx-data`), and its watcher of outside writes (G11, `watcher`); and step 7's export with plugins, which pauses playback and borrows their live instances (G7e, `export`). RENDER-33's bit-identity test, the allocation trap and the offline byte-identity check aren't here: they belong to the engine's own tests.

## Run it

```bash
# Step 3a's live engine, at CI sizes: a 3-track reference project, 1 minute of loop, 8 seeks.
cargo run -p m2-gates --release --features engine -- --quick

# The recorded run on p16: 10 minutes of loop, 50 seeks. Run it twice, as the design asks:
cargo run -p m2-gates --release --features engine           # the release build
cargo run -p m2-gates --features engine                     # the dev build `cargo run -p music2-desktop` makes

# The same gates on HEAD's engine, which replays: the negative reference.
cargo run -p m2-gates --release -- --rig replay --quick

# Seek, note edit, add effect, and step 3b's knob drags (G8, G9) through the app's server, in real
# time on the silent player.
cargo run -p m2-gates --release -- --server

# The with-plugins gate, Surge XT and Airwindows found where CLAP_PATH says (never the user's own folder
# by default in CI), and its negative reference: no instance kept across an activation.
CLAP_PATH=~/Library/Audio/Plug-Ins/CLAP cargo run -p m2-gates --release -- plugins --quick
CLAP_PATH=~/Library/Audio/Plug-Ins/CLAP cargo run -p m2-gates --release -- plugins --quick --no-arena

# Step 7's recorded runs on p50 from 3:00: G7a through the server, its engine-rig twin, G7b, and G7e,
# an export of with-plugins that pauses playback and borrows its plugins.
cargo run -p m2-gates --release -- --server --reference 50 --at 180 add-effect
cargo run -p m2-gates --release --features engine -- --reference 50 --at 180 add-effect tails
CLAP_PATH=~/Library/Audio/Plug-Ins/CLAP cargo run -p m2-gates --release -- --server export

# G7f's two parts: what one wasmtime Store per kernel instance costs a block, then what step 7 costs
# the callback, each against S (HEAD 8aa301e, the commit before step 7) measured in the same run, in
# 5 rounds of the app's layout, its A/A control and S taking turns: each part about 8 minutes on the Mac (an
# estimate). S plays in a runner of its own, built once from a clean copy of S (s/README.md).
export M2_GATES_S=$(crates/gates/s/build.sh | tail -1)
cargo run -p m2-gates --release -- store --reference 50
cargo run -p m2-gates --release -- arena --reference 50 --at 180

# G12's offline part (8a): p50 rendered on 1, 2, 3, 4, 6 and 8 threads against one; the same
# bits on each, and the pure fixtures matching e2e/renders.sha256 (judged). About 10 minutes.
cargo run -p m2-gates --release -- realtime --offline

# G12 live (8a's live half): p50 plays on the player's engine threads at 128 frames, muted. On a
# Mac on its output device (judged), elsewhere on the silent clock (information). One minute, as
# ci/gates.txt runs it; the owner's sweep and 10-minute run are ci/sweep.sh.
cargo run -p m2-gates --release -- realtime --reference 50 --minutes 1

# G13 (the agents design's track 5): G12's live run of p50 while agents work beside it: `m2 listen`
# back to back on its bars, and `m2 set` edits forwarded to an app that has it open. Build m2 first
# (it runs the m2 beside m2-gates). One minute, as ci/gates.txt runs it.
cargo build --release -p m2 && cargo run -p m2-gates --release -- realtime --reference 50 --minutes 1 --beside agents

# One or more gates by name; p50 or the audio-heavy p16 instead of p16.
cargo run -p m2-gates --release --features engine -- seek loop --reference 50
cargo run -p m2-gates --release --features engine -- add-effect --stems 4
```

`--help` lists every option. The first line of every run says which build measured: timings from a dev and a release build differ several times over, and the gates must pass on both. The second line names the machine (`m2_os::process::machine()`): only the reference Mac's timings are judged, and a record (`store-S.txt`, `callback-S.txt`) is used only on the machine it names, whatever its OS version (PLAT-1). G7f measures S in the same run, but the machine lines of `store-S.txt` and `callback-S.txt` still say which Mac judges it: on any other machine its timings are printed, not judged, and on a Mac they also say what to do if it is the reference Mac now. So keep both records, machine lines and all.

Projects are generated into a new folder under the temp dir and removed afterwards (`--work DIR` and `--keep` to look at them). Nothing reads `~/.music2` or `~/Music`, and nothing plays on a device: the binary sets `M2_AUDIO=none` before anything starts, and `M2_AUDIO_FRAMES=512` unless it is set.

The binary runs under `m2_plugins::run_main` (HOST-2): the gates on a worker thread, the process's main thread serving plugins as their main thread, as `m2` does. The harness tests serve them from one dedicated thread (`m2_plugins::test_main_thread()`).

The exit code is 0 when no gate failed, 1 when one did, 2 when a gate couldn't run.

### Features

- `engine`: step 3a's live engine (`m2_play::Player::driven`, `activate`, `swap_lane`, `Renderer::starting_at`).
- `range`: the session's range render (`Render::range`, and `Rendered::exact` and `reproducible`), for what G10 checks that a range render says about itself. It turns on `engine`.

Both are on by default now that step 3a has landed, so `cargo test --workspace` also runs `the_live_engine_passes_every_gate`. `--no-default-features` builds the harness without them.

## The reference projects

p16 and p50 are generated, never checked in, by `m2_session::reference` (`core/session/src/reference.rs`): tracks cycling std `bass` with `delay`, `pluck`, and `pad` with `reverb`, each playing `examples/first-song`'s notes repeated to 512 beats (4:02 at 127 bpm). `--stems N` adds N one-minute stereo WAVs on audio lanes, every second one warped. To write one by hand:

```bash
cargo run -p m2-server --example reference -- /tmp/p16 --tracks 16 [--stems 4]
```

## Rigs

A gate drives a rig: an engine filled a device buffer (512 frames) at a time, in simulated time, so a run never waits for a clock.

- **engine** (`src/engine.rs`) is the live engine through `Player::driven`, fed what the server feeds it: a plan prepared against the one last sent (what continues named by the session, `m2_session::tx::continues`) and activated, or for a data edit that leaves the graph as it was, `SwapLane` for each notes or control lane that changed. `--no-arena` prepares against nothing that continues: every instance new and the whole old graph a ghost for the window, the negative reference for every check the arena exists for. Its kernel-reset count is the engine's (`Engine::resets`), which counts every reset of a renderer's graph where the graph resets, so a jump that reset kernels would move it; what an activation kept and made is its plan's `Stats` (`Rig::arena`), and a node's last block its tap (`Rig::output_of`).
- **replay** (`src/replay.rs`) is HEAD's engine as the app drives it at `0ff97b4`: every seek and edit builds a new renderer and replays the song to the playhead, the player swaps it in at its next buffer, and stop outputs zeros without processing. It loops by replaying at each wrap, at the frame the wrap's beat gives, so it never drifts. It must fail the gates step 3 exists for; a gate that passes on it measures nothing. `tests/harness.rs` checks that it does.

Work done off the audio thread (building a renderer, preparing lane data, replaying) is timed on the wall clock. While it runs the device plays on for as many frames, so an engine that builds at the position it read first jumps back by that much (RENDER-8).

**Latency** is counted as the design counts it: the wall time spent preparing after the compile (which every budget leaves out), then the frames until the engine applied the change, then one 512-frame device buffer (10.7 ms at 48 kHz), which is counted, not subtracted.
