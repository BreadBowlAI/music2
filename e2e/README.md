# e2e: browser suites for the music2 UI

In short: each suite drives the real web UI in headless Chrome against the **headless server**
(`crates/server/examples/headless.rs`), on a fresh copy of a fixture and a scratch `HOME`, and
prints one `PASS`/`FAIL` line per check. Nothing reads or writes the real `~/.music2` or `~/Music`.

## Running

```sh
(cd e2e && npm ci)                   # puppeteer-core 24.43.1 (no browser download)
(cd e2e && node_modules/.bin/browsers install chrome-headless-shell@133.0.6943.141 --path ~/.cache/puppeteer)
                                     # the browser, once (as ci/check.sh gets it)
cargo build --locked -p m2-server --example headless && cargo build --locked -p m2   # the server; the CLI for `export`
(cd web && npm ci && npm run build)  # the server serves web/dist

M2_HEADLESS=target/debug/examples/headless node e2e/run.mjs graph        # one suite
M2_HEADLESS=target/debug/examples/headless node e2e/run.mjs start empty  # one suite, another fixture kind
M2_HEADLESS=target/debug/examples/headless node e2e/run.mjs all          # every suite, each on a fresh server
M2_HEADLESS=target/debug/examples/headless node e2e/run.mjs all --jobs 4 # the same, 4 at a time (ci/check.sh on Linux)
M2_HEADLESS=target/debug/examples/headless node e2e/run.mjs all --tier pr --shard 1/2 --jobs 2
                                     # half of the PR tier's runs, 2 at a time (one CI job; ci/pr.sh suites 1/2)
CLAP_PATH=~/Library/Audio/Plug-Ins/CLAP M2_HEADLESS=target/debug/examples/headless node e2e/run.mjs all
                                     # the same, with live3b's plugin part (Surge XT, Airwindows) included
```

- `--repo <checkout>` is where `examples/first-song` is copied from (every kind's `<root>/proj`). The
  suites that copy an example themselves get it as `E2E_REPO`: `live3b` copies
  `examples/with-plugins`, `fx-fixes` another `examples/first-song`. Default: this repo. It does
  **not** change what the server serves: `web/dist`, `std`, `templates/` and the projects behind
  the start screen's **Examples** come from the source tree the headless binary was compiled in (its
  `CARGO_MANIFEST_DIR` is built in; `M2_STD`, `M2_TEMPLATES` and `M2_EXAMPLES` override the last
  three, and `run.mjs` passes your environment on). So `newsong` and `fx-fixes` test the binary's
  templates whatever `--repo` says. Use the checkout the binaries were built from; `run.mjs` prints a
  note when the binary wasn't built in `--repo`.
- `--out <dir>` keeps the logs (and, with `--keep`, the scratch folders) there; by default a new temp
  folder, printed at the end. The scratch folder of a run that wasn't `ok` is always kept.
- `--jobs <n>` runs up to `n` suites at once (default 1, one at a time). Each still gets its own
  server, scratch `HOME`, folder and browser. See "In parallel" below.
- `all` prints one line per suite, in the list's order whatever the order they finish in, with how
  long each took; then a total, and the time of the whole run. A run is `ok` only when the suite exited 0, printed no
  `FAIL` and no `SKIP` line, and passed exactly the number of checks `run.mjs` expects of it (the
  `expect` counts in its `SUITES`, the same as the table below). A run that passed but printed a
  `SKIP`, or passed another number of checks, is `PART`, and the total says why: part of it didn't
  run (live3b without `CLAP_PATH`), or the suite changed and its count in `run.mjs` and here must
  follow. Exit status: 0 when every run was `ok`, 1 when any failed, 3 when none failed but some
  were `PART`.
- `M2_CLI` is the `m2` binary for `export` (default: `<headless dir>/../m2`). `E2E_CHROME` overrides
  the browser (default: puppeteer's cached `chrome-headless-shell` 133.0.6943.141 for this OS). Off
  the Mac the suites start it through `chrome-as-mac.sh`, which gives pages a Mac user agent, so they
  test the Mac's keys on every OS (`chrome.mjs`). `E2E_TIMEOUT` (seconds, default 600) bounds a suite.
- The probe plugin: only `br-plugins` and `br-presets` get `M2_PROBE=1`, so their debug server installs the built-in test plugin.
- Hosted CLAP plugins: only `live3b` and `ph-window` get `CLAP_PATH`, and only when you set it. There is no
  default, so your own plugin folder is never used unasked; `CLAP_PATH=~/Library/Audio/Plug-Ins/CLAP`
  uses it. Its with-plugins part needs Surge XT and Airwindows Consolidated in that folder. Without
  them, live3b skips those 20 checks with one `SKIP` line and passes 40 of its 60, ph-window skips
  all of its 9, and `run.mjs` reports each `PART` (with a note at the start when `CLAP_PATH` isn't
  set). Every other suite runs **without** `CLAP_PATH`; `fx-fixes` must.
- Plugin windows: `ph-window` opens Surge XT's own window. On Linux it starts an invisible Xvfb of
  its own for it (never your screen; `E2E_DISPLAY` names another), and skips without Xvfb; on macOS
  the window flashes up on your screen for a moment.
- MIDI: every suite's server and the suite itself get `M2_MIDI=inject`, so no server opens a MIDI
  device, and `POST /api/graph/midi/inject` plays what a keyboard would send. Sound input: they get
  `M2_AUDIO_INPUT=inject` and `M2_AUDIO_INPUTS="Test mic,USB mic"`, so `POST /api/graph/input/inject`
  plays what a microphone would (io-record). A suite that starts
  a server of its own gives it `M2_MIDI` too (`none`, or `inject` for `nx-midi`).

Fixture kinds (what `run.mjs` prepares in `<root>`, and the suite's arguments):

| kind     | server opens              | suite gets                               |
|----------|---------------------------|------------------------------------------|
| `proj`   | `examples/first-song`     | `<root>` (`<root>/proj`, `<root>/testhome`) |
| `cables` | `fixtures/cables` (one-file song) | `<root>` (`<root>/cables`)         |
| `fix`, `attn` | `examples/first-song` | `<root> <home> <project>`               |
| `empty`  | nothing (start screen)    | `<root> empty`                           |
| `none`   | nothing, scratch HOME     | `<root> <home>`                          |
| `export` | `examples/first-song`     | `<root> <home> <project> <m2 cli>`       |

`<root>` also holds `orig-song.ts`, `keys-orig.ts` (and `cables-orig.ts`): the fixture's files as
they started, which suites compare edits against.

### In parallel (`--jobs`)

In short: `--jobs 4` runs the suites 4 at a time and gives the same answer as one at a time, in about
3 minutes instead of 11 on the Linux server. The suites share nothing but the machine.

- The results are the same as at `--jobs 1`: the same line for each run, printed in the list's
  order, the same counts, the same `ok`/`PART`/`FAIL` rules and the same exit status. Anything that
  goes wrong in one run (the server or the suite can't start) fails that run, not all of them.
- `ci/check.sh` runs `all --jobs N` on Linux (N is a quarter of the machine's threads, 1 to 4: 4 on
  the server), and then runs each run that failed once more, alone,
  with nothing else of `run.mjs` running: the same retry as before, so "passed only on a retry"
  means what it meant. On a Mac it runs one at a time, as before, until a Mac run shows the suites
  hold at 4 (`M2_CHECK_JOBS=4 ci/check.sh` tries it).
- A suite marked `serial: true` in `run.mjs`'s `SUITES` (with the reason in a comment) runs after
  the others, alone. None needs it at present.

What the suites could have shared, and why they don't (checked 2026-10-20):

| what | how each run keeps its own |
|------|----------------------------|
| ports | every server listens on port 0 (the OS picks a free one) and writes its URL to its own session file; Chrome's debugging port is 0 too (puppeteer's default) |
| the session file | `<run>/testhome/.music2/session.json`; a suite's second server writes its own under `<run>/`. It holds both keys (AGENT-10): `page_token`, the key the server was started with, which the suites give their pages and use for the musician's own API calls, and `token`, the tools key, an agent's (`m2`, as the app's `session.json` holds it) |
| scratch `HOME` | one per run (`<run>/testhome`), and one per second server (`<run>/inject/home` and the like). music2 finds its cache, settings and plugins from `HOME` alone, never `XDG_*` |
| temporary folders | run.mjs makes one `--out` folder; suites write only under their `<root>`, `HOME` and project |
| the Chrome profile | puppeteer makes a new one for each browser (`mkdtemp`, `puppeteer_dev_chrome_profile-*`) |
| `--out` folders | one per run, named `<suite>-<kind>` (run.mjs refuses a list naming one twice); a retry goes to `e2e-retry` |
| `CLAP_PATH`, the probe plugin | the plugin files are only read; what Surge XT writes goes to the run's `HOME`. The probe plugin lives in the server's memory (`M2_PROBE=1`) |
| plugin shared memory (`/dev/shm`) | named `/m2-<server's pid>-<n>`, made with `O_EXCL`, removed once both sides map it; the plugin host talks over pipes |
| MIDI and audio | `M2_AUDIO=none`, `M2_MIDI=inject`, `M2_AUDIO_INPUT=inject`: no device is opened |
| Xvfb | only `ph-window` starts one, with `-displayfd`: the X server picks a free display |
| files in the repo | none are written (suites run in `e2e/` but write only to their folders; `ci/check.sh`'s "repo unchanged" row checks). The server reads `web/dist`, `std`, `templates/` and `examples/` from the tree, never writes them |
| a suite's log | each run's own file; a line that comes late is added to it by name, never through a closed descriptor another run may have by then, and a run counts only once its output has ended |

What they do share is CPU time, so a suite's own timing check (`export`'s "the server answers
while exporting" within 300 ms, `s8-tracks`' "within a second or so") is where parallel could hurt.
The evidence below shows none did.

| 2 | 4 | 74 of 74 ok | 3,130 of 3,130 | 2.7 min |

### Tiers and parts (`--tier`, `--shard`)

In short: every pull request runs the PR tier, `all --tier pr` (54 of the 76 runs), split over CI
machines with `--shard`. The other 22 runs are tagged `tier: "nightly"` in `run.mjs`, each with
why, and run every night with all the rest (`ci/check.sh --nightly`: `all`, one at a time).

- `--tier pr` keeps the runs with no tag; `--tier nightly` only the tagged ones. Without `--tier`,
  `all` is every run, as `ci/check.sh` wants.
- A run is tagged for one of two reasons only. **speed**: it judges how fast something happens (a
  bound under 2 s, a rate), so a slow or busy machine fails it with correct code. A wait that
  only fails when something never happens is not one: nearly every suite has those, and they stay.
  **flake**: it failed on correct code in a recorded run (HANDOFF.md's "Known flakes", or the
  open-source audit of 2026-10-21) and the cause isn't fixed. A tagged suite is never weakened to
  move back: fix the cause, then take the tag away.
- `--shard i/n` runs part i of n. The runs are dealt out longest first, by the `s` seconds each
  has in `SUITES`, to the part with the least so far, so the parts take about as long; each part
  keeps the list's order. Every run is in exactly one part: the parts of one `--tier` together are
  that `--tier` without `--shard`.
- `--list` prints the runs that would run and stops (no server, no browser), so the parts can be
  checked:

```sh
node e2e/run.mjs all --tier pr --list | sort > /tmp/one
for i in 1 2; do node e2e/run.mjs all --tier pr --shard $i/2 --list; done | sort | cmp - /tmp/one && echo same
```

- `--no-clap` leaves out the runs that need the test plugins (`live3b`, `ph-window`), for a machine
  without them (CI's Mac), and says so. Without it, such a run is `PART`, never `ok`.
- `--late-sleeps` leaves out the runs tagged `sleeps` (with why), and says so: their clock is a
  sleep (the capture's, the meters' tick), so a machine whose sleeps last longer than they ask fails
  them with correct code, every time. GitHub's Mac runner is one: its sleeps last about four times
  as long. `ci/pr.sh suites` passes it only when `M2_LATE_SLEEPS` is set, as the nightly
  workflow's Mac job sets it; everywhere else they run. The tag says nothing of the run's tier.
  Tagged now: `st-record-fix`, `s8-meters-fix` (both nightly) and `nx-click-fix` (PR tier). The
  Rust tests of the same kind are in `ci/sleeps-tests.txt`.

## Byte-identity of renders

`baseline.sh` renders the pure fixtures, twelve renders in all (full renders of `examples/first-song`,
`examples/resample`, `examples/sounds`, `examples/sampler`, `templates/starter`, `templates/empty`, and
`--from 4 --seconds 6` of each) into a folder with a `SHA256SUMS`:

```sh
e2e/baseline.sh 933f4de /tmp/base-head          # builds m2 at that commit in a temporary worktree
e2e/baseline.sh --tree . /tmp/base-now          # the working tree as it is
diff /tmp/base-head/SHA256SUMS /tmp/base-now/SHA256SUMS
```

A commit from before the `sounds` merge has no `examples/sounds`: the script skips it and says so.

`renders.sha256` is the one record every OS must match (PLAT-4); `ci/check.sh` renders with
`baseline.sh` and checks against it (`cd <out> && shasum -a 256 -c <repo>/e2e/renders.sha256`).

## Where these came from

The suites were written during steps 1–5 in a temporary folder that a reboot wiped; they were
rebuilt from the session transcripts by replaying every Write, Edit and file-touching shell command
in order (the recovery script and its log are not part of the repo). Ported here: paths come from
the arguments and the environment (`E2E_CHROME`, `E2E_REPO`, `E2E_HEADLESS`, set by `run.mjs`)
instead of the old scratch folders, and `chrome.mjs` names the browser for all of them.
